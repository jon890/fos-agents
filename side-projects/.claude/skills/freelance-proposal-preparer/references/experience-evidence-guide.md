# 경험 근거 탐색과 선정 검토

지원자의 실제 경험을 근거에 맞게 선별하고, 발주자가 선택하고 싶은 제안으로 다듬는 기준이다.

## 근거 탐색 순서

사용자가 허용한 범위에서 다음 순서로 확인한다.

1. 사용자가 직접 언급한 프로젝트와 역할
2. 공개 GitHub 저장소의 코드, README, 커밋 기록
3. 개인 작업 폴더의 task, 회고, 설계와 검증 문서
4. 개인 지식 기반의 읽기 전용 검색 결과

경험을 찾기 위해 비공개 정보의 공개 범위를 넓히지 않는다.
회사명, 내부 경로, 고객 정보, 비공개 저장소 링크는 플랫폼 지원문에서 일반화하거나 제외한다.

## 근거 강도와 표현

| 근거 | 확인 기준 | 지원문 표현 |
|---|---|---|
| 직접 구현 | 코드와 커밋에서 동작을 확인할 수 있다. | `개발했습니다`, `구현한 경험이 있습니다` |
| 운영과 개선 | 오류 처리, 성능 개선, 테스트 또는 운영 기록이 있다. | `운영했습니다`, `안정성을 개선했습니다` |
| 설계와 검토 | 문서에는 있으나 구현 근거를 확인하지 못했다. | `설계했습니다`, `검토한 경험이 있습니다` |
| 추정 | 이름이나 짧은 설명만 있고 역할을 확인하지 못했다. | 사용하지 않거나 사용자에게 확인한다. |

직접 구현 근거가 없는데 `운영했다`, `개발했다`고 쓰지 않는다.
설계 문서를 구현 경험으로 올려 쓰지 않는다.

## 과업 관련성 선별

경험은 다음 순서로 고른다.

1. 동일한 대상이나 작업 방식
2. 같은 실패 조건과 운영 문제
3. 납품 품질을 뒷받침하는 보조 기술

예를 들어 공지 감지 과업이라면 다음 경험을 우선한다.

- 사이트 크롤링과 동적 페이지 분석
- 외부 API 폴링과 식별자 중복 방지
- 재시도, 장애 격리, 장시간 실행 안정성
- 저장 응답과 모의 응답을 이용한 회귀 테스트

일반적인 언어와 프레임워크 경험은 직접 관련 경험 뒤에 둔다.
지원문에는 강한 경험 두세 개만 남기고 기술 이름을 길게 나열하지 않는다.

## 포트폴리오와 경험 서술 분리

플랫폼에 등록된 포트폴리오는 해당 과업과 직접 연결될 때만 선택한다.
관련 포트폴리오를 선택하지 않더라도, 코드나 작업 기록으로 확인한 경험은 지원문에 설명할 수 있다.

플랫폼 본문에 외부 URL이 금지되면 저장소 링크를 넣지 않는다.
대신 수행한 동작, 해결한 문제, 이번 과업과 연결되는 이유를 설명한다.
근거 URL과 로컬 문서 위치는 사용자용 HTML의 내부 검토 영역에만 둔다.
HTML을 다운로드하거나 외부에 첨부하는 산출물로 전환할 때는 로컬 경로와 비공개 링크를 제거한다.

## 선정 가능성 검토

독립 검토자는 금액, 기간, 제안문을 함께 보고 `수락`, `조건부 수락`, `거절` 중 하나로 판단한다.

다음 항목을 확인한다.

- 첫 문단에서 직접 관련 경험과 구현 가능성이 보이는가
- 짧은 납기를 검증 산출물과 제한된 범위로 설명하는가
- 개발자가 확인할 내용을 발주사 운영 책임으로 넘기지 않는가
- 외부 제약을 말한 뒤 대체 방식과 실제 확인 약속이 이어지는가
- 테스트 결과, 실행 로그, 결함 수정처럼 신뢰할 수 있는 납품 증거가 있는가
- 관련성이 낮은 경험이나 기술 목록이 핵심 근거를 가리지 않는가

구현 속도의 내부 수단은 지원문에서 강조하지 않는다.
발주자에게는 동작하는 납품물, 검증 결과, 대응 범위를 약속한다.

독립 검토에서 차단 이슈가 나오면 반영한 뒤 다시 확인한다.
최신 사용자가 명시적으로 제출을 요청한 경우에만 플랫폼의 최종 제출 동작을 수행한다.
