# 제안문 작성 기준

플랫폼 지원문을 사람다운 문장으로 작성하는 기준이다.
구현 가능성과 제약을 숨기지 않으면서도 지원 의지를 먼저 전달한다.

## 기본 구성

자유 입력형 지원문은 짧은 자기소개 뒤 세 섹션으로 구성한다.

```text
안녕하세요.
[연차와 직무], [직접 관련 있는 경험]을 바탕으로 아래와 같이 제안드립니다.

<프로젝트 진행 제안>
[구현 가능 여부]
[외부 서비스별 접근 방법]
[개발 중 검증과 운영 중 검증]
[납품 범위와 일정]

<유사 프로젝트 진행 경험>
[동일 경험 여부]
[전이 가능한 실제 경험]

<사용 기술과 툴>
- [실행 환경]
- [언어와 핵심 라이브러리]
- [검증 도구]
- [조건부 대체 기술]
```

플랫폼 예시가 다른 섹션명을 요구하면 이름만 바꾸고 역할은 유지한다.
질문별 답변이나 고정 양식에서는 세 섹션의 역할을 각 답변에 분산한다.

## 프로젝트 진행 제안

첫 문단에서 구현 가능 여부를 말한다.
구조나 기술 목록부터 길게 설명하지 않는다.

외부 서비스가 여러 개면 서비스별 접근 방법과 근거를 나눈다.
공식 API가 있으면 그 장점을 설명한다.
비공식 조회나 브라우저 자동화가 필요하면 가능한 이유와 운영 위험을 함께 쓴다.

성능을 확약할 때는 측정 기준을 분명히 한다.
외부 서비스의 게시 지연, 캐시, 네트워크 상태는 코드가 통제하지 못한다는 점을 설명한다.
같은 문단에서 통제 가능한 목표와 대안을 함께 제시한다.

## 검증 경계

개발 과정에서 확인할 내용은 개발자가 책임지고 직접 검증한다.
지원문에는 실제 응답 구조와 파싱 결과를 개발 과정에서 직접 확인하겠다고 쓴다.

- 실제 응답 형식
- 식별자와 필드 추출
- 정상 요청과 출력
- 저장 응답과 모의 응답으로 재현 가능한 오류

실제 운영에서만 드러나는 내용은 후속 검증으로 구분한다.

- 장시간 반복 요청의 제한
- IP 또는 계정 단위 차단
- 자동화 탐지와 브라우저 자동화 제한
- 외부 서비스의 정책 변경
- 실환경 네트워크 지연

외부 서비스가 자동화를 막을 수 있다는 사실을 숨기지 않는다.
다만 `차단`을 반복해 불안을 키우지 않는다.
운영 중 주기나 조회 방식 조정이 필요할 수 있다는 대응 방향을 함께 쓴다.

## 유사 프로젝트 진행 경험

동일한 프로젝트를 수행하지 않았다면 그대로 밝힌다.
그다음 과업에 직접 도움이 되는 실제 경험을 연결한다.

예를 들어 크롤링 포트폴리오가 없으면 외부 API 연동, 실시간 처리, 오류 복구, 상태 관리 경험을 설명한다.
관련성이 낮은 프로젝트 이름을 나열하지 않는다.

연차, 역할, 기술, 성과는 확인된 사실만 사용한다.
플랫폼이 회사명과 외부 URL을 금지하면 `업무 협업 도구`, `클라우드 서비스`처럼 경험의 성격만 남긴다.

## 사용 기술과 툴

기술 목록은 구현 방향을 설명하는 범위에서 구체적으로 쓴다.
필요 이상의 프레임워크와 라이브러리를 나열하지 않는다.

다음 순서를 권장한다.

- 운영체제와 실행 환경
- 언어와 버전 기준
- 핵심 통신·동시성 도구
- 테스트와 오류 재현 방법
- 출력과 설정 관리
- 조건부 대체 기술

대체 기술은 기본 구현과 구분한다.
예를 들어 직접 HTTP 요청이 기본이라면 브라우저 자동화는 필요할 때만 검토한다고 쓴다.
추가 의존성이나 실행 환경 확인이 필요하면 함께 밝힌다.

## 기본안과 선택지

출력 방식과 실행 환경은 가능한 한 기본안을 먼저 제안한다.
발주사에게 결정만 요구하는 문장으로 끝내지 않는다.

기본안의 예시는 다음과 같다.

- Ubuntu 등 Linux 운영체제
- 최신 안정 버전의 Python 3
- 표준 출력과 JSONL 파일
- 로컬 상태 파일

로컬 HTTP API를 대안으로 제시할 수 있다.
이때 출력 방식은 착수 시 하나로 확정하고 다음 범위를 구분한다.

- 엔드포인트 코드
- 실행 안내
- 서버 배포
- 상시 운영

## 사람다운 문장 점검

지원문은 고객에게 직접 설명하는 말투로 쓴다.
보고서처럼 모든 위험을 나열하거나 구조 설계 용어로 시작하지 않는다.

다음 표현을 줄인다.

- `핵심이라고 판단했습니다`의 반복
- 근거 없는 `완벽하게`, `확실히`, `반드시 가능`
- `아키텍처`, `확장성`, `고도화` 같은 추상어의 연속
- 기능 목록을 문장으로 다시 복사한 표현
- 실제 경험을 숨기는 모호한 포장

한 문단에는 하나의 결론을 둔다.
제약을 말한 다음에는 가능한 범위나 대응 방법을 이어서 설명한다.
