# Freelance Proposal Preparer

외주 공고를 실제 지원 가능한 제안으로 전환한다.
후보 리포트와 제안서는 항상 분리한다.

## 입력과 경계

확인할 자료:

- 공고 상세
- RFP, 첨부 파일, 데모
- 플랫폼 지원 양식과 제한
- 사용자의 실제 포트폴리오

지원서 본문에 외부 연락처나 금지된 URL을 넣지 않는다.
외부 플랫폼에 입력·제출하기 전에는 최신 본문을 채팅과 별도 HTML로 미리보기 한다.
사용자가 최신 미리보기를 확인한 뒤에만 제출한다.

## 작업 흐름

1. 공고와 첨부를 읽고 RFP 요구사항을 다음 축으로 대조한다.

   - 전환 제약과 기존 UI 보존
   - 데이터·공개 API·고객 조회
   - 파일·관리자·알림
   - 보안·성능·검수·인계

2. 요구사항을 기능별 기간과 금액으로 분해한다.
   합계와 공고 예산·일정의 차이를 검산한다.

3. 구현 가능성과 한계를 함께 작성한다.

   - 초기 납품이 다루는 트래픽·데이터 범위
   - 사용자·주문·파일·알림 증가 시 예상 병목
   - 페이지네이션, 지연 로딩, 큐·재시도, 관측 지표, 비용 관리 같은 고도화 방향
   - 초기 구축과 월 유지보수·운영 대응의 계약 경계

4. 지원문은 기능 목록을 반복하지 않는다.
   고객이 얻는 결과를 먼저 쓴다.

   - 기존 경험을 깨지 않는 오픈
   - 중간 데모와 수락 기준
   - 운영자가 인계받을 수 있는 결과물
   - 문제 발생 시 관측·복구 가능한 구조

5. RFP 대조표와 착수 전 확정할 항목을 별도 HTML에 넣는다.
   모순된 요구사항은 숨기지 말고 수락 기준으로 제안한다.

6. 플랫폼 양식을 확인한다.
   금액, 기간, 질문별 글자 제한, 지원 본문 권장 길이, 포트폴리오 선택, 외부 링크 정책을 검증한다.

7. 제출은 최신 미리보기의 금액·기간·질문 답변·지원 본문·포트폴리오가 모두 확인된 뒤에만 수행한다.

## 산출물

별도 HTML에는 아래를 포함한다.

- 제안 금액과 기간
- 기능별 구현 계획과 수락 기준
- RFP 요구사항 대조
- 운영 한계와 고도화 계획
- 착수 전 확정할 사항
- 플랫폼 질문 답변
- 지원 내용
- 제출 전 체크리스트

생성 뒤에는 합계, 질문 글자 수, 지원 본문 길이, HTML 필수 섹션, git diff --check를 확인한다.
