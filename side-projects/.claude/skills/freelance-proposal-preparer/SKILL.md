# Freelance Proposal Preparer

외주 공고를 과장 없이 실제 지원 가능한 제안으로 전환한다.
후보 분석 리포트와 개별 프로젝트 제안서는 분리한다.

## 입력과 경계

작업 전에 다음 자료를 확인한다.

- 공고 원문
- RFP, 첨부 파일, 데모
- 플랫폼 지원 양식과 금지 사항
- 사용자의 실제 경력과 포트폴리오
- 현재 확인 가능한 공식 API, 이용 제한, 운영 조건

시간에 따라 바뀔 수 있는 API 제공 여부, 요청 제한, 이용약관은 최신 공식 자료를 우선 확인한다.
확인하지 못한 사실은 단정하지 않고 착수 전 확인 사항으로 남긴다.
공식 자료는 착수 전 구현 가능성 판단의 근거로 사용한다.
실제 응답 구조와 파싱 결과는 개발 과정에서 직접 검증할 항목으로 분리한다.

플랫폼이 금지한 외부 연락처, 회사명, 회사 홈페이지, 외부 URL은 지원문에 넣지 않는다.
직접 수행하지 않은 경험을 유사 경험처럼 포장하지 않는다.
관련성이 낮은 포트폴리오는 억지로 연결하지 않고 `관련 포트폴리오 없음`을 선택한다.

플랫폼에 입력하기 전 최신 본문을 채팅과 별도 HTML로 미리보기 한다.
사용자와 문안을 검토하기 전에는 플랫폼에 입력하지 않는다.
사용자가 제출 금지를 요청하면 입력을 마쳐도 최종 제출 버튼은 누르지 않는다.

## 작업 흐름

### 공고와 양식 확인

공고 원문과 첨부를 읽고 요구사항, 수용 기준, 스코프 밖 항목을 분리한다.
플랫폼에서 금액, 기간, 본문 길이, 포트폴리오 선택, 외부 링크 정책을 확인한다.

작은 자동화·연동 공고에서도 다음 항목을 빠뜨리지 않는다.

- 최초 실행 때 기존 데이터를 처리하는 방식
- 재시작 후 중복 방지 유지 여부
- 오류 재시도와 대기 방식
- 한 외부 서비스의 장애가 다른 서비스에 미치는 영향
- 출력 방식과 실행 환경

### 구현 가능성 판단

구조 설명보다 구현 가능 여부를 먼저 판단한다.
결론은 `가능`, `조건부 가능`, `현재 근거로 확약 어려움` 중 하나로 분명하게 쓴다.

다음 범위를 구분한다.

- 개발자가 코드로 통제할 수 있는 범위
- 외부 서비스의 지연, 캐시, 정책, 차단처럼 통제할 수 없는 범위
- 착수 전에 확인할 사항
- 개발 과정에서 실제 응답으로 검증할 사항
- 납품 이후 실제 운영하면서 검증할 사항

수용 기준이 외부 서비스 동작까지 포함하면 측정 시작점과 종료점을 다시 정의해 제안한다.
불가능하다는 말만 앞세우지 말고, 어떤 조건이면 어느 수준까지 가능한지 함께 설명한다.

### 범위와 견적 정리

요구사항을 기능별 기간과 금액으로 분해한다.
합계와 공고 예산·일정의 차이를 검산한다.

초기 납품과 다음 항목의 경계를 명확히 나눈다.

- 서버 구축과 배포
- 상시 운영과 장애 대응
- 외부 서비스 변경 대응
- 장기 운영 검증
- 추가 기능과 유지보수

운영 검증이 필요해도 합의한 개발·납품 기간을 임의로 늘리지 않는다.
납품 이후 발주사가 확인할 항목과 개발자가 개발 중 확인할 항목을 구분한다.

### 지원문 작성

[제안문 작성 기준](references/proposal-writing-guide.md)을 읽고 적용한다.

플랫폼이 자유 입력형 본문을 제공하면 다음 세 섹션을 기본으로 사용한다.

- `<프로젝트 진행 제안>`
- `<유사 프로젝트 진행 경험>`
- `<사용 기술과 툴>`

플랫폼이 질문별 답변이나 고정 양식을 요구하면 세 섹션의 역할을 각 답변에 분산한다.
플랫폼 형식을 지키기 위해 섹션 이름은 바꿀 수 있다.

첫 문장에서 연차, 직무, 직접 관련 있는 경험을 짧게 소개해 신뢰를 만든다.
기능 목록이나 구조 설명으로 시작하지 않는다.

스크립트·자동화·데이터 수집 과업에서는 실행 환경, 언어 버전, 출력 방식, 최초 실행 처리, 재시작 중복 방지에 합리적인 기본안을 먼저 제안한다.
발주사 판단이 필요한 부분은 제안한 기본안과 변경 가능한 선택지를 함께 쓴다.

기술과 도구는 실제 납품 범위에 필요한 것만 적는다.
무거운 대체 기술은 기본 구현처럼 쓰지 않고 적용 조건과 추가 의존성을 밝힌다.

### 경험과 포트폴리오 대조

사용자의 실제 경력 근거를 먼저 확인한다.
동일 프로젝트 경험이 없으면 그 사실을 숨기지 않는다.

직접 경험 대신 다음과 같은 전이 가능한 경험을 연결한다.

- 외부 API 응답 파싱
- 실시간 처리
- 재시도와 오류 복구
- 중복 방지와 상태 관리
- 운영 도구와 구조화된 출력

플랫폼에서 회사명이나 외부 URL을 금지하면 경험의 성격만 일반화해 쓴다.
등록된 포트폴리오가 실제 과업과 직접 연결되지 않으면 선택하지 않는다.

### 기본안 선제안

발주사에게 모든 결정을 돌리지 않는다.
공고 범위 안에서 현실적인 기본안을 먼저 제시한다.

예를 들어 작은 Python 자동화 과업에는 다음과 같은 기본안을 검토한다.

- Ubuntu 등 Linux 운영체제
- 최신 안정 버전의 Python 3
- 표준 출력과 JSONL 파일
- 로컬 상태 파일을 이용한 재시작 중복 방지
- 현재 목록을 기준 상태로 저장하고 이후 신규 항목부터 출력

웹앱·관리자·CMS 과업에는 다음 기본안을 검토한다.

- 배포 환경과 운영 주체
- 인증 방식과 관리자 권한
- 데이터 모델과 공개 API 범위
- 파일 저장소와 보관 정책
- 운영 로그와 오류 확인 방법

간단한 로컬 HTTP API를 제안할 때는 출력 방식 중 하나로만 제시한다.
엔드포인트 코드와 실행 안내, 서버 배포, 상시 운영의 범위를 각각 구분한다.

### 검토와 플랫폼 입력

작성한 본문은 별도 `code-reviewer` 또는 `verifier`에게 검토를 맡긴다.
독립 리뷰에서는 다음 항목을 확인한다.

- 확인되지 않은 경험이나 성능 보장
- 지나치게 방어적이거나 불안을 키우는 표현
- 사람보다 템플릿에 가까운 문장
- 금액, 일정, 납품물의 모순
- 플랫폼 금지 사항
- 관련성이 낮은 포트폴리오 연결
- 개발 검증과 운영 검증의 혼동

리뷰 결과를 반영한 최신 본문을 사용자에게 다시 보여준다.
사용자가 문안을 확인한 뒤에만 플랫폼 입력을 진행한다.
최종 제출은 사용자가 명시적으로 요청한 경우에만 수행한다.

## 산출물

별도 HTML에는 다음 내용을 포함한다.

- 제안 금액과 기간
- 구현 가능성 판단
- 기능별 구현 계획과 수락 기준
- RFP 요구사항 대조
- 운영 한계와 이후 대응
- 착수 전 확정할 사항
- 플랫폼 입력값
- 지원 내용 미리보기
- 제출 전 체크리스트

지원 내용 미리보기에는 플랫폼에 붙여 넣을 최신 본문을 그대로 넣는다.
본문과 HTML의 금액, 기간, 포트폴리오 선택이 서로 다르지 않게 유지한다.

## 검증

산출물을 만든 뒤 다음 항목을 확인한다.

- 금액과 기간 합계
- 지원 본문 글자 수
- 세 개의 기본 섹션 또는 동일한 역할을 하는 질문별 답변 구조
- 외부 연락처, 회사명, 외부 URL 포함 여부
- 확인되지 않은 경험과 성능 보장
- 포트폴리오 관련성
- 개발 중 검증과 운영 중 검증의 구분
- HTML 필수 섹션
- 사용자 검토와 최종 제출 상태
- `git diff --check`

## 참고 자료

RFP 범위와 운영 한계 대조에는 [RFP 대조 기준](references/rfp-coverage-checklist.md)을 사용한다.
지원문 구성과 표현에는 [제안문 작성 기준](references/proposal-writing-guide.md)을 사용한다.
