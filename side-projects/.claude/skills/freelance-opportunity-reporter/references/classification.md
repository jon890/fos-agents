# 외주 공고 분류 기준

이 문서는 AI 보조 개발로 수행할 외주 공고를 분류할 때 사용한다.

## 사용자 단계

외주 수행 이력을 먼저 확인한다.

- 외주 0회: 첫 거래, 첫 후기, 일정 준수가 가장 중요한 단계로 본다.
- 외주 이력 보유: 최근 후기와 전환율을 보면서 첫 수주 적합도와 일반 수익성의 비중을 조정한다.

사용자가 외주 0회라고 확인한 경우에는 일반 점수만으로 후보를 정렬하지 않는다.
`첫 수주 적합도`를 함께 계산하고 리포트의 별도 후보군으로 표시한다.

## 잘 맞는 공고

아래 조건이 많을수록 우선 검토한다.

- 원격으로 끝까지 진행할 수 있다.
- 1-4주 안에 의미 있는 첫 납품물을 만들 수 있다.
- 산출물이 명확하다.
- 예시는 대시보드, 관리자 화면, 크롤러, API 연동, AI 요약, 챗봇, 내부 도구, 업무자동화다.
- MVP는 전체가 아니라 일부만 맡을 수 있을 때 후보로 본다.
  백엔드·API·관리자 화면처럼 경계를 그을 수 있는 조각이면 평가하고,
  기획·디자인까지 묶인 MVP 전체 구축은 거절 신호로 본다.
- AI가 아닌 범위에서도 닫힌 백엔드 개발은 적합 후보로 본다.
  - API 서버와 인증·권한
  - 외부 서비스 연동
  - 데이터 수집·정제
  - DB 모델링과 마이그레이션
  - 백오피스 API
  - 기존 서비스 기능 추가·안정화
- 기존 데이터 소스나 단순한 데이터 구조가 있다.
- 클라이언트가 단계별 납품과 검수를 받아들일 수 있다.
- 예산이 QA, 커뮤니케이션, 수정 시간을 감당할 만큼 충분하다.

## 강한 거절 신호

아래 항목이 2개 이상이면 `avoid`로 분류한다.
단, 상주·반상주·현장 작업이 필수인 공고는 하나만 있어도 `avoid`로 분류한다.

- 플랫폼, 마켓플레이스, 모바일 앱 전체를 처음부터 만들어야 한다.
- 상주 또는 풀타임 투입이 필요하다.
- 주 1일 이상 정기 출근, 상주, 반상주, 파견, 현장 테스트가 필요하다.
- 금융, 결제, 의료, 신원 인증, 보안 핵심 로직이 포함된다.
- 기존 레거시 코드를 분석해야만 범위를 알 수 있다.
- 유지보수 책임이 큰데 연간 예산이 낮다.
- 예산이 없거나 0원으로 표시된다.
- 지원자 수가 많고, 우리가 차별화할 지점이 보이지 않는다.
- 와이어프레임 기반 웹 디자인, UI 디자인, 퍼블리싱, HTML/CSS 마크업만 수행한다.
  사용자의 외주 방향과 맞지 않으므로 수집 후보에서 제외한다.
  관리자 화면, 대시보드, 업무자동화, AI/API 연동처럼 실제 기능 구현이 포함된 경우에만 별도로 평가한다.

## 점수 기준

각 항목은 1-5점으로 매긴다.
출처에 명확한 숫자가 있으면 숫자를 그대로 기록한다.

- `fit`: 작은 웹, 자동화, AI 기능, 대시보드, 데이터 도구에 얼마나 가까운지 나타낸다.
- `risk`: 납품과 범위 관리 위험을 나타낸다. 높을수록 위험하다.
- `portfolio`: 공개 또는 익명 포트폴리오로 쓸 가치가 있는지 나타낸다.
- `remote`: 완전 원격이면 5, 비정기 대면 가능성이 있으면 3, 정기 출근·상주·현장 작업이면 1로 둔다.
- `remote_only_pass`: 완전 원격 운영 조건을 통과하면 `true`, 상주·반상주·현장 작업 가능성이 있으면 `false`로 둔다.
  공개 정보만으로 원격 여부가 확정되지 않으면 `null`로 둔다.
  이 필드는 `--remote-only` 점수 계산에서 우선 적용한다.
  `null`인 후보는 점수가 높아도 바로 지원이 아니라 먼저 확인할 후보로 분류한다.

최종 점수 해석:

- 80점 이상: 바로 지원한다.
- 65-79점: 먼저 질문하고 조건이 맞으면 지원한다.
- 50-64점: 먼저 확인할 후보로 보되, 원격과 범위가 확인되지 않으면 지원하지 않는다.
- 50점 미만: 지원하지 않는다.

## 첫 수주 적합도

첫 수주 적합도는 외주 0회인 사용자가 안전하게 첫 거래와 후기를 만들 가능성을 평가한다.
일반 점수의 저예산 감점을 그대로 사용하지 않는다.

다음 조건을 모두 검토한다.

- `scope_clarity`: 납품물과 제외 범위가 얼마나 명확한지 나타낸다.
- `delivery_confidence`: 약속한 기간 안에 검증까지 끝낼 가능성을 나타낸다.
- `experience_match`: 사용자가 근거를 제시할 수 있는 기존 경험과 얼마나 가까운지 나타낸다.
- `reputation_value`: 첫 후기와 다음 제안에 재사용할 사례로서 가치가 있는지 나타낸다.
- `risk`: 약관, 외부 API, 불명확한 검수, 무제한 수정 위험을 나타낸다.

아래 조건이면 첫 수주 후보로 우선 검토한다.

- 기간이 1-14일이다.
- 납품물과 범위 밖 항목이 구분되어 있다.
- 기존 경험으로 구현 가능성을 설명할 수 있다.
- 수정 횟수와 검수 기준을 계약 전에 고정할 수 있다.
- 원격으로 끝낼 수 있거나 착수 전에 확인할 수 있다.

예산이 낮아도 첫 후기의 전략적 가치가 있으면 한 번은 후보가 될 수 있다.
다만 아래 조건이면 첫 수주 후보에서도 제외한다.

- 원격 진행이 불가능하다.
- 약관 위반이나 차단 회피가 구현의 전제다.
- 외부 서비스 상태 때문에 성공 기준을 개발자가 보장할 수 없다.
- 무제한 수정이나 상시 운영 책임이 포함된다.
- 실제 투입 시간과 플랫폼 수수료를 고려하면 완주 품질을 지킬 수 없다.

첫 수주 적합도 해석:

- 80점 이상: 원격과 계약 조건이 확정되면 바로 지원한다.
- 65-79점: 핵심 조건을 먼저 질문하고 답이 닫히면 지원한다.
- 65점 미만: 첫 수주 목적만으로 무리해서 지원하지 않는다.

원격 여부가 `null`이면 점수가 높아도 `clarify-first`로 둔다.
일반 점수보다 첫 수주 적합도가 높으면 `first-win` 관점으로 리포트 앞부분에 제시한다.

## 리포트 적용

최종 HTML 섹션과 순서는 `SKILL.md`의 `결과물 형식`을 따른다.
이 문서는 후보의 평가 관점과 행동 분류만 결정한다.

## 링크 표시

공고명은 상세 페이지 링크로 표시한다.
목록 URL만 확보한 상태로 최종 리포트를 마치지 않는다.
상세 URL을 끝내 확보하지 못하면 `상세 링크 미확인`이라고 적고, 분석 근거가 목록 요약임을 명시한다.
사용자가 HTML 리포트에서 바로 공고를 열어 확인할 수 있어야 한다.
