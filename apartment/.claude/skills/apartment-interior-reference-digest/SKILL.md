# 인테리어 레퍼런스 조사

사용자가 처음 인테리어를 준비한다는 전제에서 사진만 나열하지 않고 비용, 관리, 생활감, 하자 위험과 현재 집 적용성을 비교한다.

## 입력과 단일 출처

- 검색 범위와 평가 기준: `apartment/config/interior-reference-digest.json`
- 확정 결정과 남은 질문: `apartment/docs/interior/*.md`
- 누적 레퍼런스: `apartment/docs/interior/interior-references.md`
- 실행별 산출물: `apartment/data/interior-reference-digest/<date>/`

현재 색상, 자재, 예산과 공사 범위는 설정과 결정 문서에서 읽는다. 이 스킬에 현재 값을 복제하지 않는다.

## 조사와 판단

1. 결정 문서와 설정을 읽고 확정 항목, 현장 확인 항목과 다음 결정을 구분한다.
2. `config.searchQueries`와 `sourcePriority`를 기준으로 오늘의집 프로젝트, 실제 시공 후기, 업체 포트폴리오와 제조사 자료를 검색한다.
3. 유망한 원문을 직접 열고 사진, 시공 범위, 광고성, 출처 신뢰도와 현재 집 적용 가능성을 확인한다.
4. 정확한 단지 자료가 부족할 때만 구조와 조건이 비슷한 사례로 범위를 넓히고 차이를 표시한다.
5. `config.scoringRubric`으로 후보를 비교하되 점수만으로 채택하지 않는다. 결정에 새 정보를 주는 사례를 우선한다.

고정 개수를 채우기 위해 비슷한 사례나 근거가 약한 링크를 추가하지 않는다.

## 산출물

`report.md`에는 다음을 담는다.

- 추천 레퍼런스의 원문, 핵심 특징과 광고성 판단
- 현재 집에 적용할 부분과 적용하지 않을 부분
- 예산, 유지관리와 하자 위험
- 아직 결정하지 않은 항목의 비교 질문과 추천 이유
- 업체나 현장에서 확인할 질문

새 레퍼런스는 기존 안정적 ID 규칙을 따라 `interior-references.md`에 추가한다. 사용자가 결정을 확정하기 전에는 결정 문서에 확정 상태로 기록하지 않는다.

사용자가 결정 현황을 보여 달라고 하면 같은 실행 디렉터리에 `decision-view.html`을 만든다. Markdown 결정 문서가 원본이며 HTML은 표시용이다. 모바일에서 확정 결정, 남은 결정과 현장 확인 항목을 구분하고 링크와 잘림을 실제로 확인한다.

## 비교 질문

선택지 이름만 제시하지 않는다. 가능한 경우 실제 사진이나 제품 자료를 연결하고 다음 차이를 설명한다.

- 초기 비용과 유지 비용
- 청소와 교체 난이도
- 채광, 색감과 생활 흔적
- 시공 오차와 하자 가능성
- 현재 예산, 구조와 공사 범위에 맞는 이유

최근 리포트와 결정 문서를 확인해 이미 확정됐거나 반복된 질문을 다시 올리지 않는다. 같은 날 다시 실행해도 기존 파일의 존재만으로 건너뛰지 않고 새 근거와 다음 결정을 찾는다.

## 경계와 검증

- 블로그 가격은 참고 범위로만 쓰고 현재 견적처럼 단정하지 않는다.
- 썸네일만 보고 사례를 채택하지 않는다.
- 구조 변경, 발코니, 방화, 대피공간, 난방과 내력벽은 전문가와 관리 주체 확인을 구분한다.
- 사용자 승인 없이 업체에 연락하거나 견적을 요청하지 않는다.
- 예약 실행은 외부 전달자가 사용할 요약만 반환하며 메시지 API를 직접 호출하지 않는다.
- 외부 게시를 요청하면 공개 범위를 검사한 뒤 `report-publisher`를 사용한다.

리포트 형식은 `references/report-template.md`를 따른다.
