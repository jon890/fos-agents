# 포지션 제외 판정

5단계에서 `position` 을 골랐을 때만 읽는다.
제외 기준 읽기와 실패 처리는 [본문](../SKILL.md)의 3단계와 5단계를 따른다.

**공고가 제외인지는 코드가 판정한다.** 규칙을 읽고 직접 견주지 않고, 식별자를 만들지도 않는다.
수집기가 쓰는 판정(source 와 식별자, 정규화한 주소, 회사, 회사와 역할, 만료일)을 `check_position_exclusions` 가 그대로 돌린다.

## 호출

후보 공고를 고른 뒤 발견으로 내기 전에 한 번 부른다. 공고는 한 번에 10개까지다.

| 경로 | 호출 |
| --- | --- |
| 직접 호출 | `mcp__career__check_position_exclusions` 를 `{"postings": [...]}` 로 한 번 부른다 |
| 위임 | 같은 연결용 에이전트에 `check_position_exclusions` 한 번만 맡기고 3단계와 같은 방법으로 기다린다. 공고 목록을 `task` 에 적고 결과 JSON 을 바꾸지 말고 그대로 돌려 달라고 한다 |

공고마다 넘기는 칸은 아래와 같다.

| 칸 | 값 |
| --- | --- |
| `url` | 원문을 연 주소 그대로. 직접 정규화하거나 query 를 지우지 않는다 |
| `company`, `title` | 원문에 적힌 회사 이름과 공고 제목 |
| `source`, `identityHash` | 커넥터나 후보 목록이 준 값이 있을 때만 그대로 넘긴다. `source` 만 알면 `source` 만 넘기고, `identityHash` 는 `source` 와 함께만 넘긴다. 없으면 생략한다 |

**`source` 와 `identityHash` 를 주소나 제목에서 만들거나 추측하지 않는다.**
웹 검색과 원문 열기로 찾은 공고에는 보통 두 값이 없다. 그때는 `url`, `company`, `title` 만 넘긴다.
두 값이 없다는 사실이 판정을 막는지는 도구가 정한다.
먼저 살펴보기에는 공고 후보 목록을 읽는 도구가 없어 이 경로의 공고는 보통 두 값 없이 판정된다.

## 결과 읽기

결과의 `results` 는 `postings` 와 같은 순서이고 공고마다 `verdict` 를 가진다.

| `verdict` | 뜻 | 하는 일 |
| --- | --- | --- |
| `clear` | 이 공고에 적용되는 규칙을 모두 비교했고 걸린 것이 없다. `source` 를 모르는 공고는 식별자와 URL 을 함께 가진 규칙을 정규화 URL 로만 비교한다 | 발견으로 낼 수 있다. 제외 기준에서 읽은 회사 이름과 같은 회사로 보이면(법인명과 브랜드명, `(주)` 표기) 내지 않는다 |
| `excluded` | 규칙에 걸린다. `basis` 가 이유 종류다 | 내지 않는다. 이유를 사용자에게 다시 쓰지 않는다 |
| `undeterminable` | 이 공고에 적용되는 규칙을 모두 비교하지 못했다 | 내지 않고 그 공고 판단만 보류한다 |

`undeterminable` 의 `basis` 는 보류한 까닭이다.

| `basis` | 까닭 | 결과 블록에 적는 말 |
| --- | --- | --- |
| `identity-missing` | 식별자로만 비교하는 제외 규칙이 있는데 이 공고의 식별자를 모른다 | 공고 식별자 없이 제외 여부를 판정하지 못해 보류했다 |
| `invalid-url` | 공고 주소를 정규화하지 못했다. https 가 아니거나 계정이 들어 있다 | 공고 주소를 판정하지 못해 보류했다 |
| `rule-unreadable` | 주소를 정규화하지 못하는 제외 규칙이 있다 | 제외 규칙 일부를 해석하지 못해 보류했다 |
| `constraints-hold` | 제외 규칙이나 회사 선호를 읽지 못했다 | 제외 기준 조회 실패로 보류했다 |

보류한 공고는 알릴 발견이 아니다. 같은 영역의 다른 공고는 판정 결과대로 낼 수 있다.

**보류를 적는 자리는 까닭이 정한다.**
`identity-missing`, `invalid-url`, `rule-unreadable` 은 이번 공고의 성질이라 출처 실패가 아니다.
`summary` 에 「공고 N건은 제외 여부를 판정하지 못해 보류했다」 한 줄로 묶어 적고 `sourceFailures` 에는 넣지 않는다.
넣으면 바로 침묵 조건과 이전 값 찾기가 매번 실패한다.
`constraints-hold` 와 호출 실패는 조회 실패이므로 `sourceFailures` 에 적고, 공고마다 쓰지 않고 한 줄로 묶는다.
보류만 있고 알릴 발견이 없으면 `NOTHING_NEW` 다.
`results` 에 없는 공고나 `verdict` 를 읽지 못한 공고는 `undeterminable` 로 본다.
호출이 실패하거나 도구가 없거나 위임이 `CHECK_LIMIT` 로 거절되면 이번에 고른 공고는 모두 보류한다.
이때 `CAREER_UNAUTHORIZED` 는 연결 화면에서 다시 연결해 달라고 적는다.
공부와 동향 조사는 이 판정과 무관하게 이어 간다.

## 직접 호출과 위임

두 경로는 같은 도구와 같은 입력, 같은 결과를 쓴다. 차이는 아래뿐이다.

| 항목 | 직접 호출 | 위임 |
| --- | --- | --- |
| 호출 수 | 도구 호출 한 번 | 위임 한 번과 `agent_status(wait_seconds: 20)` 두 번까지. 그래도 끝나지 않으면 보류한다 |
| 식별 정보 | 입력의 `url`, `source`, `identityHash` 가 그대로 도구에 간다 | 모델이 쓴 `task` 를 연결용 에이전트가 읽고 인자로 옮긴다. 옮기는 값을 바꾸거나 채우지 않게 `task` 에 적힌 값만 쓰라고 한다 |
| 실패 | 도구 오류 코드 | `FAILED`, `CANCELLED`, 계속 `RUNNING`, `CHECK_LIMIT` |

결과가 요청한 공고 수와 다르거나 요청에 없던 `url` 이 있으면 그 결과 전체를 `undeterminable` 로 본다.
