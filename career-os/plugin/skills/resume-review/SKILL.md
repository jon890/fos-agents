# 이력서 평가와 보강

**목표: 심사자가 제품의 문제, 후보자의 판단·역할과 확인된 영향을 이해할 수 있는 이력서를 만들고, 남은 사실 공백을 명시한다.**

문서 평가는 Codex와 Claude Code에서 사용할 수 있다. 기존 실행기를 부를 때는 해당 스킬의 환경 계약을 따른다. 실행기 제약을 이유로 문서에 있는 작성·검토 기준까지 생략하지 않는다.

## 워크플로우 개요

| 단계 | 이름 | 통과 조건 | 기준 |
| --- | --- | --- | --- |
| 1 | 대상과 기준 확정 | 실제 제출 파일과 공고의 작성 안내가 특정됨 | 공고, 지원 디렉터리 |
| 2 | 현재 문서 평가 | 독자가 이해하지 못할 문장과 탈락 사유가 원문 위치와 함께 기록됨 | 기존 채용 리뷰 |
| 3 | 경험 근거 대조 | 문장 문제와 사실 공백이 구분됨 | 기존 주장 검증 모델 |
| 4 | 후보자 인터뷰 | 핵심 공백의 답변 또는 미확인 상태가 기록됨 | 기존 후보자 인터뷰 |
| 5 | 원고 수정 | 확인된 답변과 근거가 수정 문장으로 연결됨 | 기존 작성 기준 |
| 6 | 독립 재평가 | 동일 버전의 문서에 대한 판정과 남은 문제가 기록됨 | 기존 판정 기준 |
| 7 | 새 버전 검토 | 사용자가 원고·변경점·평가 근거를 함께 확인할 수 있음 | 버전별 검토 리포트 |

## 1. 대상과 기준 확정

지원 디렉터리의 `evidence/posting.md`, 현재 원고와 실제 제출 PDF를 읽는다. 공고의 작성 안내를 우선한다. 안내가 없으면 [공통 작성 기준](../resume-preparer/references/resume-writing-style.md)을 적용한다. 후보자의 표현 선호는 [작성 취향](../resume-preparer/references/resume-taste.md)을 따른다.

공고가 요구한 평가 과정을 정리하되, 모든 경험에 형식적인 실험이나 수치를 만들어 넣지 않는다. 진행 중인 경험은 현재까지 내린 판단·검증한 범위와 다음 검증을 구분한다.

## 2. 현재 문서 평가

[독립 채용 리뷰](../resume-preparer/references/hard-review.md)와 [판정 기준](../resume-preparer/references/scoring-rubric.md)을 사용한다. 채용 담당자와 실무 담당자의 독립 판정 방식, 점수와 제출 조건은 이 두 문서가 소유한다. 독립 검토를 실행하지 않았으면 자기 검토를 블라인드 리뷰라고 기록하지 않는다.

대표 경험마다 먼저 다음 질문에 평문으로 답한다. 이력서만으로 답할 수 없으면 누락 위치를 적는다.

- 누가 어떤 일을 하려다 막혔으며, 왜 먼저 해결할 문제였는가?
- 당시 바꿀 수 없었던 제약과 후보자가 직접 선택한 방법은 무엇인가?
- 어떤 대안을 어떻게 비교했고, 무엇으로 결과를 확인했는가?
- 제품이나 사용자의 작업은 실제로 무엇이 달라졌는가?
- 팀의 성과에서 후보자가 맡은 일과 협업으로 해결한 일은 무엇인가?

`AI 같다`고만 판정하지 않는다. 독자가 뜻을 추측해야 하는 명사, 기술 목록으로 끝난 문장, 결과처럼 쓰인 구현 항목을 인용하고 왜 이해하거나 믿기 어려운지 설명한다. 기술 이름을 지운 뒤에도 문제·판단·영향이 남는지 확인한다.

## 3. 경험 근거 대조

[주장 검증 모델](../resume-preparer/references/claim-model.md)로 구현, 소유권, 결과와 경험 깊이를 나누어 판정한다. 프로젝트 자료는 `sources/fos-study/task/`에서 먼저 찾고 부족할 때 원본 코드와 기록을 조회한다. 원본 프로젝트는 변경하지 않는다.

문장만 고치면 되는 문제와 후보자 확인이 필요한 사실을 구분한다. 테스트 통과를 사용자 가치나 모델 정확도 향상으로 바꾸지 않는다. 측정 원본이 없는 과거 수치는 새로 검증한 개선율로 쓰지 않는다. 팀 결과에서 단독 기여를 추정하지 않는다.

## 4. 후보자 인터뷰

[후보자 인터뷰](../application-package-writer/references/candidate-interview-questions.md)를 따른다. 이미 조회 가능한 재직일·연락처·구현 목록을 다시 묻지 않는다. 당시 판단, 우선순위, 검토한 대안, 협업 역할과 결과 확인 방법을 묻는다.

깊은 인터뷰에서는 답변에 따라 다음 질문을 바꿀 수 있도록 한 번에 한 질문씩 한다. 확인한 근거와 질문이 필요한 이유를 짧게 붙이고, 모범 답변을 먼저 제시하지 않는다. `evidence/candidate-interview.md`에 후보자 원문, 해석, 확인 상태와 반영할 문장을 나눈다. 답이 없으면 대기 상태로 두며 경험이 없다고 단정하지 않는다.

## 5. 원고 수정

원고 작성과 PDF 완성은 [resume-preparer](../resume-preparer/SKILL.md), 공고 적합도와 지원 전략은 [application-package-writer](../application-package-writer/SKILL.md)를 재사용한다. 문장 순서는 독자가 경험을 이해하는 흐름으로 정하고, 평가 항목 이름을 이력서의 소제목으로 반복하지 않는다.

원고에서 실제 제품·사용자·본인 역할을 먼저 설명한다. 한 개선 사례는 문제와 제약, 비교·선택, 확인한 변화가 이어지게 쓴다. 코드 내부 이름·근거 장부·미검증 표시는 검토 자료에 두고 제출 본문에는 필요한 한계만 자연스럽게 설명한다.

## 6. 독립 재평가

지원 디렉터리 `review/resume-scorecard.md`에 검토한 파일·버전, 인용한 문제 문장, 근거, 수정 여부와 남은 질문을 기록한다. 점수 산정은 기존 판정 기준, 발견 분류와 변경 후 검토 범위는 기존 독립 채용 리뷰를 따른다. 새 버전은 이전 발견이 실제로 해소됐는지 비교하고, 같은 근거를 표현만 바꿔 점수를 올리지 않는다.

제출 문장이나 공고의 필수조건을 막는 핵심 사실이 미확인이면 `blocked`, 근거는 있지만 필수 문장·배치 수정이 남으면 `revise`로 남긴다. 대표 경험과 필수 검토가 모두 통과할 때 종료한다. 사용자 답변이 필요한 동안은 관련 문장 확정을 기다리며 독립적으로 가능한 근거 확인을 진행한다. 확인되지 않은 성과를 채워 넣거나 스스로 정한 점수에 도달할 때까지 무한 반복하지 않는다.

최종 PDF는 실제 화면을 확인하고 한국어 산출물은 `korean-check`로 점검한다. 사이트 반영과 제출은 기존 승인 경계를 따른다. 이번 평가 요청만으로 지원서를 제출하지 않는다.

## 7. 새 버전 검토

사용자가 버전별 리포트를 요청하면 원고, 이전 버전과의 변경점, 공고 작성 안내별 충족 근거·공백, 채용 담당자·실무 담당자 평가를 같은 버전으로 묶어 보여 준다. 해당 환경의 리포트 형식을 따르고 후보자 자료를 공개 게시하지 않는다. 원고의 사실 확인과 사용자 검토를 거친 뒤 사이트와 제출 파일을 갱신한다.

합격 가능성을 요청받으면 서류 통과와 최종 합격을 구분한다. 채용 데이터로 계산한 확률과 검토자의 주관적 전망을 구분하고, 가정·주요 위험·불확실성을 함께 적는다. 근거가 부족하면 숫자를 확정하지 않는다. 기준 충족 점수나 자기 평가 점수를 합격률로 바꾸지 않는다.
