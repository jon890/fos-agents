# 제출 문서 판정 기준

필수 조건은 각 축에서 개별로 통과해야 한다.
공고와 현재 제출 파일을 처음부터 읽고 각 축을 `pass`, `revise`, `blocked`로 판정한다.

## 판정 축

| 축 | 통과 기준 | 차단 신호 |
| --- | --- | --- |
| 첫 화면과 포지셔닝 | 목표 역할, 경력 수준과 차별점이 빠르게 보인다. | 목표 역할이 충돌하거나 핵심 근거를 찾기 어렵다. |
| 경력 서사와 제품 연결 | 현재 경험이 목표 역할과 사용자 문제로 자연스럽게 이어진다. | 열망이 실제 경험보다 앞서거나 회사 이름만 바꿔도 성립한다. |
| 문제 난도와 소유 범위 | 그 문제가 왜 중요했는지, 당시 제약, 본인 판단과 팀 책임이 구분된다. | 구현 목록만 있고 판단이나 책임 범위가 없다. 중요성이 `중요한`, `핵심적인` 같은 평가어로만 적혀 있다. |
| 기술 결정과 검증 | 대안, 선택 이유, 실패 처리와 결과 확인 방법이 드러난다. | 기술 이름만 나열하거나 결과를 검증한 방법이 없다. |
| 근거와 경험 깊이 | 핵심 주장이 근거 범위 안에 있고 인터뷰에서 확인할 질문으로 이어진다. | 기능 개발을 운영 깊이로 확대하거나 팀 결과를 단독 성과로 쓴다. |
| 정보 구조와 A4 출력 | 중요한 정보가 먼저 나오고 HTML과 PDF가 읽기 쉽다. | 중복, 작은 글자, 페이지 넘침, 겹침이나 잘림이 있다. |
| 공개 안전 | 제출에 필요한 정보만 있고 내부 정보가 없다. | 비공개 경로, 사내 식별자, 기밀 또는 근거 없는 개인정보가 드러난다. |

대표 사례마다 문제, 중요성, 제약, 판단, 결과와 검증을 독립적으로 확인한다.
수치가 붙어 있다는 이유로 그 프로젝트의 핵심이 아닌 사례가 승부처로 올라갔는지도 함께 본다.
한 사례의 강점은 해당 사례의 근거로만 사용한다.
분량은 고정 페이지 수가 아니라 공고 안내, 근거의 양, 중복과 읽기 편의성으로 판단한다.

## 축별 점수

각 축을 통과 여부와 함께 100점 기준으로 매긴다.
`pass` 만으로는 어느 축이 아슬아슬한지 알 수 없고, 고쳐서 얼마나 나아졌는지도 비교할 수 없다.

| 점수 | 뜻 |
| --- | --- |
| 100 | 이 축이 지원의 강점이다. 심사자가 이것 때문에 부른다 |
| 75 | 통과하며 약점이 없다 |
| 50 | 통과하지만 아슬아슬하다. 심사자가 한 번 더 확인해야 한다 |
| 25 | 차단 신호가 있으나 문장이나 구성을 고치면 없앨 수 있다 |
| 0 | 근거 자체가 없다. 후보자 확인이나 새 경험이 필요하다 |

축마다 가중치를 둔다. 서류에서 결과를 정하는 순서다.

| 축 | 가중치 |
| --- | --- |
| 경력 서사와 제품 연결 | 3 |
| 문제 난도와 소유 범위 | 3 |
| 기술 결정과 검증 | 3 |
| 첫 화면과 포지셔닝 | 2 |
| 근거와 경험 깊이 | 2 |
| 정보 구조와 A4 출력 | 1 |
| 공개 안전 | 1 |

총점은 `Σ(점수 × 가중치) ÷ Σ(100 × 가중치) × 100` 으로 계산해 소수 첫째 자리까지 적는다.
공개 안전은 0점이면 다른 축의 점수와 무관하게 제출하지 않는다.

두 블라인드 검토자가 각각 총점을 내고, 검토표에 둘을 나란히 기록한다.
점수는 합격 확률이 아니다. 같은 문서를 고치기 전과 후로 비교하기 위한 값이다.

## 최종 판정

- `pass`: 모든 필수 축이 통과하고 두 블라인드 검토자가 모두 `pass`다.
- `revise`: 문장, 구조, 근거 선택이나 렌더링을 고치면 차단 신호를 없앨 수 있다.
- `blocked`: 후보자 확인이나 새로운 근거 없이는 사실 문제를 해결할 수 없다.

`review/resume-scorecard.md`에는 아래 식별자와 판정 근거를 기록한다.

```markdown
- artifact: `resume.html`
- artifactTextSha256: `<64자리 SHA-256>`
- verdict: `pass|revise|blocked`
```
