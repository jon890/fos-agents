# 이력서 공통 작성 기준

이 파일은 모든 회사의 이력서와 경력기술서에 적용하는 사실성과 표현 기준이다.
공고의 공식 안내와 확인된 업무 근거를 우선하며,
문장을 매끄럽게 만들기 위해 경험 범위를 넓히지 않는다.

## 대표 경험 선택

공고에 작성 안내가 없으면 프로젝트마다 다음 내용을 담는다.

- 해결하려던 문제와 그 중요성
- 쉽게 바꿀 수 없었던 제약
- 본인이 맡은 역할과 직접 내린 판단
- 확인된 결과와 검증 방법

대표 경험은 수치가 있는 사례가 아니라 지원 직무의 핵심 문제를 해결할 가능성을 가장 잘 보여주는 사례로 고른다.
한 프로젝트에 사례가 많으면 가장 중요한 흐름을 앞에 두고 나머지는 줄인다.

## 사실과 주장 범위

제품, 문제, 수행한 작업과 확인한 결과를 직접 쓴다.
기술 이름은 판단과 결과를 이해하는 데 필요할 때만 보완한다.

- 구현한 기능과 운영에서 내린 판단을 구분한다.
- 팀 결과와 본인이 맡은 작업을 구분한다.
- 제품 전체 범위와 특정 개선 사례의 범위를 구분한다.
- 실제로 담당한 수집, 처리, 저장, API와 사용자 기능의 계층을 구분한다.
- 기술을 사용했다는 사실과 숙련도나 운영 경험을 구분한다.

주장의 강도는 [주장 검증 모델](claim-model.md)의 근거 수준을 넘지 않는다.
확인하지 못한 결과는 관찰 범위로 낮추거나 사용자 확인 대상으로 남긴다.

## 수치와 결과

수치는 무엇을 어떤 조건에서 비교했는지 함께 설명한다.
전후 비교는 입력, 실행 조건과 평가 기준이 같을 때만 개선 결과로 사용한다.

- 한 단계의 결과를 전체 시스템의 결과로 확대하지 않는다.
- 일부 표본의 결과는 적용 범위를 함께 밝힌다.
- 평가 방식이 달라진 수치는 같은 기준의 개선으로 표현하지 않는다.
- 인과관계를 확인하지 못한 수치는 관찰 결과로만 쓴다.

지표 이름보다 비교 대상과 발견한 오류를 먼저 설명한다.
내부 구조의 개수보다 무엇을 어떤 기준으로 나눴고 어떤 변경이나 검증이 가능해졌는지를 설명한다.

## 문장과 구성

증상만 적지 말고 업무 목표가 어떻게 막혔는지부터 설명한다.
문제 발견, 판단, 조치와 검증이 이어진 경험은 하나의 흐름으로 쓴다.
같은 사실은 가장 적절한 위치에서 한 번만 설명한다.

기술 목록에는 사용 범위와 판단을 면접에서 설명할 수 있는 항목만 남긴다.
내부 식별자와 비공개 정보는 외부 독자가 이해할 수 있는 제품과 업무 표현으로 바꾼다.

최종 문서는 [독립 채용 리뷰](hard-review.md)와 [판정 기준](scoring-rubric.md)으로 검토한다.
