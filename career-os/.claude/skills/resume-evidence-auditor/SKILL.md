# Resume Evidence Auditor

이력서의 문장별 사실성을 코드와 근거 자료로 감사한다.
그럴듯한 문장보다 검증 가능한 문장을 남긴다.

## 핵심 원칙

- `references/claim-model.md`를 먼저 읽는다.
- 이력서 HTML은 주장 대상이고, 기존 이력서·업무 문서는 근거 후보일 뿐 진실의 최종 출처가 아니다.
- 코드가 존재한다는 사실은 구현 존재만 증명한다. 후보자가 설계·구현했다는 소유권은 별도로 검증한다.
- Git 작성자 기록은 커밋 기여를 증명하지만 단독 설계, 운영 영향과 사업 성과까지 증명하지 않는다.
- 현재 테스트 통과는 현재 코드 동작을 증명하지만 과거 운영 배포와 성과를 증명하지 않는다.
- 문서만 확인된 주장을 `코드 검증 완료`라고 쓰지 않는다.
- 접근할 수 없는 사내 코드는 `문서 근거`, `사용자 확인`, `미검증`을 구분한다.
- 수치, 기간, 단독 소유권과 인과 관계는 일반 기술명보다 더 강한 근거를 요구한다.
- 근거가 없으면 문구를 약화하거나 삭제한다. 빈칸을 추론으로 채우지 않는다.
- 코드와 근거 저장소는 읽기 전용이다. 이력서와 감사 산출물만 수정한다.
- 실제 제출, 업로드와 외부 공개는 하지 않는다.

## 입력

필수:

1. 감사할 이력서 또는 Candidate Brief HTML
2. 후보자 프로필

가능하면 함께 읽는다.

- 같은 지원 디렉터리의 `posting.md`, `candidate-input.md`
- 기존 이력서와 포트폴리오
- `fos-study/task/**` 업무 문서
- 관련 로컬 Git 저장소
- 공개 GitHub 저장소와 패키지 결과물

코드 저장소를 탐색할 때는 저장소 루트의 `AGENTS.md` 또는 `CLAUDE.md`를 먼저 읽는다.
경로를 찾지 못했을 때만 사용자에게 정확한 저장소 위치를 묻는다.

## 산출물

이력서와 같은 디렉터리에 만든다.

- `claim-ledger.json`: 문장별 구현·소유권·성과 검증 상태
- `evidence-audit.md`: 사람이 읽는 판정과 수정 요청
- 사용자가 개선까지 요청한 경우 검증된 문구로 수정한 HTML

`claim-ledger.json`과 `evidence-audit.md`는 내부 검토 자료다.
절대 경로, 사내 코드명과 Git 정보는 제출 HTML에 넣지 않는다.

## 감사 절차

### 1. 사실 주장을 분해한다

HTML에서 다음을 모두 독립 주장으로 추출한다.

- 회사, 팀, 기간과 역할
- `설계했다`, `구현했다`, `담당했다`, `단독` 같은 소유권 주장
- 기술·알고리즘·아키텍처 적용 주장
- 수치, 건수, 기간, 전후 변화
- 장애 원인과 해결책의 인과 관계
- 운영 배포, 안정화, 비용·품질·성능 결과

한 문장에 구현, 소유권과 결과가 함께 있으면 세 주장으로 나눈다.

### 2. 근거 지도를 만든다

각 주장마다 가능한 근거를 다음 순서로 찾는다.

1. 코드 심볼과 설정
2. 해당 동작을 검증하는 테스트
3. Git 커밋·작성자·기간
4. 실행 결과, 벤치마크, 품질 평가와 운영 기록
5. 업무 문서와 기존 이력서
6. 사용자 직접 확인

`rg`로 심볼을 찾고, 관련 파일을 직접 읽어 문맥을 확인한다.
검색 결과의 단어 존재만으로 검증 완료 처리하지 않는다.

### 3. 세 축을 독립 판정한다

각 주장을 다음 세 축으로 평가한다.

- 구현: 실제 코드·테스트·결과물이 존재하는가
- 소유권: 후보자의 기여 범위가 확인되는가
- 결과: 수치·안정화·개선 효과가 측정됐는가

세부 상태와 허용 조합은 `references/claim-model.md`를 따른다.

### 4. 모순과 과장을 찾는다

다음은 최소 `soften` 판정이다.

- 구현은 확인되지만 후보자 소유권을 확인할 수 없는 `직접 설계·구현` 문장
- 업무 문서에만 있고 코드나 테스트에서는 찾지 못한 구체 기술 주장
- 코드에서 최대값·설정값만 찾았는데 실제 처리량처럼 쓴 수치
- 테스트 fixture의 수치를 운영 성과처럼 쓴 문장
- 최신 코드의 기능을 과거부터 운영한 것처럼 확장한 기간
- 상관관계만 있는데 단일 원인으로 확정한 장애 서사

다음은 `remove` 또는 `blocked` 판정이다.

- 코드와 문서가 이력서 문장을 명시적으로 반박한다.
- 존재하지 않는 기술·회사·역할·수치를 추가했다.
- 팀 결과를 개인 단독 성과로 바꿨다.
- 후보자 확인 없이 사업 성과와 인과 관계를 만들었다.

### 5. 문구를 교정한다

- `safe`: 유지한다.
- `soften`: 확인된 범위로 주어·동사·수치를 낮춘다.
- `ask_user`: 후보자만 확인할 수 있는 사실을 한 번에 묻는다.
- `remove`: 제출물에서 삭제한다.

예시:

```text
기존: 전체 플랫폼을 단독 설계해 처리량을 3배 개선했습니다.
근거: 구현 코드 존재, 일부 커밋 작성자 확인, 처리량 측정 근거 없음.
수정: 처리 파이프라인의 병렬 실행과 실패 복구 구조를 구현했습니다.
```

### 6. 원장을 검증한다

```bash
bun career-os/.claude/skills/resume-evidence-auditor/scripts/validate_claim_ledger.ts <claim-ledger.json>
```

검증 실패 항목을 수정한 뒤 최종 판정을 내린다.

## 최종 판정

- `safe`: `unsupported`, `contradicted`, 미해결 `ask_user`가 없고 강한 주장에 충분한 근거가 있다.
- `revise`: 문구 약화 또는 사용자 확인이 필요한 주장이 남아 있다.
- `blocked`: 허위, 모순 또는 근거 없는 핵심 경력이 남아 있다.

## evidence-audit.md 형식

```markdown
# 이력서 증거 감사

## 결론

- 결과: safe|revise|blocked
- 전체 주장: 0개
- 그대로 사용: 0개
- 약화 필요: 0개
- 사용자 확인: 0개
- 삭제: 0개

## 가장 중요한 발견

## 주장별 판정

| ID | 제출 문구 | 구현 | 소유권 | 결과 | 판정 |
| --- | --- | --- | --- | --- | --- |

## 문구 수정

## 코드로 확인하지 못한 경력

## 사용자 확인이 필요한 사실

## 근거 저장소
```

## resume-evaluator 연계

`resume-evaluator`는 최종 점수를 내기 전에 이 감사를 실행한다.
다음 중 하나라도 있으면 높은 디자인·설득력 점수와 무관하게 `pass`를 금지한다.

- `unsupported` 또는 `contradicted`
- 해결되지 않은 핵심 `ask_user`
- 코드 검증 수준보다 강한 제출 문구

## 금지 사항

- 코드의 존재만으로 후보자의 소유권을 만들지 않는다.
- Git 커밋 수만으로 영향도나 실력을 평가하지 않는다.
- 문서의 수치를 코드에서 찾지 못했다는 이유만으로 자동 거짓 판정하지 않는다. `document_only`로 구분한다.
- 사내 저장소 경로, 커밋 해시와 내부 식별자를 제출 HTML에 노출하지 않는다.
- 검증을 위해 운영 시스템, 외부 계정 또는 비공개 API를 호출하지 않는다.
