# 이력서 주장 검증 모델

## 왜 세 축으로 나누는가

같은 문장 안에서도 구현, 소유권과 결과의 근거 수준은 다를 수 있다.

예를 들어 기능 코드와 테스트가 있어도 후보자가 설계했는지는 알 수 없다.
후보자의 커밋이 있어도 그 변경이 운영 비용을 줄였는지는 별도 측정이 필요하다.

## 구현 상태

| 상태 | 의미 |
| --- | --- |
| `code_verified` | 실제 코드와 관련 동작을 직접 확인했다. |
| `test_verified` | 코드와 해당 동작을 검증하는 테스트를 확인했다. |
| `artifact_verified` | 공개 패키지, 배포 결과물 또는 실행 가능한 산출물을 확인했다. |
| `document_only` | 업무 문서나 기존 이력서에서만 확인했다. |
| `user_attested` | 사용자가 직접 사실이라고 확인했다. |
| `not_applicable` | 구현 검증 대상이 아닌 기간·동기 등의 주장이다. |
| `unsupported` | 근거를 찾지 못했다. |
| `contradicted` | 근거가 주장을 반박한다. |

## 소유권 상태

| 상태 | 의미 |
| --- | --- |
| `git_verified` | 후보자 식별 정보와 일치하는 Git 작성 이력을 확인했다. |
| `document_only` | 업무 문서에 후보자 역할이 적혀 있지만 Git으로 확인하지 못했다. |
| `user_attested` | 사용자가 직접 기여 범위를 확인했다. |
| `team_result` | 구현은 확인되지만 개인 소유 범위는 분리되지 않는다. |
| `not_claimed` | 개인 소유권을 주장하지 않는다. |
| `unsupported` | 소유권 근거가 없다. |
| `contradicted` | 다른 작성자 또는 문서가 소유권 주장을 반박한다. |

## 결과 상태

| 상태 | 의미 |
| --- | --- |
| `measured` | 벤치마크, 로그, 품질 평가 또는 전후 수치가 있다. |
| `test_verified` | 결과를 직접 검증하는 테스트가 있다. |
| `documented` | 업무 문서에 결과가 기록돼 있다. |
| `user_attested` | 사용자가 직접 운영 결과를 확인했다. |
| `not_claimed` | 결과나 성과를 주장하지 않는다. |
| `unsupported` | 결과 근거가 없다. |
| `contradicted` | 측정 결과가 주장을 반박한다. |

## 최종 문구 판정

| 판정 | 조건 |
| --- | --- |
| `safe` | 제출 문구의 강도가 세 축의 근거 수준을 넘지 않는다. |
| `soften` | 사실의 일부는 확인되지만 동사·수치·인과가 근거보다 강하다. |
| `ask_user` | 후보자만 확인 가능한 핵심 사실이 결과를 바꾼다. |
| `remove` | 근거가 없거나 모순돼 제출하면 안 된다. |

## 강한 표현 게이트

- `단독`: 소유권 `git_verified`와 역할 문서 또는 사용자 확인이 함께 필요하다.
- `처음부터 설계`: 설계 문서·초기 커밋·사용자 확인 중 두 종류 이상이 필요하다.
- 구체 수치: 수치를 포함한 로그·벤치마크·문서·사용자 확인 중 하나가 필요하다.
- `해결`, `제거`, `안정화`: 결과가 `measured`, `test_verified`, `documented`, `user_attested` 중 하나여야 한다.
- `운영`: 배포 설정, 운영 문서, 릴리스 이력 또는 사용자 확인이 필요하다.

## 근거 우선순위

우선순위가 높다고 다른 근거를 자동 대체하지 않는다.

1. 실행 결과·벤치마크·운영 기록
2. 코드와 동작 테스트
3. Git 작성 이력과 설계 기록
4. 업무 문서
5. 사용자 확인
6. 추론

추론만 있는 주장은 제출 문구로 사용하지 않는다.
