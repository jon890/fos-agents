# 지원 준비

**목표: 공고가 찾는 사람과 후보자의 경험이 부합하는지 채용 심사자 관점에서 판정하고,
부합할 때만 그 근거로 제출 문서와 면접 준비를 만든다.**

부합하면 아래의 결과 문서가 생성된다. 제출과 면접에서 그대로 쓰는 것들이다.


| 받는 것          | 이직 준비에 쓰는 법                      |
| ------------- | -------------------------------- |
| 공고 항목별 적합도 판정 | 어느 경험으로 승부하고 어느 공백을 먼저 말할지 정한다   |
| 지원동기와 승부처     | 지원서 서술형 문항과 면접 첫 답변에 쓴다          |
| 포지션별 면접 질문    | 그 공고의 책임과 내 근거에서 나온 질문으로 미리 연습한다 |
| 보완할 공백과 다음 행동 | 면접 전에 무엇을 채울지 정한다                |
| 검토 화면 하나      | 위를 한 화면에서 보고 제출 여부를 정한다          |


이력서와 경력기술서, 제출 PDF 는 `resume-preparer` 가 이어받아 만든다.

## 비공개 작업본 동기화

[`flow.md`의 「비공개 작업 파일의 목표 흐름」](../../../docs/flow.md#비공개-작업-파일의-목표-흐름)을 `SKILL_NAME=application-package-writer`로 적용한다.

## 근거 원본 최신화 확인

위 동기화가 다루지 않는 `fos-study` 로컬 사본이 원격보다 뒤처졌는지 단계 1로 들어가기 전에 검사한다.
없는 문서는 없는 경험으로 판정되므로, 근거를 읽기 전에 확인한다.
private brain은 `brain-search`로 조회하며 경로로 확인하지 않는다.

검사 명령과 판정별 다음 행동, 당길 때 유의할 점은 [근거 원본 최신화 확인](references/evidence-source-freshness.md)이 소유한다.

## 지원 대상 확인

**공고 링크나 회사와 직무 이름을 인자로 받는다.**

```text
/application-package-writer <공고 URL>
/application-package-writer <회사> <직무>
```

`position-recommender` 리포트의 공고 링크를 그대로 붙여 넣는 것이 기본 경로다.


| 받은 것      | 하는 일                                            |
| --------- | ----------------------------------------------- |
| 공고 URL    | 공식 페이지를 열어 회사와 직무를 읽고 대상 디렉터리를 정한다              |
| 회사와 직무 이름 | 같은 이름의 디렉터리를 찾는다. 없으면 공고 URL 을 한 번 묻는다          |
| 인자 없음     | `brain-search` 로 private brain 의 현재 지원 대상을 확인한다 |


대상 디렉터리는 `applications/<company>/<role>/` 이다.

**대상을 하나로 좁히지 못하면 임의로 고르지 않고 한 가지 질문으로 확정한다.**
brain 에 현재 대상이 없거나 대응하는 디렉터리가 둘 이상일 때가 그 경우다.

## 실행 흐름

**아래 명령은 모두 저장소 루트에서 실행한다.** 경로는 그 자리를 기준으로 적었다.
`resume-preparer` 와 같은 자리여야 8단계에서 이어 부를 때 근거 경로가 같게 풀린다.


| 단계  | 이름        | 하는 일                                          | reference                                               |
| --- | --------- | --------------------------------------------- | ------------------------------------------------------- |
| 1   | 공고 분석     | 공고 원문을 저장하고 판정할 항목으로 나눈다                      | [적합도 판정](references/fit-judgment.md)                    |
| 2   | 근거 수집     | 항목마다 후보자의 실제 경험을 붙이고 그 경험을 어디서 확인했는지 적는다      | [적합도 판정](references/fit-judgment.md)                    |
| 3   | 적합도 판정    | 항목마다 점수 하나와 구분별 가중치를 주고 지원 여부를 결론짓는다           | [적합도 판정](references/fit-judgment.md)                    |
| 4   | 후보자 인터뷰   | 코드와 문서로 확정할 수 없는 동기와 판단, 책임 범위를 후보자에게 직접 묻는다  | [후보자 인터뷰](references/candidate-interview-questions.md)  |
| 5   | 경험과 성장 판정 | 이 자리에서 무엇을 다루게 되고 무엇을 다루지 못하는지 공개 자료로 판정한다    | [경험과 성장 판정](references/growth-judgment.md)              |
| 6   | 지원 전략 작성  | 판정과 인터뷰 답변으로 승부처와 지원동기, 기여 시나리오, 공백 보완 계획을 쓴다 | [지원 준비 품질 기준](references/application-quality-rubric.md) |
| 7   | 사용자 검토    | 초안의 문장이 본인 생각과 같은지 사용자가 직접 확인하고 모순을 없앤다       | [지원 문서 전수 검토](references/full-document-review.md)       |
| 8   | 제출 문서 연결  | `resume-preparer` 를 불러 이력서와 제출 PDF 를 만들게 한다   | [이력서 제출 준비](../resume-preparer/SKILL.md)                |


### 단계 1: 공고 분석

**공고를 항목별로 나눠 채점할 수 있게 만든다.**
항목 하나가 3단계에서 판정 하나와 점수 하나를 받는다.
어떻게 나누는지는 [적합도 판정](references/fit-judgment.md)의 「공고 분석」을 따른다.

만드는 것은 둘이다.


| 산출물      | 자리                                     | 담는 것                                   |
| -------- | -------------------------------------- | -------------------------------------- |
| 공고 원문    | `evidence/posting.md`                  | 공고 원문을 보관한다.                           |
| 분리한 항목 목록 | `evidence/fit.md` 의 「공고 항목별 적합도」 표 첫 열 | 한 행에 요구 하나. 2단계가 근거 열을, 3단계가 점수 열을 채운다 |


먼저 공식 페이지에서 공고 원문을 가져와 저장한다.
공식 URL 과 확인 시각을 함께 적는다. 공고가 닫히면 원문이 사라져 판정 근거가 없어진다.

적합도 표에 올리지 않는 것 중 아래는 `evidence/posting.md` 에 따로 표시한다. 뒤 단계가 그대로 받아 쓴다.


| 뽑을 것                              | 어디서 쓰나                      |
| --------------------------------- | --------------------------- |
| 이 자리가 해결하려는 문제와 그 문제를 겪는 사람       | 4단계 지원동기 질문과 6단계 기여 시나리오    |
| 트래픽과 데이터, 사용자 수 같은 규모 수치          | 5단계가 이 자리의 성격을 판정한다         |
| 이력서 작성 안내와 전형 단계                  | 8단계 제출물 형식                  |
| 공식 문화 기준 중 이 포지션의 판단과 행동을 구분하는 항목 | 4단계 문화 질문과 6단계 「회사 문화와의 연결」 |


**규모 수치가 공고에 없으면 없다고 적는다.**

**통과 조건:** [적합도 판정](references/fit-judgment.md)의 「공고 분석」 통과 조건을 만족한다.

### 단계 2: 근거 수집

**1단계가 나눈 항목마다 후보자의 실제 경험을 붙이고, 붙일 것이 없으면 없다고 적는다.**
어느 자료를 어떤 순서로 읽고 무엇을 기록하는지는 [적합도 판정](references/fit-judgment.md)의 「근거 수집」을 따른다.

만드는 것은 둘이다.

| 산출물 | 자리 | 담는 것 |
| --- | --- | --- |
| 항목별 근거 | `evidence/fit.md` 「공고 항목별 적합도」 표의 근거 열 | 확인한 경험과 확인한 위치. 못 찾았으면 어느 자료를 보고 못 찾았는지. 3단계가 이 열을 읽고 점수 열을 채운다 |
| 회사 공개 자료 | `evidence/fit.md` 「공개 자료로 확인한 팀과 인접 사례」 | 팀의 공식 정보와 인접 조직의 사례. 5단계의 성장 판정과 6단계의 문화 연결이 이어받는다 |

**기존 경력기술서의 문장은 그 자체로 근거가 아니다.**
`sources/fos-study/task/` 와 로컬 프로젝트에서 확인하지 못하면 사실로 확정하지 않고 `사용자 확인` 으로 남긴다.

**통과 조건:** [적합도 판정](references/fit-judgment.md)의 「근거 수집」 통과 조건을 만족하고, 위 산출물 둘이 모두 있다.

### 단계 3: 적합도 판정

**항목마다 판정 하나를 주고 총점을 내 지원 여부를 결론짓는다.**
판정 값과 판단 기준, 점수를 정하는 방식은 [적합도 판정](references/fit-judgment.md)을 따른다.

만드는 것은 셋이다.

| 산출물 | 자리 | 담는 것 |
| --- | --- | --- |
| 항목별 점수 | `evidence/fit.md` 「공고 항목별 적합도」 표의 점수 열 | 2단계의 근거 열을 읽고 0부터 100 사이 값 하나. 점수가 낮게 남은 항목은 6단계 「보완할 공백」이 그대로 받는다 |
| 구분별 가중치 | `evidence/fit.md` 의 「구분별 가중치」 표 | 공고가 무겁게 보는 구분에 더 큰 값. 보통 「주요 업무」가 가장 무겁다 |
| 지원 여부 | `evidence/fit.md` 의 「결론」 | 지원하는지, 무엇이 강하고 무엇이 약한지. 5단계와 6단계가 여기서 승부처를 고른다 |

**소계와 총점은 적지 않는다.** 행별 점수와 가중치로 화면이 계산한다.
계산은 [scripts/fit_score.ts](scripts/fit_score.ts)가 소유한다.

```markdown
| 공고 구분 | 가중치 |
| --- | --- |
| 주요 업무 | 3 |
| 기대 경험 | 2 |
| 우대 경험 | 1 |
```



**부합하지 않는다는 판정도 산출물이다.**
제출 문서 작성으로 넘어가지 않고 「결론」에 아래 넷을 남긴다.


| 남길 것      | 내용                                          |
| --------- | ------------------------------------------- |
| 막은 항목     | 어느 공고 항목이 `공백` 이라 막혔는지. 총점이 아니라 항목 이름으로 적는다 |
| 채우는 방법    | 그 공백을 채우려면 무엇을 해야 하는지와 어느 정도 걸리는지           |
| 지금 통하는 자리 | 같은 회사나 인접 직무 중 현재 근거로 자격을 채우는 공고가 있는지       |
| 다시 볼 시점   | 공고가 다시 열릴 때인지, 특정 경험이 쌓인 뒤인지                |


채우는 방법은 확인한 근거에서 나와야 한다.
「대규모 트래픽 경험을 쌓는다」처럼 실행할 수 없는 문장 대신
「인덱스와 실행 계획을 근거로 쿼리를 개선한 사례를 하나 만든다」처럼 다음 행동으로 적는다.

**통과 조건:** [적합도 판정](references/fit-judgment.md)의 「판정 기준」 통과 조건을 만족하고,
위 산출물 셋이 모두 있다. 부합하지 않는다고 결론했다면 위 표의 넷을 남겼다.

### 단계 4: 후보자 인터뷰

**문서로 확정할 수 없는 것을 후보자에게 직접 묻고, 받은 답과 받지 못한 답을 나눠 적는다.**
무엇을 묻고 어떻게 묶는지는 [후보자 인터뷰](references/candidate-interview-questions.md)를 따른다.

만드는 것은 둘이다.


| 산출물    | 자리                                           | 담는 것                                               |
| ------ | -------------------------------------------- | -------------------------------------------------- |
| 확보된 답변 | `evidence/candidate-interview.md` 의 「확보된 답변」 | 질문, 후보자 원문, 정리한 핵심을 나눠 적는다. 6단계가 지원동기와 승부처를 여기서 쓴다 |
| 미확인 질문 | `evidence/candidate-interview.md` 의 「미확인 질문」 | 아직 답을 받지 못한 질문과 그 답이 어느 문장을 바꾸는지                   |


**3단계가 `사용자 확인` 으로 둔 행을 여기서 닫는다.**
답을 받으면 적합도 표의 점수 열로 돌아가 다시 매기고 소계와 총점을 다시 낸다.
그 행은 점수 계산에서 빠져 있으므로, 닫지 않으면 총점이 일부 항목만 반영한 값으로 남는다.

**통과 조건:** 제출 문구를 바꿀 미확인 항목이 없다.
지원동기를 쓸 넷의 답을 받았다.
이 회사와 제품에 끌리는 이유, 풀고 싶은 사용자 문제, 바로 기여할 경험과 본인 역할, 약한 영역과 보완 방법이다.
남았다면 `evidence/status.md` 의 `human-confirmation` 을 `needs_input` 으로 두고 확인을 기다린다.

### 단계 5: 경험과 성장 판정

**이 자리에서 무엇을 다루게 되고 무엇을 다루지 못하는지 공개 자료로 판정한다.**
**건너뛸 수 있는 단계다.** 후보자가 이 회사에서 무엇을 배울 수 있는지 물었거나
같은 회사에 성격이 다른 공고가 둘 이상 열려 있을 때만 한다.
적합도 판정이 공고 요구와 후보자 근거가 맞닿은 정도를 재는 것과 달리,
이 판정은 지원 여부와 지원 순서를 정하는 근거를 만든다.
판정 항목과 자료를 찾는 순서, 통과 조건은 [경험과 성장 판정](references/growth-judgment.md)을 따른다.

만드는 것은 하나다.

| 산출물 | 자리 | 담는 것 |
| --- | --- | --- |
| 얻을 것과 얻지 못할 것 | `evidence/strategy.md` 의 「이 자리에서 얻을 경험과 성장」 | 하위 절 다섯. 6단계의 「보완할 공백」이 「여기서 얻기 어려운 것」을 이어받는다 |

약한 축은 4단계에서 후보자가 밝힌 약한 영역에서 가져온다.
같은 회사에 다른 공고가 열려 있으면 그 공고의 주요 업무도 읽어 같은 대조를 붙인다.
어느 쪽이 약한 축을 채우는지를 `evidence/fit.md` 의 「결론」에 적는다. 그것이 지원 순서다.

**통과 조건:** [경험과 성장 판정](references/growth-judgment.md)의 통과 조건을 만족한다.

### 단계 6: 지원 전략 작성

**1단계부터 5단계까지 모은 것으로 제출과 면접에 쓸 문장을 쓴다.**
문장의 품질 기준과 `readiness` 값은 [지원 준비 품질 기준](references/application-quality-rubric.md)을 따른다.

만드는 것은 셋이다.

| 산출물 | 자리 | 담는 것 |
| --- | --- | --- |
| 지원 전략 | `evidence/strategy.md` | 아래 표의 여섯 절 |
| 포지션별 면접 질문 | `evidence/interview-questions.json` | 공고 책임, 근거 방어, 경험 공백 셋에서 만든 질문 |
| 준비 상태 | `evidence/status.md` 의 준비 상태 세 줄 | `readiness`, `evidence`, `human-confirmation` |

절마다 받아 쓸 것이 정해져 있다. 새로 지어내는 자리가 아니다.

| 절 | 받아 쓰는 것 |
| --- | --- |
| 이 포지션에서의 승부처 | 3단계 「결론」의 강한 축과 4단계의 대표 사례 |
| 지원동기 | 4단계 「확보된 답변」. 후보자 원문에 없는 동기를 만들지 않는다 |
| 입사 후 기여 시나리오 | 1단계가 뽑은 이 자리가 해결하려는 문제와 그 문제를 겪는 사람 |
| 보완할 공백 | 3단계의 `공백` 판정과 5단계의 「여기서 얻기 어려운 것」 |
| 회사 문화와의 연결 | 1단계가 `posting.md` 에 남긴 문화 기준과 4단계의 행동 사례 |
| 면접에서 검증받을 내용 | 3단계의 `공백` 과 4단계에서 설명이 막힌 사례 |

지원서 자동 입력을 준비할 때만 `evidence/application-form.json` 을 만든다.
private brain 에서 확인한 공통 프로필의 현재 값, 회사별 입력 선택, 첨부 파일,
서술형 질문과 답변을 한 번의 제출 스냅샷으로 묶는다.
최종 제출 버튼은 사용자 승인 전에 누르지 않는다. 이 계약이 그것을 강제한다.

**통과 조건:** 위 산출물 셋이 있고, 여섯 절이 각각 받아 쓸 것에 연결된다.

### 단계 7: 사용자 검토

**보여주기 전에 전수 검토하고, 후보자만 확정할 수 있는 것만 사용자에게 묻는다.**
무엇을 어떤 순서로 보는지는 [지원 문서 전수 검토](references/full-document-review.md)를 따른다.

순서가 있다. 검토가 먼저다.

1. 외부에 나갈 문장을 전수 검토한다
2. 문서와 코드로 바로잡을 수 있는 표현은 묻지 않고 고친다
3. 남은 것만 초안과 함께 사용자에게 보여주고 묻는다

사용자가 직접 확인하는 다섯이다.

1. 지원동기가 실제 본인 생각과 같은가?
2. 본인 역할과 팀 역할이 정확히 구분됐는가?
3. 가장 강한 사례가 공고의 핵심 문제와 연결되는가?
4. 약한 영역을 숨기지 않고 전환 가능한 경험을 설명했는가?
5. 입사 후 기여 시나리오가 제품 사용자에게 닿는가?

답변은 `evidence/candidate-interview.md` 에 반영하고 지원 판단과 문구를 갱신한다.
**한 문장을 정정하면 같은 경험을 가리키는 모든 문서를 찾는다.** 같은 범위 오류가 다른 자리에도 있다.

**통과 조건:** 사용자가 위 다섯을 확인했고, 공고 원문과 답변, 제출 문구 사이에 해결하지 않은 모순이 없다.
끝났으면 `evidence/status.md` 의 `human-confirmation` 을 `complete` 로 바꾼다.

### 단계 8: 제출 문서 연결

**`resume-preparer` 를 불러 제출 문서를 만들게 하고, 검토 화면을 만든다.**
같은 사용자 요청 안에서 부른다.

이력서와 경력기술서 작성, 근거 감사, 리뷰와 렌더 검증, 제출 묶음 생성은 `resume-preparer` 가 소유한다.
**1단계가 `evidence/posting.md` 에 남긴 이력서 작성 안내와 전형 단계를 함께 넘긴다.**
제출 파일을 몇 개로 낼지가 그것으로 정해진다.

제출 문서가 준비되면 검사하고 화면을 만든다.

```bash
bun career-os/.claude/skills/application-package-writer/scripts/validate_application_package.ts <application-directory>
bun career-os/.claude/skills/application-package-writer/scripts/render_application_package.ts <application-directory>
```

검증기는 제출 문서와 지원서 답변에 내부 정보가 남았는지만 본다.
화면은 `evidence/` 의 `status.md`, `fit.md`, `strategy.md` 를 이어 붙여 `application-package.html` 을 만든다.

사용자만 확정할 수 있는 지원동기나 사실이 남으면 `needs_user_input` 에서 멈춘다.

**통과 조건:** 전체 지원 요청이면 `resume-preparer` 의 결과를 준비 상태에 반영하고 `application-package.html` 을 만들었다.
지원 전략만 요청했다면 이력서 준비 상태와 다음 행동을 `evidence/status.md` 에 남겼다.

## 산출물 계약

층별 파일 배치는 `career-os/docs/data-schema.md`의 「지원 패키지」가 소유한다.

세 파일이 아래 절을 나눠 담는다. 어느 파일에 어느 절이 가는지가 계약이다.


| 파일                     | 절                                                                                    | 채우는 단계  |
| ---------------------- | ------------------------------------------------------------------------------------ | ------- |
| `evidence/fit.md`      | 결론, 공고 항목별 적합도, 구분별 가중치, 공개 자료로 확인한 팀과 인접 사례 | 1, 2, 3, 5 |
| `evidence/strategy.md` | 이 포지션에서의 승부처, 지원동기, 입사 후 기여 시나리오, 이 자리에서 얻을 경험과 성장, 보완할 공백, 회사 문화와의 연결, 면접에서 검증받을 내용 | 5, 6    |
| `evidence/status.md`   | 준비 상태 세 줄, 제출 준비 상태, 사용자 확인 필요, 다음 행동                                                | 3, 6, 7, 8    |


절 순서도 계약이다.
「이 자리에서 얻을 경험과 성장」은 「입사 후 기여 시나리오」 뒤, 「보완할 공백」 앞에 둔다.
얻기 어려운 것이 곧 보완할 공백이므로 두 절을 이어 읽게 한다.

### 공고 항목별 적합도

공고 항목 하나에 한 행을 준다.
머리행은 `공고 항목`, `공고 구분`, `근거`, `점수` 넷이다. 이름으로 열을 찾으므로 순서는 자유다.
점수는 0부터 100 사이 값 하나이며 그 값을 정한 이유를 근거 열에 적는다.

- `evidence/posting.md`의 주요 업무, 기대 경험과 우대 경험을 항목 단위로 모두 담는다. 요약해 합치지 않는다.
- 각 행은 공고 항목 원문의 요지, 그 항목이 어느 구분에서 왔는지, 연결할 근거와 점수를 담는다.
- 근거가 여럿이면 `- ` 로 시작하는 항목을 `<br>` 로 이어 목록으로 만든다.
- 점수와 판단 기준은 [적합도 판정](references/fit-judgment.md)을 따른다.
- 점수가 낮게 남은 항목은 「보완할 공백」 절과 같은 내용을 가리켜야 한다.

### 공개 자료로 확인한 팀과 인접 사례

- 같은 팀의 공식 정보와 인접 조직의 사례를 행에서 구분한다.
- 각 행은 자료 링크, 확인한 범위, 지원 준비에 쓰는 관점을 담는다.
- 공고 페이지에 외부 링크가 없으면 직접 찾은 자료임을 밝힌다.

### 이 자리에서 얻을 경험과 성장

판단 기준은 [경험과 성장 판정](references/growth-judgment.md)을 따른다.
이 절은 선택 절이다.
후보자가 이 회사에서 무엇을 배울 수 있는지 물었거나 같은 회사에 성격이 다른 공고가 둘 이상 열려 있으면 채운다.

채우면 아래 하위 절 다섯을 이 순서로 둔다.

```markdown
### 서비스가 커질 여지
### 경쟁 서비스와 이 서비스의 위치
### 경험할 수 있는 트래픽의 성격
### 여기서 얻기 쉬운 것
### 여기서 얻기 어려운 것
```

각 하위 절이 담을 것은 위 reference가 소유한다.

`면접에서 검증받을 내용`을 작성한 뒤 다음 세 출처로 질문을 구조화한다.

- `posting_requirement`: 공고가 직접 요구하는 책임과 설계 판단
- `evidence_defense`: 이력서와 경력기술서의 핵심 경험을 방어하는 질문
- `experience_gap`: 직접 해보지 않은 영역과 모호한 근거를 확인하는 질문

질문은 `evidence/interview-questions.json` 하나에 저장하고 다음 명령으로 검증한다.

```bash
bun career-os/scripts/interview-drill/application_question_schema.ts <application-directory>
```

각 질문에는 답변에서 확인할 신호와 `evidenceBoundary`를 함께 기록한다.
공백 질문의 답변 신호는 경험을 꾸미는 모범 답안이 아니라 설계 원칙, 인접 근거와 학습 경계를 확인해야 한다.

첫 10줄 안에 아래 상태를 기록한다.

```markdown
- readiness: <값>
- evidence: <값>
- human-confirmation: <값>
```

세 줄의 허용값과 뜻은 [`data-schema.md`의 「적합도 판정과 점수」](../../../docs/data-schema.md#적합도-판정과-점수)가 소유한다.
`human-confirmation`이 `needs_input`이면 `readiness`를 `ready`로 둘 수 없다.

## 사용자에게 주는 결과

사용자가 가장 먼저 볼 파일은 `application-package.html`이다.
이 화면은 `evidence/` 의 `status.md`, `fit.md`, `strategy.md` 를 이어 붙여 만들며 다음 질문에 한 화면 안에서 답해야 한다.

- 이 공고에 지원할 가치가 있는가?
- 회사와 팀은 어떤 사람을 찾고 있는가?
- 내 경험 중 무엇으로 승부할 수 있는가?
- 어떤 공백을 정직하게 설명해야 하는가?
- 여기서 무엇을 경험하고 무엇을 얻지 못하는가?
- 이력서와 면접에서 무엇을 검증받아야 하는가?
- 다음 행동은 무엇인가?
