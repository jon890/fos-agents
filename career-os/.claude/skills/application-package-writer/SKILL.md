# 지원 준비

**목표: 공고가 찾는 사람과 후보자의 경험이 부합하는지 채용 심사자 관점에서 판정하고,
부합할 때만 그 근거로 제출 문서와 면접 준비를 만든다.**

부합하면 아래를 받는다. 제출과 면접에서 그대로 쓰는 것들이다.


| 받는 것          | 이직 준비에 쓰는 법                      |
| ------------- | -------------------------------- |
| 공고 항목별 적합도 판정 | 어느 경험으로 승부하고 어느 공백을 먼저 말할지 정한다   |
| 지원동기와 승부처     | 지원서 서술형 문항과 면접 첫 답변에 쓴다          |
| 포지션별 면접 질문    | 그 공고의 책임과 내 근거에서 나온 질문으로 미리 연습한다 |
| 보완할 공백과 다음 행동 | 면접 전에 무엇을 채울지 정한다                |
| 검토 화면 하나      | 위를 한 화면에서 보고 제출 여부를 정한다          |


이력서와 경력기술서, 제출 PDF 는 `resume-preparer` 가 이어받아 만든다.

## 비공개 작업본 동기화

[`flow.md`의 「비공개 작업 파일의 목표 흐름」](../../../docs/flow.md#비공개-작업-파일의-목표-흐름)을 `SKILL_NAME=application-package-writer`로 적용한다.

## 지원 대상 확인

**공고 링크나 회사와 직무 이름을 인자로 받는다.**

```text
/application-package-writer <공고 URL>
/application-package-writer <회사> <직무>
```

`position-recommender` 리포트의 공고 링크를 그대로 붙여 넣는 것이 기본 경로다.


| 받은 것      | 하는 일                                            |
| --------- | ----------------------------------------------- |
| 공고 URL    | 공식 페이지를 열어 회사와 직무를 읽고 대상 디렉터리를 정한다              |
| 회사와 직무 이름 | 같은 이름의 디렉터리를 찾는다. 없으면 공고 URL 을 한 번 묻는다          |
| 인자 없음     | `brain-search` 로 private brain 의 현재 지원 대상을 확인한다 |


대상 디렉터리는 `applications/<company>/<role>/` 이다.

## 실행 흐름

**아래 명령은 모두 `career-os` 디렉터리에서 실행한다.** 경로는 그 자리를 기준으로 적었다.


| 단계  | 이름        | 하는 일                                          | reference                                               |
| --- | --------- | --------------------------------------------- | ------------------------------------------------------- |
| 1   | 공고 분석     | 공고 원문을 저장하고 판정할 항목으로 나눈다                      | [적합도 판정](references/fit-judgment.md)                    |
| 2   | 근거 수집     | 항목마다 후보자의 실제 경험을 붙이고 그 경험을 어디서 확인했는지 적는다      | [적합도 판정](references/fit-judgment.md)                    |
| 3   | 적합도 판정    | 항목마다 판정 하나를 주고 구분별 소계와 총점을 내 지원 여부를 결론짓는다     | [적합도 판정](references/fit-judgment.md)                    |
| 4   | 후보자 인터뷰   | 코드와 문서로 확정할 수 없는 동기와 판단, 책임 범위를 후보자에게 직접 묻는다  | [후보자 인터뷰](references/candidate-interview-questions.md)  |
| 5   | 경험과 성장 판정 | 이 자리에서 무엇을 다루게 되고 무엇을 다루지 못하는지 공개 자료로 판정한다    | [경험과 성장 판정](references/growth-judgment.md)              |
| 6   | 지원 전략 작성  | 판정과 인터뷰 답변으로 승부처와 지원동기, 기여 시나리오, 공백 보완 계획을 쓴다 | [지원 준비 품질 기준](references/application-quality-rubric.md) |
| 7   | 사용자 검토    | 초안의 문장이 본인 생각과 같은지 사용자가 직접 확인하고 모순을 없앤다       | [지원 문서 전수 검토](references/full-document-review.md)       |
| 8   | 제출 문서 연결  | `resume-preparer` 를 불러 이력서와 제출 PDF 를 만들게 한다   | [이력서 제출 준비](../resume-preparer/SKILL.md)                |


### 단계 1: 공고 분석

**공고를 항목별로 나눠 채점할 수 있게 만든다.**
항목 하나가 3단계에서 판정 하나와 점수 하나를 받는다.
어떻게 나누는지는 [적합도 판정](references/fit-judgment.md)의 「공고 분석」을 따른다.

만드는 것은 둘이다.


| 산출물      | 자리                                     | 담는 것                                        |
| -------- | -------------------------------------- | ------------------------------------------- |
| 공고 원문    | `evidence/posting.md`                  | 공고 자체의 절 구조를 그대로 둔다. 판단을 가르는 낱말은 원문 표현을 남긴다 |
| 쪼갠 항목 목록 | `evidence/fit.md` 의 「공고 항목별 적합도」 표 첫 열 | 한 행에 요구 하나. 2단계가 근거 열을, 3단계가 판정 열을 채운다      |


먼저 공식 페이지에서 공고 원문을 가져와 저장한다.
공식 URL 과 확인 시각을 함께 적는다. 공고가 닫히면 원문이 사라져 판정 근거가 없어진다.

항목을 나누면서 아래를 따로 표시한다. 뒤 단계가 그대로 받아 쓴다.


| 뽑을 것                             | 어디서 쓰나                      |
| -------------------------------- | --------------------------- |
| 주요 업무, 기대 경험, 우대 경험 중 어느 구분인지    | 3단계가 구분마다 가중치를 다르게 준다       |
| 이 자리가 푸는 문제와 그 문제를 겪는 사람         | 4단계 지원동기 질문과 6단계 기여 시나리오    |
| 트래픽과 데이터, 사용자 수 같은 규모 수치         | 5단계가 이 자리의 성격을 가른다          |
| 이력서 작성 안내와 전형 단계                 | 8단계 제출물 형식                  |
| 공식 문화 기준 중 이 포지션의 판단과 행동을 가르는 항목 | 4단계 문화 질문과 6단계 「회사 문화와의 연결」 |


**규모 수치가 공고에 없으면 없다고 적는다.**

**통과 조건:** [적합도 판정](references/fit-judgment.md)의 「공고 분석」 통과 조건을 만족한다.

### 단계 2: 근거 수집

**1단계가 나눈 항목마다 후보자의 실제 경험을 붙이고, 붙일 것이 없으면 없다고 적는다.**
어느 자료를 어떤 순서로 읽고 무엇을 기록하는지는 [적합도 판정](references/fit-judgment.md)의 「근거 수집」을 따른다.

만드는 것은 둘이다.

| 산출물 | 자리 | 담는 것 |
| --- | --- | --- |
| 항목별 근거 | `evidence/fit.md` 「공고 항목별 적합도」 표의 근거 열 | 확인한 경험과 확인한 위치. 못 찾았으면 어느 자료를 보고 못 찾았는지. 3단계가 이 열을 읽고 판정 열을 채운다 |
| 회사 공개 자료 | `evidence/fit.md` 「공개 자료로 확인한 팀과 인접 사례」 | 팀의 공식 정보와 인접 조직의 사례. 5단계의 성장 판정과 6단계의 문화 연결이 이어받는다 |

**기존 경력기술서의 문장은 그 자체로 근거가 아니다.**
`sources/fos-study/task/` 와 로컬 프로젝트에서 확인하지 못하면 사실로 확정하지 않고 `사용자 확인` 으로 남긴다.

**통과 조건:** [적합도 판정](references/fit-judgment.md)의 「근거 수집」 통과 조건을 만족하고, 위 산출물 둘이 모두 있다.

### 단계 3: 적합도 판정

**항목마다 판정 하나를 주고 총점을 내 지원 여부를 결론짓는다.**
판정 값과 점수, 가중치와 계산식은 [`data-schema.md`의 「적합도 판정과 점수」](../../../docs/data-schema.md#적합도-판정과-점수),
판단 기준은 [적합도 판정](references/fit-judgment.md)을 따른다.

**점수는 직접 계산하고 어떻게 계산했는지 남긴다.**
`evidence/fit.md` 의 「소계와 총점」 절에 판정별 개수, 구분별 소계, 총점을 적고 계산식을 함께 보인다.


화면이 원으로 보여줄 값은 `evidence/status.md` 머리에 적는다.

```markdown
- 적합도 총점: 78.9
- 주요 업무 소계: 75.0
- 기대 경험 소계: 100.0
- 우대 경험 소계: 83.3
```

부합하지 않으면 제출 문서 작성으로 연결하지 않는다.

**부합하지 않는다는 판정도 산출물이다.** 멈추는 것으로 끝내지 않고 아래 넷을 남긴다.


| 남길 것      | 내용                                          |
| --------- | ------------------------------------------- |
| 막은 항목     | 어느 공고 항목이 `공백` 이라 막혔는지. 총점이 아니라 항목 이름으로 적는다 |
| 메우는 방법    | 그 공백을 메우려면 무엇을 해야 하는지와 어느 정도 걸리는지           |
| 지금 통하는 자리 | 같은 회사나 인접 직무 중 현재 근거로 자격을 채우는 공고가 있는지       |
| 다시 볼 시점   | 공고가 다시 열릴 때인지, 특정 경험이 쌓인 뒤인지                |


메우는 방법은 확인한 근거에서 나와야 한다.
「대규모 트래픽 경험을 쌓는다」처럼 실행할 수 없는 문장 대신
「인덱스와 실행 계획을 근거로 쿼리를 개선한 사례를 하나 만든다」처럼 다음 행동으로 적는다.

```bash
bun .claude/skills/application-package-writer/scripts/validate_application_package.ts <application-directory>
```

검증기는 필수 파일과 절, 준비 상태의 모순, 제출 문장의 개인 정보 유출, 계약 밖 파일만 본다.
**점수와 표의 모양은 검사하지 않는다.** 무엇을 어떻게 담을지는 위 두 문서가 정한다.

**통과 조건:** 모든 항목에 판정이 있고, `사용자 확인`이 아닌 항목에는 근거가 있다.
소계와 총점을 계산식과 함께 남겼고 지원 여부를 결론지었다.
부합하지 않는다고 결론했다면 위 표의 넷을 모두 남겼다.

### 단계 4: 후보자 인터뷰

`references/candidate-interview-questions.md`를 읽는다.
`evidence/candidate-interview.md`가 있으면 기존 답변을 확인한다.
이미 답한 내용은 다시 묻지 않고 `evidence/candidate-interview.md`에 누적한다.
제출 판단이 함께 달라지는 질문은 최대 6개까지 한 번에 묶는다.
한 가지 답이 다음 질문의 전제가 되거나 민감한 사실 하나만 확인하면 한 질문만 제시한다.
완성 문장 대신 키워드와 생각 조각을 받아도 된다.
질문할 때는 왜 후보자 확인이 필요한지, 어떤 제출 문장이나 면접 질문이 달라지는지 먼저 짧게 설명한다.

다음 네 항목이 확보되기 전에는 지원동기를 완성하지 않는다.

- 이 회사와 제품에 끌리는 구체적인 이유
- 입사 후 해결하고 싶은 사용자 문제
- 바로 기여할 수 있는 경험과 본인 역할
- 약한 영역과 보완 방법

대표 사례에는 후보자만 확정할 수 있는 다음 내용을 확인한다.

- 당시 실제로 중요했던 제약
- 후보자가 직접 내린 판단과 책임 범위
- 검토했지만 사용하지 않은 대안과 이유
- 결과를 확인한 방법과 확인하지 못한 범위
- 다시 한다면 바꿀 판단

코드와 문서가 사실을 뒷받침해도 당시 판단, 동기와 말로 설명할 수 있는지는 자동으로 확정하지 않는다.
제출에 사용할 대표 사례를 후보자가 30초로 요약하고 2분 동안 문제, 제약, 판단과 결과로 설명할 준비가 안 됐다면 포지션별 근거 방어 질문과 다음 행동에 남긴다.
완성 답변을 대신 작성하지 말고 답변 구조, 이미 확인한 근거, 예상 후속 질문과 과장하지 않을 경계를 제공한 뒤 후보자가 먼저 말하게 한다.

**통과 조건:** 제출 문구를 바꿀 미확인 항목이 없다.
남았다면 `human-confirmation`을 `needs_input`으로 두고 확인을 기다린다.

### 단계 5: 경험과 성장 판정

`references/growth-judgment.md`를 읽는다.
지원했을 때 이 자리에서 무엇을 다루게 되고 무엇을 다루지 못하는지 판정한다.
적합도 판정이 공고 요구와 후보자 근거가 맞닿은 정도를 재는 것과 달리, 이 판정은 지원 여부와 지원 순서를 가르는 근거를 만든다.

다음 두 경우에 이 절을 채운다.

- 후보자가 이 회사에서 무엇을 배울 수 있는지 물었다.
- 같은 회사에 성격이 다른 공고가 둘 이상 열려 있다.

다섯 가지를 정한다.

- 서비스가 커질 여지
- 경쟁 서비스와 이 서비스의 위치
- 경험할 수 있는 트래픽의 성격
- 여기서 얻기 쉬운 것
- 여기서 얻기 어려운 것

각 항목이 담을 것과 근거를 적는 방식은 그 reference의 「하위 절 다섯」이 소유한다.
「공개 자료로 확인한 팀과 인접 사례」와 자료 출처가 겹치므로 그 reference의 「이웃 절과의 경계」로 무엇을 어느 절에 둘지 가른다.

약한 축은 단계 4의 「약한 영역과 보완 방법」에서 가져온다.
같은 회사에 다른 공고가 열려 있으면 그 공고의 주요 업무도 읽어 같은 대조를 붙인다.
어느 쪽이 약한 축을 채우는지가 지원 순서를 정한다.

외부 검색은 지원 한 건당 다섯 건까지 쓴다.
무엇부터 찾을지는 그 reference의 「자료를 찾는 순서와 상한」이 정한다.
공개 수치로 확인하지 못한 축은 없다고 적고 면접 질문으로 넘긴다.

결과는 `evidence/strategy.md`의 「이 자리에서 얻을 경험과 성장」에 남긴다.

**통과 조건:** 다섯 하위 절이 모두 있고, 트래픽은 쓰기와 읽기를 나눠 적었다.
후보자의 약한 축마다 이 자리가 그 축을 채우는지 대조했다.
공개 수치로 확인하지 못한 축은 없다고 적고 면접 질문으로 넘겼다.

### 단계 6: 지원 전략 작성

지원 전략 단계에는 다음 핵심 파일만 만든다.

- `evidence/candidate-interview.md`: 사용자 원문 답변과 정리된 핵심
- `evidence/fit.md`, `evidence/strategy.md`, `evidence/status.md`: 판정과 전략, 준비 상태를 관심사별로 나눈 원본
- `evidence/interview-questions.json`: 공고 책임, 근거 방어와 경험 공백에서 만든 포지션별 질문

지원서 자동 입력을 준비할 때만 `evidence/application-form.json`을 만든다.
이 파일은 private brain에서 확인한 공통 프로필의 현재 값, 회사별 입력 선택, 첨부 파일, 서술형 질문과 답변을 한 번의 제출 스냅샷으로 묶는다.
서술형 문항이 없으면 `questions`를 빈 배열로 둔다.
이력서, 경력기술서, 근거 원장, 검토표와 PDF는 `resume-preparer`가 만든다.
`application-package.html`은 두 단계의 결과를 마지막에 하나로 묶는다.

**통과 조건:** 승부처, 지원동기와 기여 시나리오가 공고 요구와 확인한 근거에 연결되고, 공백 보완 계획과 면접 검증 포인트가 남아 있다.

### 단계 7: 사용자 검토

초안을 보여준 뒤 사용자가 다음 내용을 직접 확인하게 한다.

1. 지원동기가 실제 본인 생각과 같은가?
2. 본인 역할과 팀 역할이 정확히 구분됐는가?
3. 가장 강한 사례가 공고의 핵심 문제와 연결되는가?
4. 약한 영역을 숨기지 않고 전환 가능한 경험을 설명했는가?
5. 입사 후 기여 시나리오가 제품 사용자에게 닿는가?

사용자 답변을 `evidence/candidate-interview.md`에 반영한 뒤 지원 판단과 문구를 갱신한다.
공고 원문, 인터뷰 답변과 지원동기를 다시 읽어 서로 모순되는 역할·수치·동기가 없는지 확인한다.
초안을 사용자에게 보여주기 전에 `references/full-document-review.md`를 읽고 지원 전략, 이력서, 경력기술서와 지원서 답변의 외부 문장을 전수 검토한다.
사용자가 한 문장을 정정하면 같은 경험을 가리키는 모든 문서와 근거 원장을 찾아 같은 범위 오류가 반복되는지 확인한다.
문서와 코드로 바로잡을 수 있는 표현은 질문하지 않고 수정하며, 후보자만 확정할 수 있는 내용만 질문 묶음으로 돌린다.

**통과 조건:** 사용자가 위 다섯 내용을 확인했고, 공고 원문과 답변, 제출 문구 사이에 해결하지 않은 모순이 없다.

### 단계 8: 제출 문서 연결

지원 전략과 사람 확인이 준비되면 같은 사용자 요청 안에서 `resume-preparer`를 호출한다.
사용자에게 별도 스킬 실행 순서를 맡기지 않는다.

이력서와 경력기술서 작성, 근거 감사, 리뷰와 렌더 검증, 제출 묶음 생성은 `resume-preparer` 가 소유한다.

사용자만 확정할 수 있는 지원동기나 사실이 남으면 `needs_user_input`에서 멈춘다.
지원 전략만 요청한 경우에도 다음 행동에 이력서 준비 상태를 명시한다.

**통과 조건:** 전체 지원 요청이면 `resume-preparer`의 작성과 검증 결과를 준비 상태에 반영했다.
지원 전략만 요청했다면 이력서 준비 상태와 다음 행동을 남겼다.

## 산출물 계약

층별 파일 배치는 `career-os/docs/data-schema.md`의 「지원 패키지」가 소유한다.
검증기는 스키마에 없는 파일과 층이 어긋난 파일을 거부해 임시 검토 문서가 계속 늘어나지 않게 한다.

세 파일이 아래 절을 나눠 담는다. 어느 파일에 어느 절이 가는지가 계약이다.


| 파일                     | 절                                                                                    | 채우는 단계  |
| ---------------------- | ------------------------------------------------------------------------------------ | ------- |
| `evidence/fit.md`      | 결론, 공고 항목별 적합도, 소계와 총점, 공개 자료로 확인한 팀과 인접 사례                                        | 1, 2, 3 |
| `evidence/strategy.md` | 이 포지션에서의 승부처, 지원동기, 입사 후 기여 시나리오, 이 자리에서 얻을 경험과 성장, 보완할 공백, 회사 문화와의 연결, 면접에서 검증받을 내용 | 5, 6    |
| `evidence/status.md`   | 준비 상태 세 줄, 제출 준비 상태, 사용자 확인 필요, 다음 행동                                                | 6, 8    |


「이 자리에서 얻을 경험과 성장」만 선택 절이다. 나머지는 모두 있어야 한다.

절 순서도 계약이다.
「이 자리에서 얻을 경험과 성장」은 「입사 후 기여 시나리오」 뒤, 「보완할 공백」 앞에 둔다.
얻기 어려운 것이 곧 보완할 공백이므로 두 절을 이어 읽게 한다.

#### 공고 항목별 적합도

공고 항목 하나에 한 행을 준다.
머리행은 `공고 항목`, `공고 구분`, `근거`, `판정` 넷이며 순서까지 계약이다.

- `evidence/posting.md`의 주요 업무, 기대 경험과 우대 경험을 항목 단위로 모두 담는다. 요약해 합치지 않는다.
- 각 행은 공고 항목 원문의 요지, 그 항목이 어느 구분에서 왔는지, 연결할 근거와 판정을 담는다.
- 판정 값과 점수는 [`data-schema.md`의 「적합도 판정과 점수」](../../../docs/data-schema.md#적합도-판정과-점수), 판단 기준은 [적합도 판정](references/fit-judgment.md)을 따른다.
- 판정이 `공백`인 항목은 「보완할 공백」 절과 같은 내용을 가리켜야 한다.

#### 공개 자료로 확인한 팀과 인접 사례

- 같은 팀의 공식 정보와 인접 조직의 사례를 행에서 구분한다.
- 각 행은 자료 링크, 확인한 범위, 지원 준비에 쓰는 관점을 담는다.
- 공고 페이지에 외부 링크가 없으면 직접 찾은 자료임을 밝힌다.

#### 이 자리에서 얻을 경험과 성장

판단 기준은 [경험과 성장 판정](references/growth-judgment.md)을 따른다.
이 절은 선택 절이다.
후보자가 이 회사에서 무엇을 배울 수 있는지 물었거나 같은 회사에 성격이 다른 공고가 둘 이상 열려 있으면 채운다.

검증기는 이 절의 존재를 요구하지 않는다.
이 절이 생기기 전에 만든 지원 건을 소급해 고치지 않기 때문이다.
절이 있으면 아래 하위 절 다섯이 이 순서로 있는지 검사한다.

```markdown
### 서비스가 커질 여지
### 경쟁 서비스와 이 서비스의 위치
### 경험할 수 있는 트래픽의 성격
### 여기서 얻기 쉬운 것
### 여기서 얻기 어려운 것
```

각 하위 절이 담을 것은 위 reference가 소유한다.

`면접에서 검증받을 내용`을 작성한 뒤 다음 세 출처로 질문을 구조화한다.

- `posting_requirement`: 공고가 직접 요구하는 책임과 설계 판단
- `evidence_defense`: 이력서와 경력기술서의 핵심 경험을 방어하는 질문
- `experience_gap`: 직접 해보지 않은 영역과 모호한 근거를 확인하는 질문

질문은 `evidence/interview-questions.json` 하나에 저장하고 다음 명령으로 검증한다.

```bash
bun scripts/interview-drill/application_question_schema.ts <application-directory>
```

각 질문에는 답변에서 확인할 신호와 `evidenceBoundary`를 함께 기록한다.
공백 질문의 답변 신호는 경험을 꾸미는 모범 답안이 아니라 설계 원칙, 인접 근거와 학습 경계를 확인해야 한다.

첫 10줄 안에 아래 상태를 기록한다.

```markdown
- readiness: ready|needs_user_input|revise|do_not_apply
- evidence: safe|revise|blocked
- human-confirmation: complete|needs_input
```

`human-confirmation`은 지원동기, 본인 역할, 실제 제약, 대안, 결과의 확인 범위처럼 후보자만 확정할 수 있는 항목의 상태다.
하나라도 제출 문구를 바꿀 미확인 항목이 있으면 `needs_input`으로 두며, `readiness: ready`와 함께 사용할 수 없다.

## 사용자에게 주는 결과

사용자가 가장 먼저 볼 파일은 `application-package.html`이다.
이 화면은 `evidence/` 의 `status.md`, `fit.md`, `strategy.md` 를 이어 붙여 만들며 다음 질문에 한 화면 안에서 답해야 한다.

- 이 공고에 지원할 가치가 있는가?
- 회사와 팀은 어떤 사람을 찾고 있는가?
- 내 경험 중 무엇으로 승부할 수 있는가?
- 어떤 공백을 정직하게 설명해야 하는가?
- 여기서 무엇을 경험하고 무엇을 얻지 못하는가?
- 이력서와 면접에서 무엇을 검증받아야 하는가?
- 다음 행동은 무엇인가?

`application-package.html`은 지원 판단, 근거, 제출 문서와 남은 질문을 묶어 보여주는 유일한 로컬 검토 화면이다.
실제 제출 파일은 현재 지원 화면의 첨부 조건에 맞는 PDF 하나를 우선한다. 이력서만 받으면 `resume.pdf`, 경력기술서를 별도로 받으면 `career-description.pdf`, 한 파일만 받으면 두 문서를 합친 `submission.pdf`를 사용한다.
브라우저 자동 입력을 준비할 때는 공통 프로필, 회사별 선택값과 서술형 답변을 `evidence/application-form.json` 하나에 구조화한다.
공통 개인정보의 기준은 private brain의 `career-application-profile`이며, 후보자 인터뷰에 복제하지 않는다.

화면은 준비 상태, 적합도 총점, 결론, 제출 후보 PDF와 조건부 지원서 입력값을 탭 밖 상단에 고정하고 본문을 네 탭으로 나눈다.
적합도 총점의 계산식과 색 구간, 탭 목록과 각 탭이 담는 것은 `career-os/docs/data-schema.md`의 「검토 화면」과 「적합도 판정과 점수」가 소유한다.

근거 장부, 점수표, manifest와 HTML 중간 파일은 검증에 사용하되 사용자용 링크로 나열하지 않는다.

## 안전 경계

- private brain과 `sources/fos-study/`는 읽기 전용이다.
- 내부 파일 경로와 검토 상태를 제출 문장에 넣지 않는다.
- 로컬 프로젝트에서 찾은 사내 식별자, 호스트, 자격증명과 비공개 수치는 제출 문장에 옮기지 않는다.
