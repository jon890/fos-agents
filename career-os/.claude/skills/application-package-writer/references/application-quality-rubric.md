# 지원 준비 품질 기준

지원 패키지는 문서 수가 아니라 채용 담당자가 다음 단계에서 검증할 이유를 만드는지로 평가한다.

## 평가 축

### 포지션 적합성

- 공고의 핵심 문제와 후보자의 가장 강한 경험이 직접 연결된다.
- 필수 경험과 우대 경험을 구분한다.
- 공고에 없는 기술을 중요 요구사항으로 만들지 않는다.

### 사용자와 제품 영향

- 기술 구현이 어떤 사용자 문제를 줄이는지 설명한다.
- 입사 후 기여가 기능 목록이 아니라 사용자 변화로 이어진다.
- 플랫폼 역할이면 내부 사용자의 실험 속도와 운영 안정성도 제품 가치로 다룬다.

### 문제 해결과 판단

- 문제, 중요성과 제약, 본인 역할, 판단, 결과가 이어진다.
- 기술 이름보다 대안과 절충안, 실패 처리와 검증 방법이 드러난다.
- 구조화되지 않은 문제를 어떻게 작게 나누고 반복 개선했는지 보여준다.

### 근거와 소유권

- 구현, 소유권과 결과를 각각 근거에 대조한다.
- `brain`이나 경력기술서만 반복하지 않고 중요한 주장을 로컬 프로젝트 원본에서 다시 확인한다.
- 팀 성과와 개인 기여를 구분한다.
- 수치가 없으면 검증 방법이나 운영 변화를 구체적으로 설명한다.

### 사람 확인과 설명 가능성

- 동기, 당시 제약, 본인 판단, 기각한 대안과 배운 점은 후보자가 직접 확인한다.
- 대표 사례를 30초로 요약하고 2분 동안 문제, 제약, 판단과 결과로 설명할 수 있다.
- 설명하지 못하는 문장은 더 그럴듯하게 다듬지 않고 근거를 찾거나 표현을 낮춘다.
- 사용자가 해야 할 일은 사실 확인, 경험 설명, 선택, 연습과 승인 중 무엇인지 구분해 최대 세 개를 우선순위로 보여준다.

### 지원동기와 경력 방향

- 회사 이름만 바꿔도 성립하는 동기를 쓰지 않는다.
- 현재 경험에서 다음 역할로 확장되는 이유가 자연스럽다.
- 해보지 않은 영역은 숨기지 않고 인접 경험과 학습 행동으로 설명한다.

### 회사 문화 적합성

- 회사 공식 자료에서 포지션과 직접 관련된 기준 3개에서 5개만 고른다.
- 가치에 공감한다는 선언보다 실제 행동 사례를 연결한다.
- 후보자에게 맞지 않는 기준과 우려도 내부 판단에 남긴다.

### 제출 품질

- 첫 화면에서 목표 역할과 차별점이 보인다.
- 같은 내용을 여러 산출물에 반복하지 않는다.
- 내부 경로, 검토 상태와 비공개 정보가 제출 문장에 없다.
- 읽는 사람이 면접에서 확인하고 싶은 질문이 선명하게 남는다.

## 판정

- `ready`: 핵심 주장에 근거가 있고 사용자 확인이 끝났다.
- `needs_user_input`: 지원동기, 소유권 또는 결과를 후보자가 확인해야 한다.
- `revise`: 에이전트가 구조, 표현 또는 공고 연결을 고칠 수 있다.
- `do_not_apply`: 핵심 필수 조건이 맞지 않거나 지원 이유가 성립하지 않는다.

점수 하나로 약한 필수 조건을 가리지 않는다.
`ready`는 합격 보장이 아니라 제출 문서와 면접 서사가 현재 근거 범위에서 준비됐다는 뜻이다.
