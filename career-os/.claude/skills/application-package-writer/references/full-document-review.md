# 지원 문서 전수 검토

초안을 사용자에게 보여주기 전에 지원 전략, 이력서, 경력기술서와 지원서 답변을 한 묶음으로 검토한다.
문법 오류만 찾지 않고, 읽는 사람이 각 문장을 어디까지의 경험으로 받아들일지 확인한다.

## 검토 대상

- `application-package.md`에서 사용자가 먼저 읽는 결론, 승부처, 지원동기, 공백과 다음 행동
- `resume-draft.md`의 프로필, 프로젝트, 경력과 기술 목록
- 경력기술서가 있으면 `career-description-draft.md` 전체
- `application-form.json`의 서술형 답변
- 위 원본에서 생성한 HTML과 PDF의 실제 표시 문구

내부 근거 경로와 검토 상태는 제출 문장이 아니므로 표현 검토에서 제외하되, 외부 문장과 근거가 같은 범위를 가리키는지는 확인한다.

## 문장별 검토

외부에 보이는 각 문장에 다음 질문을 적용한다.

1. 문장이 가리키는 대상이 제품 전체, 기능, 변환 경로, 표본 또는 한 사례 중 무엇인지 드러나는가?
2. 전체 성과와 그 성과를 보여주는 한 사례를 섞지 않았는가?
3. 팀이 한 일과 후보자가 직접 판단하고 구현한 일을 구분했는가?
4. 품질이나 성능을 말했다면 무엇을 어떤 기준으로 측정했는지 알 수 있는가?
5. 확인한 결과와 그 결과에서 추론한 포지션 연결을 사실처럼 합치지 않았는가?
6. 앞뒤 문장을 함께 읽을 때 실제 담당 범위보다 넓거나 좁게 받아들일 여지가 없는가?
7. 지표, 내부 구조와 추상어를 몰라도 수행한 작업과 의미를 이해할 수 있는가?
8. 후속 질문을 받았을 때 문제, 제약, 판단, 조치, 결과와 남은 한계를 설명할 수 있는가?

전체 범위와 구체적인 개선 사례는 문장을 나눠 쓴다.
예를 들어 Document Parser의 품질 평가는 본문과 표를 모두 다루지만 실제 변환 경로 변경은 표에서만 했다면, 전체 품질 평가와 표 변환 개선을 한 성과처럼 압축하지 않는다.

## 문서 전체 검토

- 프로필의 대표 강점이 첫 프로젝트와 경력 내용으로 실제 증명되는지 확인한다.
- 같은 경험의 대상, 역할, 수치와 기간이 지원 전략, 이력서와 경력기술서에서 일치하는지 확인한다.
- 구체적인 한 사례가 제품 전체 성과로 확대되거나, 제품 전체에 만든 체계가 한 기능의 경험으로 축소되지 않았는지 확인한다.
- 공고와 연결한 문장은 확인된 경험과 지원 전략상의 해석을 구분한다.
- 비슷한 문장이 반복되면 가장 구체적인 문장만 남기고 나머지는 다른 판단 근거를 보여준다.
- 기술 이름을 뺐을 때도 문제 해결 방식과 결과가 남는지 확인한다.
- 채용 담당자가 10초 동안 읽었을 때 만들 가능성이 큰 인상을 한 문장으로 적어 보고, 의도와 다르면 문장을 고친다.

## 수정과 사용자 확인

문서나 코드로 범위를 확인할 수 있으면 별도 질문 없이 문장을 고친다.
후보자만 확정할 수 있는 소유권, 동기, 당시 제약, 기각한 대안과 실제 사용 결과는 질문으로 돌린다.
서로 독립적인 질문은 최대 6개까지 한 번에 묶고, 이미 확보한 답변은 다시 묻지 않는다.

사용자가 한 문장을 바로잡으면 그 문장만 고치지 않는다.
같은 경험을 가리키는 표현을 지원 전략, 이력서, 경력기술서, 지원서 답변과 근거 원장에서 찾아 같은 오류가 반복되는지 확인한다.
수정된 문구는 주장 근거 감사와 하드 리뷰를 다시 받아야 한다.

전수 검토 결과를 별도 Markdown 파일로 만들지 않는다.
고칠 수 있는 내용은 원본에 반영하고, 남은 사실 질문은 `candidate-interview.md`, 근거 판정은 claim ledger, 설득력 판정은 scorecard에 기록한다.
