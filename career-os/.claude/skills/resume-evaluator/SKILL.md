# Resume Evaluator

공고 맞춤 HTML 이력서를 냉정하게 채점하고, 근거가 있는 범위에서 직접 개선한다.
점수 자체보다 탈락 가능성을 키우는 약점을 먼저 제거한다.

## 실행 원칙

- `references/scoring-rubric.md`를 먼저 읽고 같은 기준을 모든 반복에 적용한다.
- 작성자와 평가자를 분리할 수 있으면 새로운 검토 문맥에서 실행한다.
- 분리가 불가능하면 정적 검사, 공고 대조, 근거 대조, 실제 렌더 검사를 모두 수행해 자기평가 편향을 줄인다.
- 문체·순서·시각 계층은 사용자에게 재확인하지 않고 적극적으로 고친다.
- 사실, 수치, 역할 범위가 불명확하고 결과를 바꿀 때만 사용자에게 묻는다.
- `fos-study`와 후보자 프로필은 읽기 전용 근거다. 원본을 수정하지 않는다.
- 실제 지원, 로그인, 업로드, 외부 전송은 하지 않는다.

## 입력

최소 입력은 HTML 이력서 경로다.
공고와 근거가 같은 지원 디렉터리에 있으면 자동으로 함께 읽는다.

권장 입력:

1. `career-os/applications/<company>/<role>/resume.html`
2. 같은 디렉터리의 `posting.md` 또는 공고 URL
3. `career-os/config/candidate-profile.md`
4. `career-os/config/candidate-profile-detail.md`
5. 관련 `fos-study/resume/**`, `fos-study/task/**` 근거

경로가 생략되면 `career-os/applications/**/resume.html`에서 가장 최근 파일을 찾는다.
후보가 둘 이상이면 임의 선택하지 말고 경로를 한 번만 묻는다.

## 산출물

- 개선된 `resume.html`
- 같은 디렉터리의 `resume-scorecard.md`

점수표에는 각 반복의 점수, 감점 근거, 실제 수정 사항, 남은 위험을 남긴다.
최종 HTML만 제출 후보이며 점수표는 내부 검토 자료다.

## 두 평가자 관점

같은 이력서를 다음 두 사람이 독립적으로 검토한다고 가정한다.

### 빅테크 인사 담당자

- 10초 안에 역할과 차별점을 이해할 수 있는가
- 다음 검토 단계로 넘길 명확한 이유가 있는가
- 경력 이동과 지원 동기가 방어적이지 않고 일관되는가
- 특정 공고가 아니어도 적합한 팀을 매칭할 수 있는가
- 정보가 많아도 핵심을 빠르게 훑을 수 있는가

### 빅테크 기술 리더

- 어려운 문제에서 본인이 소유한 범위가 어디까지인가
- 기술을 나열하지 않고 선택 이유와 제약을 설명하는가
- 성능·품질·안정성을 어떤 측정과 검증으로 판단했는가
- 팀 성과와 개인 기여가 구분되는가
- 면접에서 한 단계 깊게 질문해도 방어 가능한 주장인가

두 관점 중 하나라도 기준에 미달하면 총점만으로 통과시키지 않는다.

## 평가·개선 루프

최대 3회 반복한다.

### 0. 증거 감사를 통과한다

`resume-evidence-auditor`를 먼저 실행해 제출 문구를 코드·테스트·Git 이력·업무 문서와 대조한다.

- `unsupported`, `contradicted`, 미해결 `ask_user`가 있으면 채점을 시작하지 않는다.
- `soften` 항목을 검증된 강도로 수정한 뒤 다시 감사한다.
- 코드에 접근할 수 없는 사내 경력은 `document_only` 또는 `user_attested` 범위를 넘겨 표현하지 않는다.

### 1. 근거와 목표를 고정한다

1. 공고에서 역할, 문제 영역, 기대 행동, 우대 경험을 추출한다.
2. 후보자 프로필과 업무 문서에서 사용할 수 있는 주장과 수치를 찾는다.
3. 모든 주요 문장을 `직접 근거`, `사용자 진술`, `추론`, `근거 없음` 중 하나로 분류한다.
4. `근거 없음`인 성과·수치·역할 주장은 삭제하거나 사용자 질문으로 돌린다.

공고가 인재풀처럼 넓다면 직무 키워드 나열보다 다음을 우선한다.

- 첫 화면에서 한 문장으로 설명되는 직업 정체성
- 여러 포지션에 매칭할 수 있는 핵심 역량
- 제품과 사업 문제로 확장되는 경력 방향

### 2. 정적 검사를 실행한다

```bash
bun career-os/.claude/skills/resume-evaluator/scripts/check_resume_html.ts <resume.html>
```

정적 검사 실패는 해당 항목을 고친 뒤 채점을 시작한다.

### 3. 실제 렌더를 검사한다

Orca 브라우저가 있으면 Orca를 우선 사용한다.

1. `file://` URL로 HTML을 연다.
2. 접근성 스냅샷에서 제목, 섹션 순서, 링크 텍스트를 확인한다.
3. 스크린샷으로 글자 겹침, 잘림, 과도한 여백, 대비를 확인한다.
4. 브라우저 평가식으로 `.resume-page` 개수와 각 페이지의 `scrollHeight <= clientHeight + 2` 여부를 확인한다.

PDF 출력 호환성은 임시 PDF로만 검증할 수 있다.
최종 산출물이 HTML이면 임시 PDF와 렌더 이미지는 검증 후 삭제한다.

### 4. 100점으로 채점한다

`references/scoring-rubric.md`의 인사 40점, 기술 45점, 제출 품질 15점을 모두 점수화한다.
점수 전에 다음 두 판정을 한 문장씩 먼저 쓴다.

- 인사 담당자 판정: 다음 검토 단계로 넘길지 여부와 이유
- 기술 리더 판정: 기술 면접을 제안할지 여부와 가장 큰 검증 질문

주요 성과마다 면접에서 나올 후속 질문을 하나씩 만들어 문장이 방어 가능한지 확인한다.
각 감점은 다음 형식으로 남긴다.

```text
- 감점: -4
  위치: 첫 페이지 요약
  근거: 지원 방향은 보이지만 사용자가 해결한 문제의 규모가 드러나지 않는다.
  수정: 검증된 수치 1개와 본인 역할을 첫 화면으로 이동한다.
```

근거 없이 점수를 올려주지 않는다.
한 축에서 같은 원인의 감점을 여러 번 중복 계산하지 않는다.

채점 전에 대표 프로젝트의 순위를 별도로 검증한다.

1. 목표 역할을 가장 잘 대표하는가
2. 사용자·제품·사업 문제와 연결되는가
3. 본인 소유 범위와 검증된 결과가 분명한가
4. 다른 후보자와 구분되는가

구현 단계 수, 사용 기술 개수, 문서가 잘 정리됐다는 이유만으로 첫 사례에 올리지 않는다.
첫 사례는 가장 복잡한 프로젝트가 아니라 채용자가 이 후보자를 다음 단계로 넘길 이유를 가장 빨리 설명하는 프로젝트여야 한다.

### 5. 치명적 약점부터 직접 수정한다

수정 우선순위:

1. 과장, 근거 없음, 공개하면 안 되는 내용
2. 목표 역할 불명확, 핵심 강점 분산
3. 문제·행동·결과가 연결되지 않는 경력 문장
4. 공고·제품과 연결되지 않는 기술 나열
5. 첫 페이지 정보 과밀, 글자 잘림, 약한 시각 계층
6. 어색한 문장과 장식적 요소

단순히 문장을 줄이는 데 그치지 않는다.
섹션 순서, 제목, 정보 묶음, 여백과 강조 계층도 함께 고친다.
인쇄 이력서에서는 카드형 UI를 기본값으로 사용하지 않는다.
비교 관계가 없는 설명을 여러 카드에 나누면 문서 흐름으로 되돌린다.

### 6. 재검증하고 멈춘다

다음 조건을 모두 만족하면 `pass`로 종료한다.

- `resume-evidence-auditor` 판정 `safe`
- 총점 90점 이상
- 인사 담당자 점수 32/40 이상
- 기술 리더 점수 36/45 이상
- 제출 품질 점수 12/15 이상
- 치명적 결함 0개
- 각 축이 배점의 60% 이상
- 정적 검사 통과
- 실제 렌더에서 페이지 넘침과 겹침 0개
- 근거 없는 수치·역할 주장 0개

3회째에도 통과하지 못하면 점수를 억지로 올리지 않는다.
`revise` 또는 `blocked`로 끝내고 사용자에게 필요한 사실이나 구조적 한계를 정확히 적는다.

## 점수표 형식

`resume-scorecard.md`는 다음 구조를 따른다.

```markdown
# 이력서 평가표

## 최종 판정

- 결과: pass|revise|blocked
- 최종 점수: 0/100
- 인사 담당자: 0/40
- 기술 리더: 0/45
- 제출 품질: 0/15
- 반복 횟수: 1~3
- 치명적 결함: 0개 이상

## 평가자 판정

### 인사 담당자

### 기술 리더

## 반복 기록

### 반복 1

| 평가 축 | 점수 | 배점 | 핵심 근거 |
| --- | ---: | ---: | --- |

#### 우선 수정 항목

#### 실제 수정 사항

## 자동 검사

## 남은 위험

## 예상 심층 질문

## 근거 파일
```

내부 경로는 점수표에만 남긴다.
제출용 HTML에는 `task/`, `fos-study`, 로컬 절대 경로, 검토 상태를 노출하지 않는다.

## 금지 사항

- 없는 매출, 전환율, 트래픽, 팀 규모, 성과율을 만들어내지 않는다.
- 팀 결과를 개인 단독 성과로 바꾸지 않는다.
- 기술 키워드를 공고에 있다는 이유만으로 추가하지 않는다.
- 디자인 점수를 높이기 위해 본문 크기를 9pt 미만으로 줄이지 않는다.
- 페이지 수를 맞추려고 핵심 근거를 숨김 처리하거나 화면 밖으로 자르지 않는다.
- 점수표를 이력서 안에 포함하지 않는다.
- 외부 제출을 완료했다고 표현하지 않는다.
