# 이력서 작성 취향

이 파일은 회사에 관계없이 재사용하는 개인 이력서 취향을 관리한다.
공고의 공식 작성 안내와 회사별 기준이 있으면 먼저 따르고, 이 파일은 그 범위 안에서 경력과 일하는 방식을 어떻게 보여줄지 정한다.
일반 표현 검증은 [resume-writing-style.md](resume-writing-style.md)를, HTML과 PDF 배치 검증은 [resume-design.md](resume-design.md)를 함께 적용한다.

## 목표

이력서는 경력과 일하는 방식을 지원 직무에서 만들 수 있는 기여로 연결한다.
목표는 제출 문서가 다음 전형으로 넘어갈 이유를 빠르게 보여 주어 서류 합격 가능성을 최대한 높이는 것이다.

첫 화면에서는 현재 역할, 다루는 문제와 지원 직무에 연결되는 대표 근거가 보여야 한다.
뒤쪽에서는 경력 흐름, 프로젝트, 기술 범위와 검증 가능한 결과를 확인할 수 있어야 한다.

## 프로젝트 한 절을 쓰는 방식

**네 축을 모두 채운다.** 하나라도 비면 읽는 사람이 그 부분을 스스로 채워야 한다.

| 축 | 확인할 것 |
| --- | --- |
| 어떤 문제를 해결했는지 | 증상이 아니라 무엇이 막혀 있었는지 |
| 그 문제가 왜 중요했고 어떤 제약이 있었는지 | 목표가 어떻게 막혔는지, 쉽게 고치지 못한 이유 |
| 어떤 역할을 맡았고 어떤 판단을 했는지 | 감수한 위험과 고르지 않은 선택지 포함 |
| 결과적으로 어떤 변화가 있었는지 | 문제로 건 것이 닫혔는지 |

**시간 순으로 쓴다.** 문제를 만난 시점부터 해결과 공유까지 순서대로 두면, 고치기 전에 관측부터 한 것 같은 판단이 저절로 드러난다.

**상위 불릿과 하위 불릿을 나눈다.** 상위만 훑어도 흐름이 읽히게 하고, 제약과 상세는 하위에 둔다.

- 한 마디에 여러 일이 들어 있으면 나눈다. 「검증 환경을 만들었다」는 표본 확보, 자원 발급, 자동화 세 가지일 수 있다
- 압축해서 뜻을 잃는 곳은 풀어 쓴다. 「나눠 처리」보다 「페이지 단위로 나눠 처리」가 맞다
- 문제와 결과가 서로를 가리키는지 본다. 메모리를 문제로 걸었으면 결과도 메모리여야 한다

**원인을 찾은 내용을 적는다.** 「원인을 찾아 고쳤다」는 면접 첫 질문이 된다. 무엇을 발견했는지 한 구절이 있으면 관측을 먼저 한 이야기와 이어진다.

**스스로 정한 값과 시스템이 보여준 값을 함께 둔다.** 설정을 올린 것은 사람의 선택이고, 보호 장치가 동작하지 않는 것은 관측이다. 둘이 나란히 있어야 앞의 수치를 믿을 근거가 된다.

**같은 일을 두 번 말하지 않는다.** 원인을 세 갈래로 나눴다고 쓰고 그 세 갈래를 고쳤다고 다시 쓰면 중복이다. 원인과 조치를 한 줄씩 짝지어 묶는다.

## 읽는 사람과 문체

**이력서는 인사담당자도 읽는다.** 기술을 정확히 몰라도 맥락을 따라갈 수 있게 쓰고, 도구 이름은 「기술」 줄로 내린다.

- 자원 조건 수치를 나열하지 않고 상황으로 요약한다. 「프로세스 풀 4개, 메모리 8GB, 한도 32GB」보다 「메모리를 과도하게 사용해 인스턴스가 응답하지 못했음」이 읽힌다
- 내부 단계 이름을 그대로 쓰지 않는다. 「페이지 전처리」는 「문서 준비 단계」다
- 기술 이름이 한 문장에 셋 이상 몰리면 무엇을 왜 고쳤는지로 풀어 쓴다

**프로젝트 불릿은 개조식으로 끝낸다.** 명사와 「음」으로 맺어 읽는 피로를 줄인다. 프로필과 소개는 존댓말 문장으로 둔다.

**AI가 즐겨 쓰는 표현을 쓰지 않는다.** 「재는 수단」, 「~하는 자리」, 「축이 된다」처럼 비유로 일반 명사와 동사를 대체한 말은 평소 쓰는 낱말로 바꾼다. 「재는 수단」은 「관측 방안」이다.

## 쓰지 않는 것

**당연한 것을 성과로 쓰지 않는다.** 그 기술을 쓰면 따라오는 구성은 강조점이 되지 않는다. 원래 없었던 것이 문제였지 넣은 것이 성과는 아니다.

**만든 것의 종류를 바꾸지 않는다.** API 서버와 도구를 감싼 Skill 은 다르다. 면접에서 구현을 물었을 때 어긋나는 표현을 쓰지 않는다.

**결과를 실제 상태보다 크게 쓰지 않는다.** 내부 도구를 정식 서비스로, 외부 API 호출을 라우팅 설계로 쓰지 않는다.

**확인할 수 없는 도입 범위를 쓰지 않는다.** 「전사적으로 사용 중」 대신 「사내 게시판에 공유해 사용」처럼 확인 가능한 사실로 낮춘다.

**하지 않은 것에 대한 설명은 면접으로 넘긴다.** 확정하지 않은 값, 걸러내지 못한 이유, 채택하지 않은 후보의 상세가 여기 해당한다.

**사내 식별자와 도구 고유 이름을 넣지 않는다.** 조직 밖에서 뜻이 통하지 않는 번호는 종류와 규모로 바꾸고, 사내 도구는 하는 일로 부른다. 내부 호스트, 계정, 경로와 비공개 수치도 넣지 않는다.

**분량이나 개수 같은 값은 정보가 아니다.** 「17쪽 세미나」는 무엇을 공유했는지 말하지 않는다. 공유는 청중 범위로 쓴다.

## 이력서에서 뺀 것은 면접 자료로 옮긴다

분량을 줄이려고 뺀 문장은 지우지 말고 그 지원의 후보자 확인 기록으로 옮긴다.
사실이 아니어서 뺀 것이 아니라는 것을 함께 적어, 면접에서 물으면 답할 수 있게 남긴다.

| 구분 | 대상 |
| --- | --- |
| 이력서에 남긴다 | 문제, 판단, 결과, 검증 조건 |
| 면접 자료로 옮긴다 | 자원 조건 수치, 걸러내지 못한 이유, 재지 않은 값, 기각한 후보의 상세, 아쉬웠던 점 |

## 표현

프로필은 현재 소속과 역할, 업무의 대상과 목적, 관심을 보여주는 실제 행동을 짧게 연결해 쓴다.
소개에서 연차를 말할 때는 실제 재직 기간으로 계산하고 `N년 차`로 표현한다.
회사명, 기간과 기술 목록은 이 파일에 예시 값으로 고정하지 않는다.

개발과 유지보수는 실제 역할에 맞춰 쓴다.
수식어는 실제 동작의 주체를 가리켜야 하며, 팀이 만든 결과와 본인이 맡은 작업을 구분한다.
같은 내용은 가장 적절한 위치에서 한 번 설명하고 다른 섹션에서는 반복하지 않는다.

도구와 프로젝트는 목적을 담은 제목으로 시작한다.
프로젝트 제목은 전체 담당 범위를 간결하게 보여주고, 개별 개선 사례는 본문에 둔다.
그 아래에는 소속 팀, 실제 참여 기간, 핵심 행동과 결과를 짧은 항목으로 둔다.
수치를 쓰면 집계 기간과 확인 시점을 함께 표시한다.
전후 비교는 [resume-writing-style.md](resume-writing-style.md)의 측정 대상과 조건 기준을 따른다.

기술 목록은 사용 범위와 판단을 설명할 수 있는 항목으로 선별한다.
테스트 경험은 독립된 기술 나열보다 관련 프로젝트에서 어떤 검증을 했는지로 설명한다.

## 정보 구조

연락처는 이름과 값을 함께 표시한다.
회사명과 팀 재직 기간 아래에는 해당 회사에서 수행한 프로젝트를 제목 계층으로 묶는다.
각 프로젝트에는 소속 팀과 실제 참여 기간을 연결하고, 팀 재직 기간과 프로젝트 참여 기간은 구분한다.
학력과 자격증은 독립 섹션으로 둔다.

학력은 재학 기간과 평점을 한 줄로 묶고, 전공과 부전공을 별도 한 줄로 묶는다.
회사와 학교는 실제 로고를 사용한다.
로고를 사용할 근거가 불명확하면 텍스트 표기로 대체하고 확인 대상으로 남긴다.

공식 브랜드 강조색은 지원별로 선택한다.
색상값은 이 파일에 고정하지 않고, 제목, 아이콘과 구분선에 제한해 적용한다.
분량과 페이지 수는 제출처 제한, 근거의 양, 중복과 읽기 편의성으로 정한다.

## 함께 수정하는 방식

사용자와 합의한 문구는 Markdown 원고에 먼저 반영한다.
사용자가 PDF 갱신을 요청하면 렌더링을 다시 실행하고 실제 배치를 확인한다.
글자 겹침, 잘림, 링크, 대비와 페이지 넘침은 [resume-design.md](resume-design.md)의 검증 기준으로 확인한다.

작성 취향 합의와 개인 사실 정정의 분리는 [brain-context.md](brain-context.md)의 「환원 분기」를 따른다.
