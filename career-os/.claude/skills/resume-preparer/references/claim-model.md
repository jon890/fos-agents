# 이력서 주장 검증 모델

## 왜 세 축으로 나누는가

같은 문장 안에서도 구현, 소유권과 결과의 근거 수준은 다를 수 있다.

예를 들어 기능 코드와 테스트가 있어도 후보자가 설계했는지는 알 수 없다.
후보자의 커밋이 있어도 그 변경이 운영 비용을 줄였는지는 별도 측정이 필요하다.

## 구현 상태


| 상태                  | 의미                                  |
| ------------------- | ----------------------------------- |
| `code_verified`     | 실제 코드와 관련 동작을 직접 확인했다.              |
| `test_verified`     | 코드와 해당 동작을 검증하는 테스트를 확인했다.          |
| `artifact_verified` | 공개 패키지, 배포 결과물 또는 실행 가능한 산출물을 확인했다. |
| `document_only`     | 업무 문서나 기존 이력서에서만 확인했다.              |
| `user_attested`     | 사용자가 직접 사실이라고 확인했다.                 |
| `not_applicable`    | 구현 검증 대상이 아닌 기간·동기 등의 주장이다.         |
| `unsupported`       | 근거를 찾지 못했다.                         |
| `contradicted`      | 근거가 주장을 반박한다.                       |


## 소유권 상태


| 상태              | 의미                                    |
| --------------- | ------------------------------------- |
| `git_verified`  | 후보자 식별 정보와 일치하는 Git 작성 이력을 확인했다.      |
| `document_only` | 업무 문서에 후보자 역할이 적혀 있지만 Git으로 확인하지 못했다. |
| `user_attested` | 사용자가 직접 기여 범위를 확인했다.                  |
| `team_result`   | 구현은 확인되지만 개인 소유 범위는 분리되지 않는다.         |
| `not_claimed`   | 개인 소유권을 주장하지 않는다.                     |
| `unsupported`   | 소유권 근거가 없다.                           |
| `contradicted`  | 다른 작성자 또는 문서가 소유권 주장을 반박한다.           |


## 결과 상태


| 상태              | 의미                            |
| --------------- | ----------------------------- |
| `measured`      | 벤치마크, 로그, 품질 평가 또는 전후 수치가 있다. |
| `test_verified` | 결과를 직접 검증하는 테스트가 있다.          |
| `documented`    | 업무 문서에 결과가 기록돼 있다.            |
| `user_attested` | 사용자가 직접 운영 결과를 확인했다.          |
| `not_claimed`   | 결과나 성과를 주장하지 않는다.             |
| `unsupported`   | 결과 근거가 없다.                    |
| `contradicted`  | 측정 결과가 주장을 반박한다.              |


## 경험 깊이 상태

기술을 사용한 사실과 그 기술을 주력으로 다룬 경험을 구분한다.
`experienceDepth`는 기술 범위, 경력 기간, 운영과 숙련도를 말하는 주장에 기록한다.


| 상태                    | 의미                                    |
| --------------------- | ------------------------------------- |
| `usage_verified`      | 빌드 설정과 코드에서 해당 기술을 사용한 사실을 확인했다.      |
| `delivery_verified`   | 후보자의 Git 이력과 코드·테스트에서 기능 변경 범위를 확인했다. |
| `operations_verified` | 장애, 배포, 성능, 관측 또는 운영 판단의 근거를 확인했다.    |
| `user_attested`       | 후보자가 경험 수준과 범위를 직접 확인했다.              |
| `not_claimed`         | 기술 숙련도나 운영 깊이를 주장하지 않는다.              |
| `unsupported`         | 주장한 경험 깊이를 뒷받침할 근거가 없다.               |
| `contradicted`        | 사용자 확인이나 다른 근거가 경험 깊이 주장을 반박한다.       |


코드 파일과 커밋 수는 `usage_verified` 또는 `delivery_verified` 근거다.
`operations_verified`에는 별도 운영 근거가 필요하다.

## 최종 문구 판정


| 판정         | 조건                                |
| ---------- | --------------------------------- |
| `safe`     | 제출 문구의 강도가 세 축의 근거 수준을 넘지 않는다.    |
| `soften`   | 사실의 일부는 확인되지만 동사·수치·인과가 근거보다 강하다. |
| `ask_user` | 후보자만 확인 가능한 핵심 사실이 결과를 바꾼다.       |
| `remove`   | 근거가 없거나 모순돼 제출하면 안 된다.            |


`soften`, `ask_user`, `remove`가 남아 있으면 제출 준비를 이어간다.
사용자 확인이 필요한 문장은 최종 평가 전에 후보자 확인을 받는다.

## 강한 주장에 필요한 근거

- `단독`: 소유권 `git_verified`와 역할 문서 또는 사용자 확인이 함께 필요하다.
- `처음부터 설계`: 설계 문서·초기 커밋·사용자 확인 중 두 종류 이상이 필요하다.
- 구체 수치: 수치를 포함한 로그·벤치마크·문서·사용자 확인 중 하나가 필요하다.
- `해결`, `제거`, `안정화`: 결과가 `measured`, `test_verified`, `documented`, `user_attested` 중 하나여야 한다.
- `운영`: 배포 설정, 운영 문서, 릴리스 이력 또는 사용자 확인이 필요하다.
- `주력`, `숙련`, `전문`, `노하우`: `operations_verified` 또는 구체적인 사용자 확인이 필요하다.
- `트러블슈팅`: 장애 현상, 진단 과정, 선택한 조치와 결과 중 세 항목 이상이 필요하다.
- `N년 동안 A와 B`: A와 B를 독립된 주장으로 나누고 각 기간을 따로 확인한다.

## 애매한 경험의 사용자 확인

먼저 로컬 코드, 테스트, Git 이력, ADR, 장애 기록과 배포 문서를 확인한다.
그래도 경험 깊이를 판단할 수 없고 후보자의 답에 따라 제출 문구가 달라지면 `ask_user`로 판정한다.

서로 독립적으로 답할 수 있으면 다음 요소를 질문으로 묶어 확인한다.
한 답이 다음 질문의 전제가 되면 한 질문씩 이어간다.

- 실제로 맡은 기능과 기간
- 해당 기술 때문에 발생한 문제
- 후보자가 직접 내린 판단과 조치
- 운영 결과 또는 다시 적용할 수 있는 노하우

운영 근거는 일반적인 기술 설명보다 구체적인 운영 사례로 판정한다.
구체적인 사례가 없다는 답변도 유효한 확인이며, 해당 기술을 주력 목록에서 빼는 근거로 기록한다.
제출 문구를 바꾸지 않는 면접 대비 질문은 `evidence/interview-questions.json`에 선택적으로 남길 수 있다.
claim ledger의 `safe` 판정은 검증된 제출 문구와 근거로 결정한다.

## 근거를 어디서 인용했는지 적는 방법

근거의 `path`만 적으면 파일은 있고 인용한 내용은 그 파일에 없는 원장도 통과한다.
실측으로 한 원장이 후보자 인터뷰 파일을 138회 인용했는데 117건이 그 파일에 없는 내용이었고,
87건 중 71건의 주장이 영향을 받았다.

`schemaVersion: 3`부터 `document`와 `user` 근거에 `locator`를 함께 적는다.
검증기가 그 자리를 근거 파일에서 직접 찾으므로 형식을 넷으로 좁힌다.


| 형태                  | 예                            | 검증기가 확인하는 것            |
| ------------------- | ---------------------------- | --------------------- |
| `heading:<제목>`      | `heading:경력 기간 계산 기준`        | 마크다운 제목 줄의 글자에 그 문자열이 있다 |
| `line:<번호>`         | `line:42`                    | 그 줄이 파일 안에 있고 비어 있지 않다  |
| `lines:<시작>-<끝>`    | `lines:42-58`                | 그 범위가 파일 안에 있고 비어 있지 않다 |
| `quote:<문구>`        | `quote:워커 RSS가 누적됐다`         | 본문에 그 문구가 그대로 있다      |


제목과 문구는 공백을 하나로 줄이고 `*`, `` ` ``, `_`를 지운 뒤 비교한다.
그래서 `heading:이력서 전면 개편에서 확인한 사실`은 `## 이력서 전면 개편에서 확인한 사실: 2026-09-06`에도 걸린다.

`code`, `test`, `git`, `artifact`, `runtime` 근거에는 locator를 요구하지 않는다.
파일 하나를 수십 번 인용하는 종류가 아니고, `runtime`은 원격 URL을 쓴다.

이미 제출한 `schemaVersion: 2` 원장은 locator 어긋남을 경고로만 보고한다.
과거 건을 소급해 고치지 않고, 새로 만드는 원장부터 `schemaVersion: 3`을 쓴다.

## 근거 우선순위

근거 우선순위가 높아도 주장 축별 확인은 따로 수행한다.

1. 실행 결과·벤치마크·운영 기록
2. 코드와 동작 테스트
3. Git 작성 이력과 설계 기록
4. 업무 문서
5. 사용자 확인
6. 추론

제출 문구에는 위 근거 중 하나 이상으로 확인된 주장만 사용한다.
