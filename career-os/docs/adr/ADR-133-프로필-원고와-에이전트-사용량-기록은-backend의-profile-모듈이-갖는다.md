## ADR-133: 프로필 원고와 에이전트 사용량 기록은 Backend 의 profile 모듈이 갖는다

- **status**: `accepted`
- **결정**:
  - 원티드, LinkedIn, GitHub 프로필 원고와 월별 에이전트 사용량 기록의 원본을 커리어 Backend 의 `profile` 모듈에 둔다. 비공개 작업본의 `library/profiles/` 에는 두지 않는다.
  - 프로필 원고는 문서 키 `wanted`, `linkedin`, `github` 의 Markdown 본문이다. 저장 계약은 후보자 맥락 문서와 같다. 본문 전체 교체, `expectedVersion` 낙관적 잠금, `note`, 저장마다 남는 이력 행이다.
  - 사용량 기록은 달마다 한 행이다. **그 달의 기록이 이미 있으면 저장 요청을 받아도 값을 바꾸지 않는다.** 바꾸려면 요청이 `replace` 와 사유를 명시한다.
  - 측정은 세션 기록이 있는 기기에서만 한다. 그 기기의 수집기가 매일 돌며 기록이 없는 끝난 달만 측정해 올린다.
  - GitHub 프로필의 차트는 저장한 이미지가 아니라 사용량 기록에서 그때마다 그린다.
- **맥락**:
  - 세션 기록은 시간이 지나면 기기에서 지워진다. 2026년 9월 7일에 24.6B 로 측정한 8월을 10월 2일에 다시 세니 8.2B 였고, 7월의 Claude Code 기록은 남아 있지 않았다. 측정값을 그때 적어 두지 않으면 다시 얻을 수 없다.
  - 프로필 원고와 측정 기록은 `library/profiles/` 의 파일이었다. 비공개 작업본은 release 단위로 통째로 동기화하고 홈서버 SSH 가 있어야 읽고 쓴다. 2026년 10월 2일에 SSH 가 닿지 않아 한 달 전에 받은 원고로 프로필을 갱신했고, 고친 원고를 발행하지 못했다.
  - 프로필 갱신을 fos-assistant 의 커넥터에서도 하려 한다. 커넥터의 MCP 서버는 파일을 읽지 않고 HTTP API 만 부른다.
- **대안 기각**:
  - 후보자 맥락 문서에 키를 더한다: 코드와 CLI 를 그대로 쓴다. 그러나 후보자 맥락은 스킬이 판단에 쓰는 입력이고 프로필 원고는 밖에 올린 결과다. [ADR-131](ADR-131-후보자-맥락은-backend-문서로-두고-공부-추천-기준-버전을-문서-버전에서-계산한다.md)이 키를 넷으로 고정한 까닭이 오타로 새 문서가 생기지 않게 하는 것이었고, 성격이 다른 문서를 같은 표에 넣으면 그 목록이 판단 입력의 목록이 아니게 된다.
  - 파일을 원본으로 두고 Backend 로 복사한다: 같은 원고가 두 곳에 있어 한쪽만 고쳐진다.
  - fos-assistant 의 Memory 문서로 둔다: 그 서비스 토큰은 읽기 전용이라 수집기가 측정값을 올릴 길이 없다.
  - 더 큰 값이 오면 기록을 바꾼다: 달 중간에 측정한 값을 고칠 수 있다. 그러나 환산 비용은 단가표가 바뀌면 함께 바뀌어 같은 달의 값이 흔들린다. 수집기가 끝난 달만 올리게 해 중간 측정을 막는다.
  - 차트 이미지를 저장한다: 기록에서 계산되는 값이다. 저장하면 기록과 이미지가 어긋날 수 있다.
- **결과**:
  - 얻는 것: 홈서버 SSH 없이 Backend 만 닿으면 원고를 읽고 쓴다. 노트북의 `sync-profile` 과 커넥터가 같은 원고를 본다. 측정값이 세션 기록보다 오래 남는다.
  - 감당할 것: 문서 저장 코드가 후보자 맥락 모듈과 비슷하게 한 벌 더 있다. 수집기가 한 달 넘게 돌지 않으면 그 달의 값은 실제보다 작게 기록되고, 그 사실은 `measuredOn` 으로만 드러난다. 2026년 7월과 8월은 옛 차트에서 되읽은 토큰만 있고 환산 비용과 세션 수가 없다.
