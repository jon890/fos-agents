# ADR-111 학습자료와 추천 상태는 블로그 API로 관리한다

- **status**: `accepted`
- **결정**: 블로그 연동 모드의 자료, 추천 이력과 개인 상태는 `fos-blog`의 기존 MySQL을 기준으로 관리한다. career-os는 HTTP API로 수집 결과와 추천을 전달하며 DB에 직접 연결하지 않는다.

## 맥락

최근 피드만 읽고 실행 자료를 폐기하면 오래된 자료를 다시 찾거나 기기 간 즐겨찾기를 공유하기 어렵다.
파일 추천 이력과 실제 게시 결과가 어긋나면 이미 추천한 자료도 다시 후보로 들어온다.
사용자는 PC와 모바일에서 같은 자료·별표·읽음·메모를 관리하고, 기존 블로그의 공통 관리자 로그인을 사용하기로 했다.

[파일 기반 피드백 결정](ADR-102-별도-웹-대시보드보다-파일-기반-피드백-루프를-사용한다.md)은 별도 웹 서비스의 운영 비용을 피하려는 결정이었다.
이번에는 이미 운영하는 블로그와 DB를 재사용하므로 학습자료 기능에 한해 서버 상태를 추가할 가치가 있다.
[S3 release 결정](ADR-108-비공개-작업-release는-범용-s3-collection에-보관한다.md)의 지원·면접 파일 계약은 유지한다.

## 상태와 트랜잭션

같은 원문은 기존 `contentKey`로 식별하고, 여러 소스의 수집 기록을 하나의 자료에 연결한다.
추천 여부, 별표와 읽음은 서로 독립적이며 재수집으로 개인 상태를 덮어쓰지 않는다.

자료 묶음과 다음 수집 위치는 한 트랜잭션에 저장한다.
추천은 리포트 전체를 원자적으로 반영하고, 저장 시점에 과거 자료와 직전 주제의 중복을 다시 검사한다.
요청 재시도에는 같은 키와 본문을 사용하여 응답 유실이 중복 저장으로 이어지지 않게 한다.

## 대안 기각

| 대안 | 기각 이유 |
| --- | --- |
| 임시 피드 캐시를 장기 저장소로 사용 | 재생성 가능한 응답과 개인 상태의 보존 책임이 다르다 |
| Google Sheets에 모든 상태 저장 | 기존 블로그 UI와 DB가 있는데 동시 수정·권한·검색 계약을 별도로 만들어야 한다 |
| career-os가 MySQL에 직접 연결 | DB 자격증명과 저장 구조가 수집 환경에 노출되고 양쪽이 같은 테이블 변경에 묶인다 |
| 파일과 DB에 동시에 추천 이력 쓰기 | 부분 실패 때 어느 쪽을 기준으로 중복을 판정할지 모호해진다 |

## 결과와 적용 범위

연동 모드는 서버 장애 시 쓰기를 중단하며 파일 이력으로 자동 전환하지 않는다.
기존 파일 모드는 운영 전환 전까지 유지하고, 이관은 파일과 게시 결과를 대조한 미리보기 후 별도로 적용한다.
과거 반복 추천은 리포트별 노출 이력으로 보존한다.

얻는 것은 과거 자료 검색, 기기 간 동일한 개인 상태와 일관된 추천 중복 판정이다.
감당할 것은 블로그 API의 가용성, DB 백업·복구와 계약 변경 관리다.
이 결정의 수용은 구현 완료나 운영 DB 적용을 뜻하지 않는다.

공부 화면은 관리자 로그인 후 본인에게 제공하며 공개 자료 모음의 자동 발행은 포함하지 않는다.
원문 링크와 출처, 직접 작성한 짧은 소개를 보관하고 원문 전체·이미지·영상 자막 복제를 기본 기능에 넣지 않는다.
공개 기능을 추가할 때는 소개문이 원문 표현을 이용하는 정도를 별도로 검토한다.
일반 링크를 원문 복제와 구분한 [대법원 판결](https://www.law.go.kr/LSW/precInfoP.do?precSeq=141381)과
[저작권법의 공정 이용 규정](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=05&joNo=0035&lsiSeq=283335&urlMode=lsScJoRltInfoR)을 참고하되,
출처 표시나 글자 수를 허용 여부의 보장 조건으로 사용하지 않는다.
