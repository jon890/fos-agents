# ADR-117 포지션 분석은 우선순위 큐와 버전 이력으로 재사용한다

- Status: Accepted
- Date: 2026-09-17

## 결정

포지션 추천은 매 실행마다 모든 활성 공고를 모델로 다시 평가하지 않는다.
개인 제외 정책을 먼저 적용하고, 회사 티어와 분석 상태로 제한된 분석 큐를 만든다.
일일 기본 20건 중 16건은 상위 회사 우선 슬롯, 4건은 오래 기다린 공고 보장 슬롯으로 사용한다.

공고별 분석은 `state/position-analysis/`에 버전 이력으로 저장한다.
공고 본문 hash, 후보자 기준 버전, 분석 계약 버전과 유효기간이 모두 맞을 때만 재사용한다.
아직 분석하지 않은 활성 공고는 전체 순위에 억지로 넣지 않고 분석 대기로 표시한다.
추천 결과에는 재사용과 신규 분석 건수뿐 아니라 부분 실패한 수집 소스도 표시한다.

## 대체된 부분

[ADR-100](ADR-100-position-recommender-신규-후보-강제-회전-폐기.md)의 신규 공고 강제 추천 금지는 유지한다.
다만 모든 활성 공고를 매 실행마다 평가한다는 결정은 제한된 분석 큐와 분석 대기 목록으로 대체한다.

[ADR-115](ADR-115-회사-조사-사실은-유효기간과-함께-재사용한다.md)의 회사 사실 재사용 결정은 유지한다.
다만 최종 추천 판단을 저장하지 않는다는 결정은 명시적인 무효화 조건을 가진 공고별 분석 이력으로 대체한다.

## 맥락

2026-09-17 실행은 활성 후보 122건을 다루면서 모델 API를 51회 호출했고 입력 3,460,816토큰을 사용했다.
추천 JSON 검증 뒤의 16회 호출만 1,759,795토큰이었다.
같은 날 다시 수집한 후보풀은 105건, 406,092바이트였으므로 파일 크기보다 누적 대화 기록을 반복 전송한 비용이 컸다.

매일 실행하면 전날과 같은 공고를 다시 분석하는 비율이 높다.
반대로 신규 공고만 우선하면 관심 회사의 변경 공고나 오래 기다린 다른 회사 공고를 놓칠 수 있다.
사용자가 보고 싶지 않은 회사의 공고를 낮은 순위로 계속 분석하는 것도 비용과 검토 시간을 낭비한다.

## 대안 기각

- 전체 후보를 매일 다시 평가하는 방식은 최신성은 높지만 같은 본문과 판단을 반복한다.
- 신규 공고만 먼저 분석하는 방식은 회사 우선순위와 기존 공고 변경을 반영하지 못한다.
- 회사 티어만 적용하는 방식은 하위 티어 공고가 계속 대기할 수 있다.
- MySQL 저장은 질의와 동시 처리에는 편하지만 현재 단일 사용자 cron과 후보 규모에는 운영 요소가 늘어난다.
- 공고마다 새 범용 에이전트를 시작하면 고정 system prompt와 도구 정의를 공고 수만큼 다시 입력한다.

## 결과

- 얻는 것: 반복 실행은 유효한 분석을 재사용하고 모델은 선택된 공고만 읽는다.
- 얻는 것: 상위 회사 공고를 먼저 보면서도 오래 기다린 공고에 최소 분석 기회를 보장한다.
- 얻는 것: 개인 제외 회사는 모델 입력 전에 빠지고, 수집 실패와 분석 대기는 최종 결과에서 확인할 수 있다.
- 감당할 것: 후보자 기준이 바뀌면 비공개 정책의 `candidateContextVersion`을 갱신해야 한다.
- 감당할 것: 저장 분석의 점수는 여러 날의 공고를 비교하므로 분석 계약과 결정적 정렬 규칙을 유지해야 한다.
- 감당할 것: 첫 실행이나 정책 버전 변경 직후에는 분석 대기가 남을 수 있다.

## 적용 범위

career-os의 `position-recommender`와 비공개 작업 release에만 적용한다.
Hermes의 세션 구조, 다른 저장소와 외부 데이터베이스는 변경하지 않는다.
