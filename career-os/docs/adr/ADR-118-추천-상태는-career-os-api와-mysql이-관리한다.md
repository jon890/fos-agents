# ADR-118 추천 상태는 career-os API와 MySQL이 관리한다

- **status**: `accepted`
- **결정**: 포지션 추천과 학습자료 추천의 장기 상태는 `career-os`가 소유하는 HTTP API와 홈서버 MySQL의 `fos_career` 데이터베이스에서 관리한다. 수집기와 skill은 DB에 직접 연결하지 않고 Bearer token이 있는 HTTP API만 호출한다.

## 대체된 부분

[ADR-111](ADR-111-학습자료와-추천-상태는-블로그-api로-관리한다.md)의 `fos-blog` API와 DB가 학습자료 상태를 소유한다는 결정을 대체한다.
`fos-blog`는 전환 검증 뒤 study 테이블과 API를 제거하고, 필요한 화면은 새 API를 호출하는 소비자로만 남길 수 있다.

[ADR-117](ADR-117-포지션-분석은-우선순위-큐와-버전-이력으로-재사용한다.md)의 회사 우선순위와 오래 기다린 공고 보장 규칙은 유지한다.
다만 공고별 분석을 `state/position-analysis/` 파일에 저장한다는 결정은 `fos_career`의 버전 이력으로 대체한다.

[ADR-102](ADR-102-별도-웹-대시보드보다-파일-기반-피드백-루프를-사용한다.md)의 지원 문서와 면접 자료 저장 결정은 유지한다.
포지션과 학습자료의 수집·분석·추천 상태만 HTTP API와 MySQL을 사용한다.

## 맥락

포지션 추천은 매일 실행되므로 같은 공고와 분석을 다시 읽는 비율이 높다.
2026-09-17 실행은 모델 API를 51회 호출하면서 입력 3,460,816토큰을 사용했고,
추천 JSON 검증 이후에도 누적 대화 기록을 16회 다시 전달해 1,759,795토큰을 사용했다.
같은 날 다시 수집한 후보풀은 105건과 406,092바이트였으므로 파일 하나의 크기보다 여러 호출에 누적 기록을 다시 보낸 영향이 컸다.

파일 저장은 한 실행 환경에서는 단순하지만 cron과 수동 실행이 겹칠 때 원자적인 갱신과 중복 방지를 별도로 구현해야 한다.
학습자료도 이미 누적 자료, cursor, 추천 이력과 개인 상태를 관계형 스키마로 설계했으므로 두 추천 기능의 저장 경계를 한 서비스로 모을 수 있다.

## 서비스와 배포 경계

- `career-os`는 Backend 코드, HTTP 계약, migration과 도메인 검증을 소유한다.
- Backend는 Bun의 HTTP 서버와 `Bun.SQL`을 사용하며 새 ORM과 외부 queue를 도입하지 않는다.
- Backend만 최소 권한 MySQL 계정을 가지며 skill과 cron에는 API URL과 token만 제공한다.
- `fos-home-infra`는 MySQL database와 계정 생성, container 배포, 비밀 값 주입, healthcheck, backup과 rollback을 담당한다.
- `fos-blog`는 기존 study 계약의 소비자 전환과 검증된 제거 migration만 담당한다.
- 기본 배포는 홈서버 내부 network에서만 접근하게 하며 공개 인터넷 endpoint를 요구하지 않는다.

## 데이터와 트랜잭션 경계

공고의 안정적인 식별자와 관측 버전, 개인 분석과 추천 실행을 서로 다른 표로 나눈다.
공고 본문 변경과 후보자 기준 변경을 각각 식별할 수 있어야 하므로 주관적 분석을 공고 행에 직접 넣지 않는다.

수집 실행 반영은 공고와 버전, 실행 항목, 소스 진단을 한 트랜잭션으로 저장한다.
응답으로 반환하는 분석 큐는 개인 제외 규칙을 적용한 뒤 상위 회사 슬롯과 오래 기다린 공고 슬롯으로 제한한다.
분석 반영은 서버가 발급한 실행 ID와 선택 항목을 다시 대조하고, 모두 유효할 때 한 트랜잭션으로 저장한다.

학습자료는 기존 `fos-blog` study 스키마의 source, cursor, material, tag, 개인 상태, 추천 실행, 게시 이력과 요청 중복 방지 관계를 보존한다.
현재 운영 표가 비어 있으므로 데이터 복사는 필요하지 않지만, 새 API의 계약 검증과 전환 확인을 마치기 전에는 기존 표를 제거하지 않는다.

## 호출 방식

cron 한 번은 동기 HTTP 요청으로 다음 단계를 진행한다.

1. 수집 결과와 소스 진단을 멱등 키와 함께 저장한다.
2. Backend가 분석하지 않았거나 본문이 바뀌었거나 유효기간이 지난 공고만 제한된 큐로 반환한다.
3. 모델은 반환된 공고만 분석한다.
4. 분석 결과를 실행 ID와 함께 반영한다.
5. Backend가 저장 분석과 대기 공고, 실패 소스 진단을 조립해 추천 리포트 입력을 반환한다.

별도 queue와 worker는 두지 않는다.
중복 cron은 멱등 키와 실행 상태로 구분하고 같은 요청을 다시 보내도 새 이력을 만들지 않는다.
향후 병렬 소비자가 필요해질 때만 DB lease 기반 작업 표를 별도 결정한다.

## 대안 기각

| 대안 | 기각 이유 |
| --- | --- |
| 공고와 분석을 Git 제외 파일로 저장 | 단일 실행에는 단순하지만 cron 중복, 부분 반영, 조건 검색과 두 기능의 공통 조회를 별도로 구현해야 한다 |
| skill이 MySQL에 직접 연결 | DB 자격증명과 migration 결합이 모든 실행 환경으로 퍼지고 HTTP 계약에서 권한과 검증을 한 곳에 둘 수 없다 |
| `fos-blog`가 공고와 학습자료 Backend를 모두 소유 | 포지션과 추천 실행의 도메인 변경이 블로그 저장소 배포에 묶이며 career-os가 자기 계약을 소유하지 못한다 |
| 외부 message queue를 함께 도입 | 현재 단일 사용자 cron은 동기 요청과 멱등성으로 처리할 수 있고 별도 broker 운영 근거가 없다 |

## 결과

- 얻는 것: 매일 같은 공고와 학습자료 분석을 재사용하고 필요한 행만 모델에 전달할 수 있다.
- 얻는 것: 회사 우선순위, 명시적 제외, 오래 기다린 공고와 분석 만료를 SQL 조건으로 일관되게 고를 수 있다.
- 얻는 것: 쿠팡 상세 조회의 HTTP 429 같은 소스 실패를 실행 진단으로 보존하고 최종 결과에 표시할 수 있다.
- 얻는 것: cron 재시도와 중복 실행을 멱등 키와 트랜잭션으로 처리할 수 있다.
- 감당할 것: Backend와 MySQL의 배포, migration, backup, token 교체와 장애 대응이 필요하다.
- 감당할 것: Backend가 중단되면 추천 상태를 파일에 대신 쓰지 않고 실행을 실패로 끝낸다.
- 감당할 것: `fos-blog` study 표 제거는 새 API 전환과 rollback 기간을 확인한 뒤 별도 migration으로 수행한다.
