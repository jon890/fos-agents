## ADR-122: 추천 상태는 질의 단위로 읽고 쓴다

- **status**: `accepted`
- **결정**: Backend는 `fos_career`의 필요한 행만 질의로 읽고 바뀐 행만 쓴다. database 전체를 메모리에 두지 않는다. 큐 선택의 순서와 제한은 `ORDER BY`와 `LIMIT`이 표현한다. 쓰기 트랜잭션은 시작할 때 자기 실행 행을 `SELECT ... FOR UPDATE`로 잠근다. 잠금 단위는 수집 실행, 회사 tier 실행, 공고 분석 실행, 추천 실행, 정책 다섯이다. 기동은 연결 확인과 적용된 migration 조회만 한다.
- **맥락**: 지금은 `fos_career` 전체를 기동할 때 Map 아홉 개로 읽고, 쓰기마다 그 상태 전체를 `INSERT ... ON DUPLICATE KEY UPDATE`로 다시 쓴다. 요청 하나가 쓰는 행 수가 저장된 행 수와 같다. 2026-09-21 홈서버 운영 `fos_career`의 `information_schema.TABLES`를 조회하니 전체 1,003행이고 데이터 2.44MB에 index 0.53MB다. 지금은 견디지만 `positions`와 `position_versions`는 매일 실행마다 늘고 줄지 않는다. 공고를 지우지 않는 것이 버전 이력의 전제여서 행 수가 단조 증가한다. 조회 조건도 SQL이 풀지 않는다. 분석 큐 선택과 회사 tier 큐 선택이 모두 메모리 순회라 index가 있어도 쓰이지 않는다. 그리고 `transactionTail`이라는 프로세스 안의 잠금 하나가 모든 쓰기를 직렬화해 동시성 문제를 덮고 있는데, 서비스를 둘 띄우면 그 보장이 사라진다는 사실이 코드 어디에도 적혀 있지 않다.
- **대안 기각**:
  - 스냅샷을 유지하고 매핑만 [ADR-121](ADR-121-추천-backend는-nestjs와-prisma로-운영한다.md)의 Prisma로 바꾸는 안은 기각했다. 저장 계층 코드는 줄지만 행 수에 비례하는 쓰기와 메모리 상주가 그대로 남는다. 두 결정을 따로 기록하는 이유가 여기 있다. ORM 교체와 접근 방식 변경은 각각 단독으로 성립하고, 이 안은 앞만 하고 뒤를 하지 않는 선택이다.
  - 스냅샷을 유지하되 변경된 것만 쓰는 안은 기각했다. 어느 행이 바뀌었는지 알려면 이전 상태와 비교해야 하고, 그 비교를 손으로 쓰는 것이 질의를 직접 쓰는 것보다 어렵다. 비교가 틀려도 결과가 드러나지 않는다.
  - 프로세스 안의 잠금을 그대로 두는 안은 기각했다. 서비스가 하나일 때만 맞는 보장이라 배포 방식이 바뀌면 오류 없이 결과만 달라진다. 잠금 단위를 DB 행으로 옮기면 그 조건이 사라진다.
  - 행 수가 문제가 될 때 고치는 안은 기각했다. 그때는 저장된 행이 더 많아 이관이 지금보다 비싸다. 회사 tier table 셋은 2026-09-21 기준 아직 0행이다.
- **결과**:
  - 얻는 것: 요청 하나가 읽고 쓰는 양이 저장된 전체 행 수와 무관해진다. 큐 선택이 index를 쓴다. 기동이 전체 적재를 기다리지 않으므로 `GET /health/ready`가 빨라진다. 동시 쓰기의 안전이 프로세스 수에 기대지 않는다.
  - 감당할 것: 동시 쓰기의 의미가 달라진다. 지금은 멱등 키가 다른 두 요청이 같은 실행에 동시에 와도 직렬화되어 안전하지만, 전환 뒤에는 행 잠금이 그 자리를 대신하므로 잠그지 않은 경로가 하나라도 있으면 결과가 갈린다. 다섯 개 쓰기 경로 각각에 대해, 멱등 키가 다른 두 요청을 같은 실행에 동시에 보내 하나만 반영되는 것을 확인하는 테스트를 둔다. 그 테스트가 잠금을 없앴을 때 실패하는 것까지 확인해야 검증으로 친다. 테스트의 기반도 바뀐다. 메모리 저장소 위에서 빠르게 돌던 도메인 테스트가 실제 MySQL을 요구하므로 `MemoryPositionRepository`와 그 테스트는 제거한다. 느려지는 대신 `CHECK` 제약과 `ENUM` 기본값처럼 메모리 가짜가 표현하지 못하는 것을 확인한다. 멱등 계층은 바뀌지 않는다. `request_receipts`의 선점은 이미 `INSERT IGNORE`와 영향받은 행 수로 DB 수준에서 판정한다.
- **적용 범위**: `services/recommendation-api/`의 저장 계층과 도메인 서비스 전체, `docs/code-architecture.md`. `scripts/position-recommender/`의 12개 파일은 import 경로와 두 pipeline 테스트의 분할만 바뀐다. HTTP 계약과 저장 모델은 바뀌지 않는다. 다만 회사 대표 공고를 고르는 순서가 달라진다. `position_collection_items`에 수집 pool 안의 순서를 담는 열이 없어서다. 전환 전에는 메모리에 든 pool 순서로 골랐고 서버를 다시 띄운 뒤에는 `position_id` 순으로 골라, 같은 입력에도 재시작 전후로 결과가 달랐다. 전환 후에는 언제나 `(source_key, identity_hash)` 순으로 고른다. 실행마다 같은 값이 나오는 대신, 회사 하나에 공고가 넷 이상일 때 `representativePostingUrls`의 세 개가 전환 전과 다를 수 있다. 순서 열을 더하는 것은 schema 변경이라 이 전환의 범위 밖이고, 필요하면 별도 결정으로 다룬다. 정책 경로의 잠금은 「없애면 그 테스트가 실패한다」로 검증할 수 없다. `configurePolicy`가 한 행짜리 `INSERT ... ON DUPLICATE KEY UPDATE` 하나뿐이라 MySQL의 고유 키 잠금이 이미 두 요청을 직렬화하고 읽고 고쳐 쓰는 단계가 없어 섞일 자리가 없다. 잠금은 이 경로가 읽고 고쳐 쓰는 형태로 바뀔 때를 위해 남긴다. 그 테스트는 결과를 지키는 회귀 방어이고 그 사실을 테스트 주석이 적는다. 저장된 추천을 다시 읽을 때도 응답을 다시 조립한다. 전환 전에도 프로세스를 다시 띄우면 같은 자리를 같은 방식으로 다시 읽었고 포착해 둔 값 자체가 그 조립 경로에서 나왔으므로 동작이 달라진 것은 아니다. 응답 전문을 담을 열을 더하면 만든 시점의 값을 그대로 돌려줄 수 있으나 그것은 schema 변경이다. 정책을 읽어 쓸 내용을 정하는 세 경로는 `lockPolicy`를 실행 행 잠금보다 먼저 부르지 않는다. 읽은 뒤에 정책이 commit되면 그 실행은 옛 정책으로 결과를 쓴다. 다른 행에 쓰므로 값이 덮어써지지는 않는다. 수집이 보낸 `analysisContractVersion`도 같은 모양이다. `position_collection_runs`에 그 값을 담는 열이 없어, 전환 전에도 서버를 다시 띄우면 분석 실행 행에서 되읽을 수 있을 때만 값이 남고 그 전에는 1로 떨어졌다. 전환 후에는 언제나 1이다. 저장소에서 1이 아닌 값을 보내는 곳은 없다. `.claude/skills/position-recommender/`는 손대지 않는다.
