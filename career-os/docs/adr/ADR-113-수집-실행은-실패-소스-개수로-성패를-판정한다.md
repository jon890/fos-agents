## ADR-113 수집 실행은 실패 소스 개수로 성패를 판정한다

- Status: Accepted
- Date: 2026-09-09

### 맥락

`collect_live_postings.ts`는 어댑터를 순차로 돌리고 각 어댑터의 예외를 잡아
`status: failed` 진단으로 바꾼 뒤 남은 소스의 결과로 후보풀을 만든다.
소스 하나가 죽어도 나머지로 추천을 만들 수 있게 한 의도한 동작이다.

그런데 실패 개수를 판정하는 자리가 없었다.
소스 대부분이 실패한 실행과 전부 성공한 실행이 같은 종료 코드 0으로 끝났다.

2026-09-09 17:29 실측이다.
16개 소스 중 9개가 `failed`, 6개가 결과 0건인 `partial`로 끝났고,
수집기는 종료 코드 0으로 후보 122건을 정상 산출물로 남겼다.
같은 명령을 20:56에 다시 돌리자 195건이었다.

빠진 73건에 그날 사용자가 지원 대상으로 지정한 회사 셋이 모두 들어 있었다.
쿠팡 15건, 카카오 계열 16건, 우아한형제들 5건이다.

후보풀 스키마 검증은 이것을 잡지 못한다.
122건짜리 후보풀도 형식이 옳고, 추천 검증기도 후보풀과 추천의 일치만 본다.
결과가 적다는 사실은 어디에서도 실패로 취급되지 않았다.

홈서버 크론은 이 실행을 자동으로 돌린다.
사람이 진단을 읽지 않으면 소스 둘로 만든 추천이 그대로 발행된다.

### 결정

- `live-postings/collection_health.ts`가 실행 전체의 성패를 판정한다.
- 실패 소스가 허용 개수를 넘으면 수집기가 종료 코드 1로 끝낸다.
- 허용 개수의 기본값은 전체 수집이 2개, 단일 소스 수집이 0개다.
- `--max-failed-sources <개수>`로 그 값을 덮어쓴다.
- 어댑터가 `partial`로 보고했더라도 하나도 수집하지 못한 채 오류만 냈으면 실패로 센다.
- 후보가 0건이면 실패 소스가 허용 범위 안이어도 실패로 끝낸다.
- 실패로 끝나도 후보풀 파일은 남긴다. 사람이 실패한 실행의 내용을 열어 볼 수 있어야 한다.
- 실패 사유는 `FAIL collection health` 줄에 담고, 실행을 막지 않는 것은 `WARN collection health` 줄에 담는다.
- 허용 범위 안에서 실패한 소스의 이름도 경고로 알린다. 종료 코드가 0인 실행에서도 사람이 그 이름을 알아야 한다.

판정이 어댑터가 보고한 숫자에 의존하므로 그 숫자의 뜻을 함께 고정한다.

- `collectedCount`는 어댑터가 `Posting`으로 만들어 넘긴 공고 수다. 원본 목록 건수가 아니다.
  뜻은 `contracts.ts`의 `sourceDiagnosticSchema`가 소유한다.
- 원본 목록 건수는 `message`의 `raw`에 적는다.
  `samsung-careers`, `cj-careers`, `sk-careers` 셋이 이 값을 `collectedCount`에 넣고 있었다.
- 요청이나 파싱이 실패해 판단하지 못한 공고는 `failedCount`로 센다. `skippedCount`는 의도적으로 뺀 수만 담는다.
  `samsung-careers`의 상세 요청 실패가 `skippedCount`로 세어지고 있었다.
- 어댑터는 상세 요청 실패를 삼키지 않는다.
  `wanted`가 상세 실패를 `continue`로 넘기고 `status: "ok"`와 `failedCount: 0`을 상수로 보고하고 있었다.
  `wanted`는 후보를 가장 많이 넣는 소스라, 그 실행이 정상으로 읽히면 이 ADR의 판정이 무의미해진다.

### 허용 개수를 2개로 정한 이유

한 소스의 일시적 장애로 매일 도는 크론 전체를 멈추면 추천이 아예 없는 날이 생긴다.
반대로 허용 개수를 크게 두면 이 ADR이 막으려는 상황이 다시 통과한다.

실측 두 건이 기준이 됐다.
정상 실행은 실패 소스가 0개였고 결과 0건인 소스 셋도 오류 없이 `ok`로 끝났다.
장애 실행은 실패로 세는 소스가 15개였다.
둘 사이가 넓어서 2개는 정상 실행을 막지 않고 장애 실행을 통과시키지 않는다.

단일 소스 수집을 0개로 둔 것은 그 소스의 실패가 곧 실행 전체의 실패이기 때문이다.

### 대안과 기각 이유

- **후보 개수의 하한을 둔다.** 소스별 공고 수가 날마다 달라 하한을 정할 근거가 없다.
  결과가 적은 것은 원인이 아니라 증상이고, 원인인 소스 실패를 직접 세는 것이 맞다.
  0건은 예외로 둔다. 날마다 달라지는 값이 아니라 추천을 만들 수 없는 상태다.
- **소스 진단 확인을 스킬 지침에만 남긴다.** 허용 개수가 2이므로 실패 소스 둘까지는 종료 코드 0으로 끝난다.
  그 둘이 지원 대상 회사의 소스일 수 있어, 종료 코드가 0인 실행에서도 실패한 소스 이름을 경고로 낸다.
- **후보풀에 판정 결과를 필드로 담는다.** `sourceDiagnostics`가 이미 소스별 상태를 담고 있어
  같은 사실을 두 곳에 쓰게 된다. 판정은 종료 코드로만 낸다.
- **실패하면 후보풀 파일을 쓰지 않는다.** 무엇이 실패했는지 확인할 근거가 사라진다.
  파일은 남기고 종료 코드로 성패를 알린다.
- **어댑터 실패를 예외로 올려 첫 실패에서 중단한다.** 뒤에 오는 소스의 상태를 알 수 없게 된다.
  전부 돌린 뒤 판정하면 어느 소스가 살아 있는지 한 번에 드러난다.
- **스킬 지침에만 진단 확인을 적는다.** 지침은 실행마다 지켜져야 한다.
  사람이 없는 크론에서는 지켜질 근거가 없어 실측으로 나흘간 확인되지 않았다.
