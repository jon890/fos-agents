## ADR-142: 먼저 살펴보기의 공고 제외 판정은 수집기와 같은 코드가 하고 식별 불가는 보류한다

- **status**: `accepted`
- **결정**:
  - **공고가 개인 제외 규칙에 걸리는지는 코드가 판정한다.** 커넥터에 읽기 도구 `check_position_exclusions` 를 더한다. 입력은 공고마다 `url`, `company`, `title` 이고 `source`, `identityHash` 는 커넥터나 후보 목록이 준 값만 선택으로 받는다.
  - **판정 규칙은 수집기의 것을 재사용한다.** 비교 순서와 URL 정규화를 `scripts/position-recommender/feedback/exclusion-match.ts` 로 옮기고, 수집기 `exclusions.ts` 의 `filterExcludedPostings` 와 plugin 이 같은 함수를 부른다. 새 제외 규칙을 만들지 않는다.
  - **결과는 `excluded`, `clear`, `undeterminable` 셋이다.** `clear` 는 이 공고에 적용되는 모든 규칙을 비교했고 걸린 것이 없다는 뜻이다. 비교하지 못한 규칙이 남으면 `undeterminable` 이고 그 공고는 추천하지 않는다.
    - 공고에 식별자가 없는데 식별자로만 비교하는 규칙(URL 이 없는 공고 제외)이 있다. 공고의 source 를 모르면 모든 source 의 규칙이, 알면 같은 source 의 규칙이 해당한다.
    - 공고의 source 를 알고 식별자를 모르는데 같은 source 의 규칙이 식별자와 URL 을 함께 가졌다. URL 이 바뀐 같은 공고일 수 있다.
    - 공고나 규칙의 URL 을 정규화하지 못했다.
    - 제외 규칙이나 회사별 선호를 읽지 못했다.
  - **`source` 와 `identityHash` 를 모델이 만들지 않는다.** `source` 는 수집기 어댑터 이름만 받고 `identityHash` 는 `source` 와 함께만 받는다. 도구도 주소에서 만들지 않는다. 웹으로 찾은 공고는 보통 두 값이 없으므로 URL 과 회사, 역할로 비교하고 식별자가 필요한 경우는 보류한다.
  - **제외 기준 읽기(`get_position_research_constraints`)는 유지하되 판정에 쓰지 않는다.** 검색 전에 읽기 가능 여부(`readiness`)와 검색어에 넣지 않을 회사 이름을 얻는 데만 쓴다.
  - **직접 호출과 위임이 같은 도구, 같은 입력, 같은 결과를 쓴다.** 위임은 세 번째 위임을 쓰므로 `max-delegations` 3 안에서 맥락 읽기, 제외 기준 읽기, 공고 판정이 각각 한 번이다.
- **맥락**:
  - Backend 의 posting 제외는 `identityHash` 나 `url` 중 하나로 저장할 수 있고, 수집기는 source 와 식별자 또는 정규화한 URL 로 비교한다. 먼저 살펴보기의 지침은 `source`, `identityHash` 를 읽지 않았고 공고 URL 이 같은지만 모델이 견주게 했다.
  - 그래서 식별자만 저장된 제외, URL 이 바뀐 같은 공고, tracking parameter 나 fragment, query 순서, 끝 슬래시만 다른 URL 이 새 제안으로 남을 수 있었다. 규칙을 읽는 데 성공한 것과 특정 공고를 판정할 수 있는 것도 구분하지 않았다.
  - 모델이 식별자를 만들거나 URL 을 정규화하면 같은 공고의 판정이 실행마다 달라진다.
- **대안 기각**:
  - 지침에 `source`, `identityHash` 와 정규화 규칙을 더 적고 모델이 견주게 한다: 정규화가 모델마다 달라지고 누락된 식별자를 지어낼 수 있다. 같은 규칙을 지침과 코드에 두 번 적게 된다.
  - 공고 URL 에서 source 와 식별자를 도구가 유도한다: 어댑터마다 식별자 규칙이 달라(예: 일부는 응답의 실제 번호) 어댑터 16개의 규칙을 복제하게 되고 어긋나면 엉뚱한 공고를 제외한다. 필요하면 어댑터가 소유한 함수를 분리해 따로 정한다.
  - 식별자가 없으면 모든 규칙을 해당으로 보고 보류한다: URL 을 함께 가진 규칙이 대부분이라 웹으로 찾은 포지션이 전부 보류돼 쓸 수 없다.
  - 식별자가 없으면 URL 만 비교하고 통과시킨다: 식별자만 저장된 제외가 조용히 새 제안으로 돌아온다.
- **결과**:
  - 얻는 것: 수집기와 먼저 살펴보기가 같은 판정을 쓴다. 식별자만 저장된 제외와 URL 표현 차이를 코드 시험으로 고정한다. 판정하지 못하는 공고는 추천 대신 보류로 드러나고 공부와 동향 조사는 이어진다.
  - 감당할 것: 웹으로 찾은 공고에 식별자가 없어, 식별자만 저장된 제외가 있으면 그 source 의 공고는 보류된다. source 를 모르는 공고는 URL 을 가진 규칙의 URL 이 바뀐 같은 공고를 막지 못한다. 위임 경로는 위임 한도 셋을 모두 쓴다.
