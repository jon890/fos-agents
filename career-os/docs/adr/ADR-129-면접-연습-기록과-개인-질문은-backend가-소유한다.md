## ADR-129: 면접 연습 기록과 개인 질문은 Backend가 소유한다

- **status**: `accepted`
- **결정**: `interview-practice` 의 주제별 복습 상태, 연습 기록과 개인 질문을 파일에서 `fos_career` 로 옮긴다. `scripts/interview-drill/drill-engine.ts` 는 `/api/interview/v1` 로 읽고 쓰며 이 셋을 파일에 쓰지 않는다. 복습일 계산은 연습 기록 추가와 같은 transaction 안에서 Backend 가 한다. 공개 질문 은행, 공고별 질문과 질문 출처 config 는 파일로 남는다.
- **맥락**:
  - 면접 연습은 hermes 의 `career` profile 에서 여러 대화에 걸쳐 진행한다. 복습 상태가 container 안 작업본의 `state/drill-progress.json` 에 있으면 작업본을 다시 준비하거나 다른 실행 환경에서 연습할 때 기록이 이어지지 않는다.
  - 스킬은 결과를 기록하라고 지시했지만 엔진 CLI 에는 기록 명령이 없었다. 모델은 즉석 스크립트로만 기록할 수 있었고, hermes 는 그런 명령을 막는다. 2026-09-27 에 노트북, 홈서버와 hermes 어디에도 연습 기록 파일이 없었다.
  - 개인 질문은 비공개 작업본 release 로 동기화했다. 대화 중에 더한 질문은 release 를 다시 발행해야 다음 대화에 보인다.
  - 커리어 Backend 는 이미 hermes 와 같은 Docker network 에 있고 hermes 는 연결값을 가지고 있다. 새 운영 구성 요소가 필요 없다.
- **대체된 부분**: [ADR-102](ADR-102-별도-웹-대시보드보다-파일-기반-피드백-루프를-사용한다.md) 가 면접 자료에 파일 기반 상태를 적용한 부분 중 연습 기록과 개인 질문을 이 ADR 이 대체한다. 지원 문서와 공고별 질문에는 ADR-102 가 그대로 적용된다.
- **대안 기각**:
  - 파일을 유지하고 기록 명령만 더하는 안은 기각했다. 기록 누락은 고치지만 실행 환경마다 복습 상태가 따로 쌓이는 문제가 남는다.
  - Backend 에 닿지 못할 때 로컬 파일에 쌓았다가 다시 보내는 안은 기각했다. 원본이 둘이 되고 재전송 코드와 파일 상태가 다시 생긴다. Backend 는 hermes 와 같은 홈서버에 있어 한쪽만 멈추는 일이 드물다. 닿지 못하면 명령이 실패하고 모델이 기록되지 않았다고 알린다.
  - 질문 출처 config 까지 옮기는 안은 기각했다. [ADR-126](ADR-126-읽을거리-소스-목록은-backend가-원본을-가진다.md) 이 읽을거리 출처를 옮긴 이유는 매일 도는 cron 에서 실패하는 출처를 커밋 없이 꺼야 한다는 것과, 출처를 가리키는 DB 행이 있다는 것이었다. 면접 질문 출처에는 둘 다 없다.
  - 개인 질문의 `answerSignals` 와 `followUps` 를 자식 table 로 나누는 안은 기각했다. 이 목록은 따로 조회하거나 집계하지 않고 질문 전체가 한 번에 모델에게 전달된다. 조회에 쓰는 칸만 컬럼으로 두고 나머지는 쓰기 전에 검사한 JSON 으로 둔다.
- **결과**:
  - 얻는 것: 어느 대화에서 연습해도 같은 복습 상태로 질문을 고른다. 대화 중에 더한 개인 질문이 다음 연습에 바로 쓰인다. 기록 재시도는 `attemptId` 로 한 번만 반영된다. 두 대화가 같은 주제를 동시에 기록해도 주제 행 잠금으로 순서대로 반영된다.
  - 감당할 것: Backend 가 멈추면 연습 질문을 고를 수도 기록할 수도 없다. 복습일 규칙이 client 에서 서버로 옮겨 가므로 규칙을 바꾸면 Backend 를 배포해야 한다. 개인 질문 JSON 의 형식은 DB 제약이 아니라 Backend 의 zod 검사가 지킨다.
