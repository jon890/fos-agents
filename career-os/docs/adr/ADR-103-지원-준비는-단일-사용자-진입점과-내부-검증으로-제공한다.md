## ADR-103 지원 준비는 단일 사용자 진입점과 내부 검증으로 제공한다

- Status: Accepted
- Date: 2026-08-26

### 맥락

지원 패키지 생성, Markdown 검토, 이력서 근거 감사와 HTML 평가가 각각 사용자 스킬로 드러나면 사용자가 어떤 문서를 읽고 어떤 순서로 실행해야 하는지 다시 판단해야 한다. 폐기한 웹 자동화의 상태 전이와 별도 `review.md`는 현재 스킬 중심 흐름에서 소비되지 않는다.

### 결정

- 사용자는 `application-package-writer` 하나로 지원 준비를 시작한다.
- `application-package.md`를 지원 판단, 공고·회사 기준, 후보자 근거, 승부처, 공백과 다음 행동을 설명하는 중심 원본으로 사용한다.
- 사용자 검토 화면은 `application-package.html` 하나로 제공하며 후보자 인터뷰, 지원 판단, 제출 문서와 현재 검증 상태를 함께 보여준다.
- 검토 화면의 첫 영역에는 현재 할 일, 제출 후보 PDF와 필요한 경우의 지원서 입력값만 보여준다. 승부처, 지원동기, 공백과 다음 행동을 먼저 보여주며 나머지 지원 전략, 이력서 원문, 개별 PDF, 면접 질문과 후보자 인터뷰 기록은 닫힌 상세 영역으로 제공한다.
- 근거 장부, 점수표, manifest와 HTML 중간 파일은 검증에 사용하지만 사용자용 링크로 나열하지 않는다.
- 기본 원본은 `candidate-interview.md`, `application-package.md`, `resume-draft.md`와 `interview-questions.json`만 유지한다.
- 브라우저 자동 입력을 준비하면 private brain의 공통 프로필 스냅샷, 회사별 선택값, 첨부 파일과 서술형 문항을 `application-form.json` 하나로 만든다. 후보자 인터뷰에는 공통 개인정보를 복제하지 않는다.
- 경력기술서는 채용 사이트가 요구할 때만 만들고, 이력서와 경력기술서는 각각 HTML·PDF를 유지한다. 한 파일 제출이 필요하면 `submission.pdf`를 추가한다.
- 후보자 인터뷰는 기존 답변을 보존하고 서로 독립적인 질문을 최대 6개까지 묶어 확인한다. 한 답이 다음 질문을 바꾸면 한 질문씩 이어간다.
- `application-package-writer`는 공고 분석, 후보자 인터뷰와 지원 전략을 책임지고 전체 지원 요청에서는 다음 단계를 자동으로 연결한다.
- `resume-preparer`는 이력서와 경력기술서 작성, 사람 확인, 근거 감사, 블라인드 하드 리뷰, HTML·PDF와 제출 묶음 검증을 책임진다.
- 초안을 사용자에게 보여주기 전에 지원 전략, 이력서, 경력기술서와 지원서 답변의 외부 문장을 전수 검사한다. 제품 전체에 만든 체계와 구체적인 한 개선 사례의 범위를 구분하고, 같은 경험의 대상, 역할, 수치와 기간을 모든 문서에서 일치시킨다.
- 사용자가 한 문장을 정정하면 같은 경험을 가리키는 모든 문서와 근거 원장을 확인한다. 문서 근거로 고칠 수 있는 내용은 자동으로 수정하고 후보자만 확정할 수 있는 내용만 질문으로 돌린다.
- 동기, 당시 제약, 본인 판단, 기각한 대안, 확인하지 못한 결과와 설명 가능성은 후보자에게 돌려주며, 제출 문구를 바꿀 미확인 항목이 있으면 `ready`로 판정하지 않는다.
- 사실 근거 감사와 설득력 평가는 `resume-preparer` 안에서 순서와 기준을 분리하되 별도 사용자 스킬로 노출하지 않는다.
- 최종 `ready` 판정은 각 제출 문서, 근거 원장, 검토표와 PDF manifest의 해시가 일치할 때만 허용한다.
- claim ledger를 다시 설명하는 evidence audit, 공통 디자인을 복제한 공고별 design 문서와 이전 제출 PDF는 만들거나 보존하지 않는다.

`fit-analysis.md`, `cover-letter.md`, `submission-checklist.md`를 모든 지원 건에 만드는 대안은 같은 내용을 여러 파일에서 반복하게 하므로 기각한다.
별도 Markdown reviewer를 유지하는 대안은 작성 스킬의 자기검토와 계약 검사를 반복하고 소비되지 않는 `review.md`를 늘리므로 기각한다.
이력서 작성, 근거 감사와 HTML 평가를 각각 별도 스킬로 유지하는 대안은 사용자가 실행 순서를 판단하게 하고 같은 제출 문서를 세 스킬이 번갈아 소유하므로 기각한다.
모든 제출 문서 책임을 `application-package-writer`에 넣는 대안은 공고 분석과 문서 검증의 조건을 한 진입점에 과도하게 쌓으므로 기각한다.
사용자용, 원본과 내부 파일을 하위 디렉터리로 바로 이동하는 대안은 현재 생성기와 검증기의 상대 경로 계약을 동시에 깨뜨리고 다음 실행에서 중복 파일을 만들 수 있어 이번 변경에서는 기각한다. 물리적 분리는 모든 생산자와 검증기를 함께 바꾸는 별도 마이그레이션으로 다룬다.
공통 프로필을 `application-form.json`에서 참조만 하는 대안은 제출 시점의 실제 입력값을 검토하고 재현할 수 없으므로 기각한다. 대신 private brain을 기준으로 현재 값을 복사하되 출처와 확인일을 함께 기록한다.

### 결과

사용자는 한 화면과 최종 제출물만 중심으로 검토한다.
준비 상태는 합격 보장이 아니라 현재 근거와 사용자 확인이 충분한지를 나타낸다.
