# 실행 흐름

career-os의 각 흐름은 외부 입력을 검증하고, 사용자 판단에 필요한 산출물을 만든 뒤, 승인 없이는 외부 상태를 바꾸지 않는 데서 끝난다.

## 포지션 추천

외부 채용 소스의 열린 공고에서 실제 지원 후보를 고른다.

1. `config/position-collection.ts`와 회사별 채널 설정을 읽는다.
2. 소스 어댑터가 개별 공고를 공통 형태로 수집한다.
3. 스크립트가 종료 여부, 마감일, URL 중복과 억제한 개별 공고 URL을 검사한다.
4. 유효한 공고만 이번 실행의 임시 후보풀에 저장한다.
5. 모델이 후보자 프로필과 원문 공고를 모두 읽고 개수 제한 없이 기준을 통과한 추천 대상을 선별하며 전체 후보의 적합도 순위와 한 줄 판단을 만든다.
6. 추천 결과와 전체 후보 순위가 후보풀의 모든 공고와 정확히 일치하는지 검증한다.
7. 같은 추천 데이터에서 상위 3건의 우선 검토 카드, 나머지 추천, 별도 보류·주의 목록과 검색 가능한 전체 순위로 구성된 반응형 HTML 리포트를 만든다.
8. 게시와 검증이 끝나면 후보풀, 추천 데이터와 HTML을 삭제한다.
9. 사용자는 공개 URL에서 공고 원문을 확인하고 지원 또는 제외를 결정한다.

모델은 닫힌 공고를 추측해 제거하지 않는다.
마감일과 활성 상태처럼 명시적으로 확인할 수 있는 조건은 수집 코드가 처리한다.

## 지원 준비와 검증

선택한 공고 하나에 맞춘 지원 자료를 만들고 제출 가능성을 검증한다.

1. 공고 경로가 없으면 private brain에서 현재 지원 대상을 찾고 대응하는 지원 디렉터리를 확인한다.
2. 공식 공고와 회사 문화 자료의 최신 상태를 확인한다.
3. 기존 후보자 인터뷰 답변을 읽고 비어 있는 질문만 한 번에 하나씩 확인한다.
4. 공고 요구사항과 회사 기준을 후보자 근거에 연결하고 확인됨, 인접 경험, 공백과 사용자 확인으로 나눈다.
5. 지원 판단과 근거를 `application-package.md`에 통합하고 제출용 이력서 초안을 만든다. 지원 화면이 경력기술서를 받으면 별도 초안도 만든다.
6. 공고 책임, 제출 근거 방어와 경험 공백을 `interview-questions.json`에 구조화한다.
7. 원본, 후보자 인터뷰 기록과 현재 제출 파일 링크를 `application-package.html` 하나로 묶는다.
8. 사용자는 이 화면에서 지원동기, 소유권, 가장 강한 사례, 공백과 입사 후 기여 시나리오를 검토한다.
9. 공고 원문, 후보자 답변과 제출 문서를 다시 대조하고 계약 검사로 누락과 공개 범위를 확인한다.
10. 준비 상태는 `ready`, `needs_user_input`, `revise`, `do_not_apply` 중 하나로 남긴다.
11. 최종 제출 문서, 근거 원장과 점수표의 문구 해시가 모두 일치해야 `ready`로 끝낸다.
12. `ready`여도 실제 제출은 사용자 승인 전까지 수행하지 않는다.

## 이력서 근거 감사와 개선

이력서와 경력기술서 문장을 실제 업무 근거에 연결하고 HTML 결과를 반복 개선한다.

1. 각 제출 문서의 Markdown 원본과 디자인 계약으로 HTML과 PDF를 만든다.
2. 최신 이력서와 후보자 프로필에서 검증할 주장을 추출한다.
3. 업무 문서, 코드, 테스트, Git 이력, 공개 결과물을 대조한다.
4. 구현, 소유권, 결과와 경험 깊이를 분리해 근거 장부를 만든다.
5. 코드 사용과 기능 개발만 확인되고 운영 노하우가 불명확하면 후보자에게 한 번에 한 질문으로 확인한다.
6. 근거가 약한 문장은 삭제하거나 확인 가능한 표현으로 낮춘다.
7. 사용자 확인이나 수정 판정이 남으면 최종 평가를 시작하지 않는다.
8. evaluator가 공고와 제출 PDF만으로 블라인드 채용 담당자·기술 리더 판정을 먼저 만든다.
9. 근거 방어, 내용, 가독성, 채용 공고 적합도와 HTML 품질을 채점한다.
10. 두 검토자가 모두 통과하고 경쟁상 차단 항목이 없을 때만 점수표를 `pass`로 기록한다.
11. 점수표에는 평가한 파일명과 근거 원장과 같은 문구 해시를 기록한다.
12. 정적 검사와 실제 브라우저 렌더링으로 페이지 수와 잘림을 확인한다.
13. 보이는 문구가 바뀌면 해당 문서의 근거 감사와 평가를 다시 실행한다.
14. 경력기술서가 있으면 별도 PDF와 통합 `submission.pdf`를 만들고, manifest의 파일 해시까지 제출 묶음 검사를 통과한다.

개인 연락처가 포함된 이력서는 사용자의 명시적 요청 없이 공개 게시하지 않는다.

## 기술·인성 면접 답변 연습

짧은 답변을 반복하고 약점을 다음 실행에 반영한다.

1. 포지션별 연습이면 private brain에서 현재 지원 대상을 찾는다.
2. 대응하는 지원 디렉터리의 포지션 질문, 공개 질문 은행과 개인 질문 자료에서 문제를 고른다.
3. 사용자가 먼저 자신의 답변을 작성한다.
4. 에이전트가 정확성, 구조, 근거, 전달력을 평가한다.
5. 보완할 핵심과 다음 복습 시점을 정한다.
6. `state/drill-progress.json`에 진행 상태를 갱신한다.
7. 현재 지원 대상이 있으면 공고 책임, 근거 방어와 명시한 경험 공백을 후속 질문에 반영한다.

완성 답변을 먼저 길게 제공하지 않는다.
사용자의 생각을 바탕으로 실제 말할 수 있는 답변을 만드는 데 집중한다.

## 아침 읽을거리 추천

등록된 외부 소스에서 그날 읽거나 볼 가치가 높은 자료를 선별한다.

1. `config/external-reading-sources.ts`의 활성 소스를 모두 읽는다.
2. 피드와 페이지 어댑터가 최신 글과 영상을 결정적으로 수집한다.
3. URL 중복과 수집 실패를 정리해 후보풀을 만든다.
4. 모델이 글의 내용, 시의성, 출처 신뢰도, 사용자 경력 방향을 함께 보고 선별한다.
5. 회사 기술 블로그, 개발 동향, 엔지니어 성장, AI 공식 자료와 영상 추천을 카테고리별로 제시한다.
6. 같은 선별 결과에서 Markdown과 HTML을 만든다.
7. 리포트에는 카테고리, 제목, 요약, 추천 이유, 원문 링크를 담는다.
8. `report-publisher`로 Cloudflare Pages에 게시하고 공개 URL을 검증한다.
9. 게시 검증 뒤 시스템 임시 경로의 실행 자료를 정리한다.

외부 자료가 없는 학습 주제를 모델이 새로 만들지 않는다.
AI 공식 자료는 모델, 에이전트, 하네스, 평가와 개발 도구를 함께 검토한다.
`study-topic-recommender` 호출은 공개 가능한 아침 리포트의 게시 요청을 포함한다.

## 질문 은행 갱신

공개 가능한 일반 질문과 개인 경험 질문을 분리한다.

1. 공식 원문을 열어 URL과 확인일을 검증한다.
2. 출처 묶음을 `public/question-bank/sources.json`에 등록하거나 기존 항목을 재사용한다.
3. 공개 질문 후보의 중복과 표현을 검증한다.
4. 일반화할 수 있는 질문만 `public/question-bank/`에 추가한다.
5. 개인 경력에서 반복해서 연습할 일반 질문은 `private/question-bank/`에 둔다.
6. 공고와 지원 근거에서 나온 포지션별 질문은 해당 `applications/` 디렉터리의 `interview-questions.json`에 둔다.
7. 답변 연습은 세 범위를 합쳐 사용할 수 있지만 공개 산출물에는 개인 질문과 포지션별 질문을 포함하지 않는다.

## HTML 리포트 게시

사용자가 공유 링크를 요청했을 때만 외부 게시까지 이어간다.

1. 리포트 HTML을 시스템 임시 디렉터리에 만든다.
2. 개인 정보, 비공개 회사 맥락, 로컬 절대 경로를 검사한다.
3. `report-publisher` skill로 Cloudflare Pages에 게시한다.
4. 게시된 페이지와 핵심 링크가 열리는지 확인한다.
5. 임시 HTML과 중간 데이터를 삭제한다.
6. 검증된 URL과 다음 행동을 사용자에게 전달한다.

사용자가 로컬 사본을 명시적으로 요청한 경우에만 지정한 경로에 보존한다.
