확인하지 못한 값은 추정하지 않고 확인하지 못했다고 적는다.

## 실행을 막았던 결함

먼저 배포돼 있던 image에서는 쓰기 요청이 모두 첫 호출부터 409로 거절됐다.
응답 메시지는 `같은 요청이 처리 중입니다.`였다.

Bun 1.3.5의 MySQL driver는 DML 결과의 `count`에 반환한 행 수를 담는다.
INSERT에서는 반환할 행이 없으므로 그 값이 항상 0이고,
실제로 바뀐 행 수는 `affectedRows`에만 들어온다.
컨테이너 안에서 직접 측정한 값이다.

| 요청 | `count` | `affectedRows` |
| --- | --- | --- |
| INSERT IGNORE 성공 | 0 | 1 |
| INSERT IGNORE 중복 | 0 | 0 |
| UPDATE 1행 | 0 | 1 |
| DELETE 1행 | 0 | 1 |

`startReceipt`는 `result.count === 1`로 멱등 키 선점 성공을 판정했다.
그래서 INSERT가 실제로 성공해도 항상 실패로 봤다.
`idempotent`는 이 판정을 try 블록 밖에서 하므로 정리 단계인 `abandonReceipt`가 실행되지 않는다.
결과로 `request_receipts`에 `processing` 행만 남고 그 멱등 키는 다시 쓸 수 없게 된다.

영향 범위는 수집 실행 저장, 분석 결과 반영, 추천 실행 생성, 분석 정책 설정,
회사 정책 설정이다. 쓰기 경로 전체가 해당한다.

기존 검사는 메모리 구현만 확인했다.
MySQL 통합 검사는 `CAREER_RECOMMENDATION_TEST_DATABASE_URL`이 없으면 건너뛰도록 돼 있고
실제로 건너뛰고 있었다. 그래서 이 결함이 검사에 걸리지 않았다.

`73cd604`에서 `affectedRows`를 보도록 고치고
driver가 실제로 돌려주는 결과 모양을 고정하는 검사 둘을 추가했다.
고친 코드를 운영 데이터베이스에 직접 연결해 최초 선점, 중복 거절, 완료 응답 복원, 정리를 확인했다.

같은 브랜치에서 `cli-contract.test.ts`의 추천 fixture가 schema 9에 머물러 있어
검사 8건이 실패하던 것도 schema 10에 맞춰 고쳤다.

## 실행 경로

평소 이 추천은 Hermes cron이 매일 07:30에 실행한다.
그 job은 `position-recommender`와 `report-publisher` 스킬을 붙이고
`gpt-5.6-terra` 모델과 `openai-codex` 제공자, 추론 강도 `medium`으로 돈다.

Hermes gateway가 떠 있지 않아 오늘 07:30 job은 발동하지 않았다.
2026-09-18에 시작된 Hermes 세션이 하나도 없는 것을 확인했고
포지션 추천 cron의 마지막 실행은 2026-09-17 07:30이다.

`cron tick`은 밀린 job을 모두 실행하므로 다른 워크스페이스 job까지 함께 발동한다.
그래서 cron job의 지시문과 스킬, 모델, 제공자, 추론 강도, 작업 디렉터리를 그대로 두고
한 번만 실행했다. 중복 실행은 없다.

## 실행과 공고와 분석의 연결

| 실행 | 식별자 | 상태 |
| --- | --- | --- |
| 수집 | `position-postings-2026-09-18T00:36:03.405Z` | `completed` |
| 분석 | `85ad5728-8f5c-534b-8fc9-90253e68cdd3` | `completed` |
| 추천 | `38a3921d-49cf-5496-8095-c5f9b888b766` | 생성됨 |

선택한 20건의 처리 결과다.

| `result_status` | 건수 | `analysis_id` 있음 | `failure_code` 있음 | 최대 제출 횟수 |
| --- | --- | --- | --- | --- |
| `created` | 20 | 20 | 0 | 1 |

`pending`, `reused`, `failed`로 남은 항목은 없다.
그래서 분석 실행은 `partial`이 아니라 `completed`로 끝났고 재제출은 일어나지 않았다.

ADR-119가 요구하는 정합성 조건도 확인했다.
`created`인 20건이 가리키는 분석과, `created_by_analysis_run_id`가 이 실행인 분석이 모두 20건으로 같다.

선택 이유는 우선 슬롯 16건과 대기 보장 슬롯 4건으로 정책의 슬롯 배분과 같다.
20건 모두 분석 상태가 `new`였다.

빈 데이터베이스에서 시작한 첫 실행이라 재사용할 분석이 없었다.
그래서 재사용 경로와 만료된 분석의 재분석 경로는 이번 실행으로 확인하지 못했다.
`staleAfterDays`가 30이므로 이 두 경로는 다음 실행부터 확인할 수 있다.

회사 제외 정책은 이번 실행에서 적용되지 않았다.
`company_preferences`가 0행이라 모든 회사가 기본 tier 3으로 처리됐다.
개인 제외 규칙은 수집 직후에 3건을 제거했고 이 값은 수집 실행과 추천 응답에 함께 남았다.

## 수집 소스 실패가 보이는 곳

설정된 소스 16개 중 `coupang-careers` 하나가 부분 실패했고 실패 건수는 14건이다.
나머지 15개는 정상이다.

| 자리 | 실패가 보이는가 |
| --- | --- |
| `position_source_run_diagnostics` 표 | 보인다. 소스 이름, 상태, 실패 건수 |
| 추천 응답의 `collectionHealth.warningSources` | 보인다 |
| 공개 리포트 HTML의 수집 경고 절 | 보인다 |
| 사용자에게 전달된 최종 답변 | 보이지 않는다 |

리포트에는 `coupang-careers · partial · 실패 14건`과 함께
일부 공고를 확인하지 못해 후보가 누락됐을 수 있다는 문장이 붙는다.
원본 오류 문구와 URL 목록은 들어가지 않는다.

**사용자가 받는 최종 답변만 보고는 수집 실패를 알 수 없다.**
cron job의 지시문이 정한 답변 형식은 수집 후보 수, 추천 수, 상위 3건과 리포트 링크만 담는다.
수집 경고 자리가 없다. 실제로 이번 답변도 `수집 후보 121건 · 실제 추천 10건`까지만 적었다.
실패를 확인하려면 리포트를 열어야 한다.

2026-09-17 조사에서 남긴 문제 중 리포트에 실패가 전달되지 않던 부분은 해소됐다.
최종 답변까지 전달되지 않는 것은 남아 있다.

## 남은 설정과 위험

- `company_preferences`가 0행이다.
  등록된 회사가 없어 모든 공고가 기본 tier 3으로 처리되고 회사별 우선순위가 실제로 작동하지 않는다.
  우선 슬롯 16건의 순서도 tier가 구분하지 못했다.
  20건이 모두 tier 3이고 분석 상태도 모두 `new`였으므로
  남은 기준인 마감 긴급도와 대기 시작 시각, 공고 식별자만 순서를 정했다.
  회사 우선순위를 쓰려면 회사 정책 설정 명령으로 tier와 제외 여부를 한 번 넣어야 한다.
- Hermes gateway가 떠 있지 않아 cron이 발동하지 않는다.
  이 상태가 이어지면 다음 날 추천도 자동으로 실행되지 않는다.
- 배포한 Backend image는 홈서버 로컬에만 있다.
  registry push가 권한 부족으로 거절돼 image를 지우면 `73cd604`에서 다시 만들어야 한다.
- MySQL 통합 검사는 접속 정보 환경 변수가 없으면 건너뛴다.
  이번 결함이 검사에 걸리지 않은 이유이므로 이 검사를 실제로 실행하는 경로가 필요하다.
