# application-package-writer 단계별 감사

단계마다 같은 기준으로 훑는 작업이다.
1단계부터 3단계까지 끝났고, 4단계부터 8단계가 남았다.

## 목표

**각 단계가 의도한 대로 도는지 확인할 수 있게 만든다.**
스크립트는 반드시 참이어야 하는 것만 보고, 무엇을 더 담을지는 모델이 정한다.

## 단계 하나를 볼 때 확인하는 다섯

| 확인할 것 | 1단계부터 3단계까지 이 순서로 문제가 나왔다 |
| --- | --- |
| 이 단계가 무엇을 만드는가 | 2단계는 첫 문장이 활동이었고 산출물이 없었다 |
| 만든 것이 어느 파일 어느 자리에 앉는가 | 3단계는 「결론」 절을 어느 단계가 쓰는지 적혀 있지 않았다 |
| 뽑은 것을 누가 소비하는가 | `공백` 판정이 6단계 「보완할 공백」으로 간다는 연결이 없었다 |
| 규칙이 이 단계 것인가 | 2·3단계가 `fit-judgment.md` 의 통과 조건을 복제했다 |
| 모델이 지시 없이도 하는가 | 「공고 요구를 근거에 연결한다」는 단계 이름을 다시 쓴 것이었다 |

판정 기준 전체는 `harness-cleanup` 의 `references/judgment.md` 와 `references/audit-axes.md` 가 소유한다.

## 끝난 것

### 산출물을 관심사별로 나눴다

`evidence/application-package.md` 하나가 셋이 됐다. 단계별 분리는 막힌다.
적합도 표 하나를 1·2·3단계가 열로 나눠 채우기 때문이다.

| 파일 | 절 | 채우는 단계 |
| --- | --- | --- |
| `evidence/fit.md` | 결론, 공고 항목별 적합도, 소계와 총점, 공개 자료로 확인한 팀과 인접 사례 | 1, 2, 3 |
| `evidence/strategy.md` | 승부처, 지원동기, 기여 시나리오, 얻을 경험과 성장, 보완할 공백, 회사 문화와의 연결, 면접에서 검증받을 내용 | 5, 6 |
| `evidence/status.md` | 준비 상태 세 줄과 적합도 총점, 제출 준비 상태, 사용자 확인 필요, 다음 행동 | 3, 6, 8 |

### 스크립트가 모델을 막던 자리를 없앴다

| 없앤 것 | 이유 |
| --- | --- |
| `growth_section.ts`, `fit_score.ts` | 하위 절 다섯의 이름과 순서, 점수 계산과 표 모양을 강제했다 |
| 필수 파일과 계약 밖 파일 검사 | 문서의 모양을 검사기가 정하고 있었다 |
| 필수 절 이름과 준비 상태 세 줄의 허용값 | 같은 이유다. 화면은 없는 값을 「판정 대기」로 보여준다 |
| 판정별 점수와 구분별 가중치, 총점 계산식 | 공고마다 다른 값이 고정이었다. 모델이 정하고 계산식을 남긴다 |

**검증기는 이제 제출 문서와 지원서 답변의 내부 정보 유출만 본다.** 188줄에서 66줄이 됐다.
렌더러는 없는 원본 파일과 없는 상태 값을 견딘다.

### 단계별로 고친 것

| 단계 | 넣은 것 |
| --- | --- |
| 1 | 산출물 둘, 공고를 읽는 방법(표에 올릴 것, 구분 셋으로 옮기는 표, 쪼개는 기준, 원문 표현) |
| 2 | 산출물 둘(근거 열, 공개 자료 절), 자료를 읽는 순서, 로컬 저장소가 사라지는 문제 |
| 3 | 산출물 셋(판정 열, 소계와 총점, 결론), 부적합일 때 넷을 적을 자리 |

「요구사항과 근거」 절은 없앴다. 지원 건 셋이 같은 절에 셋 다 다른 것을 담고 있었다.

### 소유권을 옮겼다

| 무엇 | 어디로 |
| --- | --- |
| 판정 값, 판단 기준, 점수를 정하는 방식 | `docs/data-schema.md` 에서 `references/fit-judgment.md` 로 |
| 적합도 점수의 색 구간 | `render_application_package.ts` 가 소유 |

## 여덟 단계를 모두 봤다

4단계부터 8단계까지 고친 것이다.

| 단계 | 넣은 것 |
| --- | --- |
| 4 | 산출물 둘(확보된 답변, 미확인 질문), `사용자 확인` 을 닫는 자리, 지원동기 넷의 통과 조건 |
| 5 | 산출물 하나, 지원 순서를 「결론」에 적는 것. 나머지는 `growth-judgment.md` 에 위임 |
| 6 | 산출물 셋, 여섯 절이 어느 단계에서 받아 쓰는지의 표, `readiness` 연결 |
| 7 | 검토, 수정, 질문의 순서. 끝나면 `human-confirmation` 을 바꾼다 |
| 8 | 검증기와 렌더 명령, 1단계의 이력서 작성 안내를 넘기는 연결 |

**가장 큰 것은 8단계였다.** 검토 화면을 만드는 명령이 스킬 어디에도 없었고,
검증기도 3단계에서 뺀 뒤 옮기지 않아 제출 문장 유출 검사가 한 번도 돌지 않았다.

한 번에 묶는 질문 수를 아홉 자리에서 6에서 넷으로 고쳤다. 질문 도구가 넷까지 받는다.
`docs/adr/` 의 두 건은 이력이므로 그대로 뒀다.

## 앞으로 볼 것

- `resume-preparer` 를 같은 다섯 기준으로 훑는다. 8단계가 그 스킬로 넘어간다.
- `evidence` 값 `safe|revise|blocked` 의 뜻이 코드에도 문서에도 없다. 지울 자리가 아니라 채울 자리다.
- 사라진 규칙 하나. 대상을 하나로 좁히지 못하면 임의로 고르지 않고 한 가지 질문으로 확정한다.

## 감사가 찾았으나 아직 반영하지 않은 것

- `render_application_package.ts` 가 절 목록을 `package_contract.ts` 와 따로 갖는다.
  검증기에서 필수 절을 없애 이제 사본이 아니라 화면의 탭 구성이므로 다시 볼 필요가 있다.
- `evidence` 값 `safe|revise|blocked` 의 뜻이 코드에도 문서에도 없다. 지울 자리가 아니라 채울 자리다.
- `readiness` 허용값이 여러 자리에 흩어져 있다.

## 이 저장소의 함정

**고친 파일이 커밋 사이에 옛 내용으로 돌아간다.** 실측으로 네 번 일어났다.

- `position-recommender/SKILL.md` 에서 2단계의 통과 조건과 `WARN` 설명이 사라진 채 커밋됐다.
- `application-package-writer/SKILL.md` 에서 비유어 하나를 아홉 자리 고치고
  `grep` 으로 없는 것까지 확인했는데, 커밋된 내용에는 옛 문장이 그대로였다.

대응은 셋이다.

- 편집과 확인을 한 Bash 명령에 묶는다.
- 커밋한 뒤 `git show HEAD -- <파일>` 로 실제 들어간 줄을 본다.
- 표 행은 `korean-check` 가 건너뛰므로 `grep` 을 함께 돌린다.

표를 통째로 매칭하지 않는다. 포매터가 정렬한 공백 때문에 행 전체 치환이 실패한다. 셀 내용만 바꾼다.

## 검증 명령

```bash
cd career-os
bun test ./.claude/skills/application-package-writer/scripts/
~/.claude/skills/korean-check/scripts/check.sh <파일>
```

저장소 루트에서 `bunx tsc --noEmit` 도 함께 돈다.
지원 건 셋이 모두 검증과 렌더를 통과하는지도 본다.

```bash
for d in applications/*/*/; do
  bun .claude/skills/application-package-writer/scripts/render_application_package.ts "$d" >/dev/null || echo "FAIL $d"
done
```

`career-os/AGENTS.md` 와 `accountbook/` 열 파일은 이 작업 전부터 작업본에 있던 변경이다.
